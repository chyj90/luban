# Sprint 1：连接企业系统 + 工具注册表

> **状态：🔴 待审阅** | **周期：4 周** | **目标：鲁班连接企业系统，以问数为核心服务，通过 A2A 协议供外部 Agent 调用**
>
> Sprint 1 的核心定位是「问数」——让企业数据可被自然语言查询。鲁班作为 Agent，通过 A2A（Agent-to-Agent）协议与外部 Agent 协作，将企业 HTTP API、SQL 查询、企业 MCP 统一注册为工具，鲁班 Agent 自主规划调用并返回结果。通用工具基础设施为后续扩展（开发、运维等）奠定基础。

## 零、现有基础（基线）

Sprint 1 不是从零开始，以下能力已存在，直接复用：

| 模块 | 实现 | 对 Sprint 1 的影响 |
|------|------|------|
| 鲁班 Web Agent | 3 个智能体，ReAct + Plan-Execute 双模式，浏览器端运行 | **不动**，功能定位为 AI 辅助开发（CodePage 可视化、代码生成），与核心 Agent 完全独立 |
| 鲁班核心 Agent | **Sprint 1 新建**，后端运行，管理员配置大模型端点 + SK | 系统核心，负责问数、工具调用，不暴露给用户，稳定运行 |
| 可视化看板 | CodePage（HTML/CSS/JS）+ iframe 实时预览 | 无需改动 |
| 人审批流程 | 拖拽设计器 + ProcessEngine（JPA 状态机） | 扩展：支持 `scope=PLATFORM` 平台级内置流程，`applicationId` 改为可空 |
| 数据源管理 | Datasource CRUD，MySQL 直连 | SQL 工具的数据源直接复用 |
| 查询管理 | Query CRUD，SQL 编写与执行 | SQL 执行器复用 QueryService |
| 用户认证 | Spring Security + JWT | 内部 API 沿用 JWT，外部连接新建 API Key 认证 |

> **关键架构决策：鲁班有两个 Agent，定位完全不同，不可混用。**
>
> | Agent | 运行位置 | 配置方式 | 定位 | 用户可见 |
> |-------|---------|---------|------|:--:|
> | **Web Agent** | 浏览器端 | 用户自己配置 API Key | AI 辅助开发（CodePage、代码生成） | ✅ 用户可见 |
> | **核心 Agent** | 后端服务器 | 管理员统一配置大模型端点 + SK | 系统级服务（问数、工具调用、A2A） | ❌ 不暴露 |
>
> 核心 Agent 是鲁班的"发动机"，管理员配置后全局生效，所有问数、工具调用、外部 Agent 请求都经过它。Web Agent 是鲁班的"开发助手"，只服务于 CodePage 等开发场景。

## 一、Sprint 目标

**核心价值：Sprint 1 新建鲁班核心 Agent（后端运行），作为系统级服务，负责问数、工具调用、A2A 交互。与现有 Web Agent（AI 辅助开发）完全独立，管理员统一配置大模型端点 + SK。**

核心 Agent 通过三级渐进式策略（系统路由 → 语义检索 → Schema 加载）按需将工具暴露给大模型，避免 prompt 冗长。**双向 MCP：鲁班既是 MCP Server（暴露工具），也是 MCP Client（调用企业 MCP）。**

**关键验收标准：**

| # | 场景 | 操作 | 预期结果 | 对应路径 |
|---|------|------|---------|---------|

| 3 | 工具注册 | 在控制台注册一个 HTTP 工具和一个 SQL 工具 | 工具列表可见，可测试调用 | 路径一 |

| 5 | MCP 暴露工具 | Claude Desktop 配置鲁班 MCP 地址 | 连接成功，Agent 能看到鲁班注册的企业工具 | 路径二 |

| 7 | 鲁班调用企业已有 MCP 问数 | 注册企业 MCP Server，Agent 对话问"这个月销售额" | 鲁班自动发现企业 MCP 工具，调用并返回数据 | 路径六 |

## 一、二 使用路径与角色定义

### 平台角色体系

Sprint 1 引入平台级角色，通过复用现有 `workflow_roles` 表并增加 `scope` 字段区分平台角色和应用角色。

| 平台角色 | slug | 职责 | 可见菜单 |
|------|------|------|------|
| **超级管理员** | `super_admin` | 全局管理：人员 + 系统 + 审批 | 全部 |
| **系统管理员** | `system_admin` | 管理系统连接 + 审批 | 系统连接、工作中心 |
| **企业普通员工** | `user` | 日常问数 + 流程 | 工作中心 |
| **外部开发者** | `developer` | 开发接入 | 系统连接（仅我的Key + MCP网关） |

> **复用 Role 表方案：** 现有 `workflow_roles` 加 `scope` 列（`APP` / `PLATFORM`），平台角色 `applicationId = NULL`。新增 `user_role` 关联表（`user_id` + `role_id`）替代现有 `memberIds` JSON 字段，新增 `user_dept` 关联表（`user_id` + `department_id`）。
> 
> **多角色支持：** 一个人可以同时拥有多个平台角色，不互斥。例如一个人可以同时是 `system_admin`（管理 MES 系统）和 `developer`（写代码开发），菜单按角色并集展示。

### 角色定义

Sprint 1 涉及四类角色：

| 角色 | 身份 | 持有什么 | 做什么 |
|------|------|------|------|

### 直属领导与部门领导：在哪里维护

审批链中「直属领导」和「部门负责人」不是凭空生成的，依赖现有数据模型中的两个字段：

| 审批人类型 | 数据来源 | 字段 | 维护位置 |
|------|------|------|------|
| **直属领导**（leader） | `members` 表 | `leaderId` → 指向另一个 Member 的 ID | 人员管理 → 成员管理 → 编辑成员 → 设置直属上级 |
| **部门负责人**（department_head） | `departments` 表 | `managerId` → 指向 Member 的 ID | 人员管理 → 组织架构 → 编辑部门 → 设置部门负责人 |

```
members                              departments
┌──────────────────────┐             ┌──────────────────────┐
│ 张三                  │             │ 技术部                │
│   leaderId = 李四     │──直属上级──▶│   managerId = 王五     │──部门负责人──▶ 王五
│   departmentId = 1    │──归属部门──▶│   id = 1              │
└──────────────────────┘             └──────────────────────┘
```

**审批时的查找逻辑：**

```
员工张三发起系统权限申请
  → 查 members.leaderId → 李四 → 创建审批任务给李四
  → 李四审批通过
  → 查 members.departmentId → 技术部 → 查 departments.managerId → 王五 → 创建审批任务给王五
  → 王五审批通过 → 权限生效
```

> **维护入口：** 超级管理员在「人员管理」中维护这些关系。`leaderId` 在成员编辑页设置，`managerId` 在部门编辑页设置。**这两个字段目前已有，Sprint 1 只需在人员管理页面中暴露编辑入口即可。**
>
> **Bug 修复：** 现有 `ProcessEngine.resolveAssignees()` 中 `department_head` 的查找逻辑用 `leaderId == null` 判断部门负责人（错误），Sprint 1 改为读 `Department.managerId`。

### 路径一：系统管理员注册系统与工具（核心路径）

**场景描述**：MES 系统管理员将 MES 的 HTTP API 注册为鲁班工具，并生成公私钥对用于审计签名。

**前置条件**：
- 系统管理员已登录鲁班 Web 控制台
- 系统管理员就是该业务系统的负责人（如 MES 管理员），不需要向任何人索要凭证
- 企业 API 的 URL、鉴权方式、参数格式已知

**动作步骤**：

| 步骤 | 角色 | 操作位置 | 操作 | 预期反馈 |
|:--:|------|---------|------|---------|
| 1 | 系统管理员 | 鲁班控制台 → 系统管理 | 点击「添加系统」，填写系统名称（如"MES系统"）、系统编码（如"mes"）、描述。**不需要填 Base URL 和 API 凭证——一个系统可能有多个 Base URL，** | 系统创建成功，出现在系统卡片列表中，自动生成 Ed25519 公私钥对 |
| 2 | 系统管理员 | 系统管理页 | 点击刚创建的系统卡片，公钥展示在卡片底部显著位置，点击「下载公钥」或「复制公钥」| 获取公钥文件，待回本地系统配置 |
| 3 | 系统管理员 | 本地 MES 系统代码 | 将公钥添加为配置项，在网关/拦截器中加入签名验证代码（见 2.2 节示例代码），部署上线 | 本地系统改造完成，能验证鲁班发来的请求签名 |
| 4 | 系统管理员 | 工具管理 → 工具列表 | 点击「创建工具」，进入创建表单 | 打开工具创建表单 |
| 5 | 系统管理员 | 创建工具表单 | 填写工具名称（如 `query_device_status`）、描述、选择工具类型「HTTP」、选择所属系统「MES系统」 | 表单校验通过 |
| 6 | 系统管理员 | 创建工具表单 → 接口配置 | 填写请求方法（GET）、请求 URL（`http://192.168.1.100:8080/api/device/{device_id}/status`），路径参数自动识别。**Base URL 在工具级别配置，不在系统级别** | URL 参数被自动识别并高亮 |
| 7 | 系统管理员 | 创建工具表单 → 鉴权配置 | 无需额外配置鉴权——鲁班调用该工具时，自动用所属系统的私钥签名请求，企业系统用公钥验签即完成认证。如果企业系统还有额外鉴权需求（如特定 Header），在此补充 | 鉴权默认走签名，无需手动填凭证 |
| 8 | 系统管理员 | 创建工具表单 → 参数定义 | 点击「从 URL 自动生成」，补充参数描述 | 参数 Schema 自动填充 |
| 9 | 系统管理员 | 创建工具表单 | 点击「测试调用」，输入测试参数，点击「发送请求」 | 返回 JSON 响应 |
| 10 | 系统管理员 | 创建工具表单 | 测试通过后，点击「保存」 | 工具保存成功，出现在工具列表中 |

**路径终点**：企业工具已注册到鲁班，公私钥对已生成，本地系统已改造完成。

### 路径一·附：Swagger 批量导入工具

**场景描述**：系统已有 Swagger/OpenAPI 文档，系统管理员通过 Swagger URL 或文件一次性批量导入多个 API 为鲁班工具，避免逐个手动创建。

**前置条件**：
- 系统管理员已完成路径一步骤 1-3（系统已创建，公私钥已生成，本地系统已改造）
- 企业 API 提供 Swagger/OpenAPI 3.0 文档（URL 或 JSON/YAML 文件）

**动作步骤**：

| 步骤 | 角色 | 操作位置 | 操作 | 预期反馈 |
|:--:|------|---------|------|---------|
| 1 | 系统管理员 | 系统管理页 → 目标系统卡片 | 点击「导入 Swagger」按钮 | 弹出导入弹窗 |
| 2 | 系统管理员 | 导入弹窗 | 选择导入方式：粘贴 Swagger URL（如 `http://192.168.1.100:8080/v3/api-docs`）或上传 JSON/YAML 文件 | URL 格式校验通过 / 文件解析成功 |
| 3 | 系统管理员 | 导入弹窗 | 点击「解析」，鲁班后端读取 Swagger 文档，提取所有接口路径 | 展示接口列表：路径、方法、Summary、Tags |
| 4 | 系统管理员 | 接口预览列表 | 勾选需要导入的接口（如勾选 `GET /api/device/{id}/status`、`POST /api/workorder`），取消勾选不需要的（如内部接口、健康检查） | 已勾选 N 个接口，可全选/取消全选 |
| 5 | 系统管理员 | 接口预览列表 | 点击「预览」展开某个接口，查看自动生成的工具名称、描述（取自 Swagger summary/description）、参数列表（取自 Swagger parameters/requestBody schema） | 工具预览信息完整，可手动修改名称和描述 |
| 6 | 系统管理员 | 导入弹窗 | 点击「批量导入」，鲁班将勾选的接口逐一注册为工具 | 导入完成，显示「成功导入 5 个工具」，工具列表自动刷新 |
| 7 | 系统管理员 | 工具列表 | 确认导入的工具已出现在列表中，类型为「HTTP」，所属系统为当前系统 | 工具列表可见，可逐个测试调用 |

**Swagger 字段映射规则：**

| Swagger/OpenAPI 字段 | 映射为鲁班工具字段 | 示例 |
|------|------|------|
| `operationId` 或 `summary`（驼峰化） | 工具名称 | `getDeviceStatus` |
| `summary` 或 `description` | 工具描述 | "根据设备编号查询设备状态" |
| `path` 中的 `{param}` | 路径参数 | `device_id` |
| `parameters`（query/header） | 工具参数 | `?status=running` |
| `requestBody` schema | 工具参数（body） | `{"device_id":"CNC-07"}` |
| `tags[0]` | 工具分类标签 | MES-设备管理 |
| `servers[0].url` + `path` | 完整请求 URL | `http://192.168.1.100:8080/api/device/{id}/status` |

**错误处理：**
- Swagger URL 不可达 → 提示「无法连接 Swagger 服务，请检查 URL 和网络」
- JSON/YAML 解析失败 → 提示「文档格式错误，请检查是否为有效的 OpenAPI 3.0 规范」
- 接口路径包含未解析的 `{param}` → 自动识别为路径参数，标记为「必填」
- 重复导入（工具名已存在）→ 提示「工具名已存在」，跳过或覆盖可选

**路径终点**：批量导入完成，工具已在注册表中，等待被 Agent 调用。

### 路径四：SQL 工具注册与调用（数据库查询路径）

**场景描述**：开发者在「应用开发」中已经创建了数据源和 Query，如果他是某个系统的管理员，可以直接将已有的 Query 注册为该系统的工具，让 Agent 能查询企业数据库。

**与「应用开发」中 Query 的关系：**

```
┌─────────────────────────────────────────────────────────────────┐
│ 应用开发（现有能力）                                               │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ 开发者 → 创建数据源 → 编写 Query → 在应用页面中使用           │ │
│ │                                                             │ │
│ │ Query 归属：应用（applicationId=123）                         │ │
│ │ 用途：页面渲染、流程变量、数据展示                              │ │
│ └─────────────────────────────────────────────────────────────┘ │
│                           ↓                                      │
│         如果开发者是某系统的管理员，可以将 Query 注册为工具           │
│                           ↓                                      │
│ ┌─────────────────────────────────────────────────────────────┐ │
│ │ 系统连接 → 工具注册表（Sprint 1 新增）                        │ │
│ │                                                             │ │
│ │ 系统管理员 → 选择系统 → 注册工具 → 选择「SQL」类型             │ │
│ │           → 从已有 Query 列表中勾选 → 注册为工具               │ │
│ │                                                             │ │
│ │ Query 同时归属：应用（不变） + 工具注册表（新增关联）            │ │
│ │ 用途：Agent 自然语言问数 → 调用工具 → 执行 Query → 返回结果     │ │
│ └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

**结论：不需要单独建 SQL 工具创建流程。** 开发者在应用开发中写 Query，如果他是系统管理员，在系统管理页面直接勾选已有 Query 注册为工具即可。一个 Query 可以同时服务于页面渲染和 Agent 问数。

**前置条件**：
- 系统管理员已创建数据源（Datasource）和查询（Query）（现有功能）
- Query 中已编写好 SQL 语句（如 `SELECT * FROM daily_output WHERE date BETWEEN ${startDate} AND ${endDate}`）

**动作步骤**：

| 步骤 | 角色 | 操作位置 | 操作 | 预期反馈 |
|:--:|------|---------|------|---------|
| 1 | 开发者 | 应用开发 → 数据源 | 确认数据源（MySQL）已配置且连接正常 | 数据源状态为「已连接」 |
| 2 | 开发者 | 应用开发 → Query | 编写 SQL 查询（如"日产量查询"），点击「运行」测试 SQL 可正常执行 | 返回查询结果，确认 SQL 正确 |
| 3 | 系统管理员 | 系统连接 → 系统管理 → 某系统详情 | 点击「注册工具」，选择类型「SQL」，系统列出该管理员作为创建者的应用下所有 Query | 看到可注册的 Query 列表 |
| 4 | 系统管理员 | 注册工具弹窗 | 勾选"日产量查询"等 Query，设置参数映射（Query 参数自动识别），确认只读 + 行数限制 | 工具配置完成 |
| 5 | 系统管理员 | 注册工具弹窗 | 点击「测试调用」，输入参数 `startDate: "2026-08-10"`, `endDate: "2026-08-17"` | 返回数据库查询结果 JSON |
| 6 | 系统管理员 | 注册工具弹窗 | 测试通过后，点击「注册」 | SQL 工具注册成功，出现在该系统的工具列表中 |
| 7 | 企业普通员工 | Agent 对话面板 | 输入"帮我查最近 7 天的日产量" | Agent 自动调用 SQL 工具，返回结果 |
| 8 | 外部 Agent 开发者 | Claude Desktop | 输入"查询鲁班数据库中最近 7 天的产量数据" | Claude 通过 MCP 调用 SQL 工具，返回结果 |

**路径终点**：SQL 查询能力通过工具注册表暴露给 Agent，支持内外部调用。

**为什么需要这个路径：**

```
企业现状：已有 MCP Server 暴露数据查询能力
  ┌─────────────────┐
  │ 企业数据平台 MCP  │  ← 企业已部署，暴露了 query_sales、query_inventory 等工具
  └────────┬────────┘
           │ 鲁班如何对接？

  ┌─────────────────┐
  │ 鲁班 MCP Client  │  ← 鲁班连接企业 MCP，自动发现工具，注册到工具表
  └────────┬────────┘
           │ 企业普通员工问"这个月销售额多少？"
           ▼
  ┌─────────────────┐
  │ 鲁班 Agent      │  ← 自然语言 → 选择工具 → 调用企业 MCP → 返回结果

| 9 | 企业普通员工 | Agent 对话面板 | 继续追问"哪个产品卖得最好？" | Agent 自动调用 `query_products` 或继续使用 `query_sales` 按产品维度查询，返回排名 |
| 10 | 企业普通员工 | Agent 对话面板 | 输入"帮我对比一下和上个月的数据" | Agent 连续调用企业 MCP 工具（上月 + 本月），自动对比并生成分析 |

**路径终点**：企业普通员工无需知道数据在哪个系统、通过什么接口查询，只需自然语言问数，鲁班自动通过企业 MCP 获取数据。

**关键设计决策：**

| 决策点 | 选择 | 原因 |
|--------|------|------|
| 工具发现方式 | 管理员手动触发发现 + 勾选导入 | 避免自动导入不相关工具，给予管理员控制权 |
| 每次调用是否重新连接 | 按需连接，调用后断开 | 企业 MCP 连接资源有限，避免长连接占用 |
| 是否缓存工具列表 | 定时同步（默认每小时） | 企业 MCP 工具可能变动，需要定期刷新 |
| MCP_PASSTHROUGH 工具是否可编辑 | 只读（来源企业 MCP 定义） | 工具定义由企业 MCP 决定，鲁班只做透传 |

**伪代码：**

```java
// HTTP 执行器签发请求时的核心逻辑
public void signRequest(HttpRequest request, ToolDefinition tool, ToolGroup system) {
    // 1. 构造审计头
    String audit = """
        {"key_id":%d,"owner":"%s","tool":"%s","ts":%d}
        """.formatted(currentKeyId, currentOwner, tool.getName(), System.currentTimeMillis());
    request.setHeader("X-Luban-Audit", audit);

    // 2. 用所属系统的私钥签名（每个系统一对密钥，互不干扰）
    byte[] privateKey = decrypt(system.getPrivateKeyEnc());  // AES-256 解密
    byte[] signature = Ed25519.sign(privateKey, audit.getBytes(UTF_8));
    request.setHeader("X-Luban-Signature", "ed25519=" + Base64.encode(signature));
}
```

**关键约束：**

| 约束 | 说明 |
|------|------|
| 一个系统一对密钥 | 私钥和公钥存储在 `tool_group` 表，系统创建时自动生成 |
| 工具调用用所属系统的私钥 | `tool_definition.group_id` → `tool_group.private_key_enc` |
| 私钥不在代码中硬编码 | 从数据库加密字段读取，运行时解密 |
| 轮换密钥 | Sprint 1 暂不设置轮换，后续版本再考虑 |

**鲁班与企业 API 之间的信任模型：**

```
外部开发者           鲁班                      企业 API（如 MES）
    │                 │                           │
    │ ① lb_Key       │                           │
    │ ─────────────▶ │                           │
    │                 │ ② 用私钥签名请求            │
    │                 │ ────────────────────────▶  │
    │                 │                           │ ③ 用公钥验签
    │                 │                           │ ④ 验签通过 = 认证通过
    │                 │ ⑤ 返回结果                 │
    │                 │ ◀────────────────────────  │
    │ ⑥ 返回结果      │                           │
    │ ◀────────────  │                           │
```

**核心问题**：企业传统系统如何以最小改造，让鲁班安全地调用，同时用户无感知？

**方案：公私钥对即认证。** 鲁班用私钥签名请求，企业系统用公钥验证签名。验签通过即认证通过，不需要额外的 API Key 或 Token。

```
鲁班调用企业 API 时发出的 HTTP 请求：

POST /api/mes/device/status HTTP/1.1
Host: mes.internal:8080
X-Luban-Audit: {"key_id":1,"owner":"张三","tool":"query_device_status","ts":1718000000}
X-Luban-Signature: ed25519=Base64(signature)
```

两个头，各干各的：

| 头 | 作用 | 谁生成 | 谁验证 |
|------|------|------|------|
| `X-Luban-Audit` | 审计元数据：谁在什么时间通过什么工具调用了这个接口 | 鲁班 | 企业 API（可选，写日志用） |
| `X-Luban-Signature` | 签名：用私钥对 `X-Luban-Audit` 签名 | 鲁班（私钥） | 企业 API（公钥）→ **验签通过 = 认证通过** |

**签名方案：Ed25519 非对称签名**

```
┌─────────────────────────────────────────────────────────────────┐
│  密钥模型                                                        │
│                                                                 │
│  鲁班（签名方）                    企业 API（验证方）               │
│  ┌──────────────────┐            ┌──────────────────┐          │
│  │ 私钥（加密存储）   │            │ 公钥（明文存储）   │          │
│  │ 只存在于鲁班       │            │ 管理员下载后交付   │          │
│  │ 用于签名           │            │ 用于验证签名      │          │
│  │ 永不外传          │            │ 泄露也无安全风险   │          │
│  └──────────────────┘            └──────────────────┘          │
│                                                                 │
│  签名 = 认证：                                                    │
│  1. 鲁班用私钥对 X-Luban-Audit 内容签名                            │
│  2. 签名放在 X-Luban-Signature 头中                               │
│  3. 企业 API 用公钥验证签名                                       │
│  4. 验签通过 → 请求确实来自鲁班，认证通过，放行                      │
│  5. 验签失败 → 拒绝请求（401 Unauthorized）                        │
└─────────────────────────────────────────────────────────────────┘
```

**为什么需要签名？**

```
场景：系统 A 和鲁班都在企业内网，系统 A 知道 X-Luban-Audit 的格式。

┌──────────────────────────────────────────────────────────────┐
│  没有签名时：                                                   │
│                                                              │
│  系统 A ── POST /api/mes/device/status ──▶ 企业 API           │
│          X-Luban-Audit: {"owner":"张三",...}                 │
│                                                              │
│  企业 API：这是张三在调用？→ 审计日志被污染                      │
│  张三：我没调过啊！→ 无法自证清白                               │
│                                                              │
│  问题：企业 API 无法区分「鲁班发的」和「系统 A 伪造的」            │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  有签名时：                                                     │
│                                                              │
│  鲁班 ── POST /api/mes/device/status ──▶ 企业 API             │
│        X-Luban-Audit: {"owner":"张三",...}                   │
│        X-Luban-Signature: ed25519=Base64(私钥签名)            │
│                                                              │
│  系统 A ── POST /api/mes/device/status ──▶ 企业 API           │
│          X-Luban-Audit: {"owner":"张三",...}                 │
│          X-Luban-Signature: ed25519=瞎编的                    │
│                                                              │
│  企业 API：用公钥验证签名 → 鲁班的请求通过，系统 A 的请求丢弃     │
│  系统 A 没有鲁班私钥，无法伪造签名                               │
└──────────────────────────────────────────────────────────────┘
```

**签名机制：**

| 项目 | 说明 |
|------|------|
| 算法 | Ed25519（RFC 8032） |
| 密钥对 | 鲁班为每个系统自动生成一对公私钥，私钥 AES-256 加密存储，公钥明文展示 |
| 签名内容 | `X-Luban-Audit` 的原始 JSON 字符串（UTF-8 字节） |
| 头格式 | `X-Luban-Signature: ed25519=<Base64>`，Base64 为标准 Base64（RFC 4648），长度 88 字符 |
| 防重放 | `X-Luban-Audit` 中包含 `ts`（Unix 毫秒时间戳），企业 API 拒绝超过 5 分钟的请求 |

**企业系统改造：验证签名示例代码**

企业 API 只需在网关/中间件层加一段验证逻辑。以下为各语言示例：

**Java（Spring Boot 拦截器）：**

```java
// 依赖：org.bouncycastle:bcprov-jdk18on:1.78
// 或 Java 15+ 内置 Ed25519 支持

import java.security.Signature;
import java.security.spec.EdECPublicKeySpec;
import java.security.spec.NamedParameterSpec;
import java.security.KeyFactory;
import java.util.Base64;
import java.time.Instant;

public class LubanAuditInterceptor implements HandlerInterceptor {

    // 从鲁班控制台下载的公钥（Base64 编码的 raw bytes，44 字符）
    private static final String LUBAN_PUBLIC_KEY = "MCowBQYDK2VwAyEA...";

    private final PublicKey publicKey;

    public LubanAuditInterceptor() throws Exception {
        byte[] keyBytes = Base64.getDecoder().decode(LUBAN_PUBLIC_KEY);
        EdECPublicKeySpec spec = new EdECPublicKeySpec(
            NamedParameterSpec.ED25519, keyBytes);
        this.publicKey = KeyFactory.getInstance("Ed25519").generatePublic(spec);
    }

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws Exception {
        String auditHeader = request.getHeader("X-Luban-Audit");
        String signatureHeader = request.getHeader("X-Luban-Signature");

        if (auditHeader == null || signatureHeader == null) {
            return true; // 非鲁班请求，走原有认证逻辑
        }

        // 1. 解析时间戳，防重放
        long ts = parseTimestamp(auditHeader);
        if (Math.abs(Instant.now().toEpochMilli() - ts) > 300_000) {
            response.setStatus(403);
            response.getWriter().write("{\"error\":\"luban audit expired\"}");
            return false;
        }

        // 2. 提取签名
        if (!signatureHeader.startsWith("ed25519=")) {
            return false;
        }
        byte[] signature = Base64.getDecoder().decode(
            signatureHeader.substring(8));

        // 3. 验证签名
        Signature verifier = Signature.getInstance("Ed25519");
        verifier.initVerify(publicKey);
        verifier.update(auditHeader.getBytes(StandardCharsets.UTF_8));
        if (!verifier.verify(signature)) {
            response.setStatus(403);
            response.getWriter().write("{\"error\":\"luban signature invalid\"}");
            return false;
        }

        // 4. 签名通过，记录审计日志
        request.setAttribute("luban_audit", auditHeader);
        return true;
    }

    private long parseTimestamp(String auditJson) {
        // 简单解析 JSON 中的 ts 字段
        int idx = auditJson.indexOf("\"ts\":");
        if (idx < 0) return 0;
        int end = auditJson.indexOf(",", idx);
        if (end < 0) end = auditJson.indexOf("}", idx);
        return Long.parseLong(auditJson.substring(idx + 5, end).trim());
    }
}
```

**Go（HTTP 中间件）：**

```go
// 依赖：crypto/ed25519（Go 标准库，无需额外依赖）

import (
    "crypto/ed25519"
    "encoding/base64"
    "encoding/json"
    "net/http"
    "strings"
    "time"
)

// 从鲁班控制台下载的公钥（Base64）
const lubanPublicKey = "MCowBQYDK2VwAyEA..."

var pubKey ed25519.PublicKey

func init() {
    keyBytes, _ := base64.StdEncoding.DecodeString(lubanPublicKey)
    pubKey = ed25519.PublicKey(keyBytes)
}

func LubanAuditMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        auditHeader := r.Header.Get("X-Luban-Audit")
        signatureHeader := r.Header.Get("X-Luban-Signature")

        if auditHeader == "" || signatureHeader == "" {
            next.ServeHTTP(w, r) // 非鲁班请求
            return
        }

        // 1. 防重放
        var audit struct {
            Ts int64 `json:"ts"`
        }
        json.Unmarshal([]byte(auditHeader), &audit)
        if time.Now().UnixMilli()-audit.Ts > 300_000 {
            http.Error(w, `{"error":"luban audit expired"}`, 403)
            return
        }

        // 2. 提取签名
        sigBytes, err := base64.StdEncoding.DecodeString(
            strings.TrimPrefix(signatureHeader, "ed25519="))
        if err != nil {
            return
        }

        // 3. 验证签名
        if !ed25519.Verify(pubKey, []byte(auditHeader), sigBytes) {
            http.Error(w, `{"error":"luban signature invalid"}`, 403)
            return
        }

        // 4. 签名通过，传递审计信息
        r.Header.Set("X-Luban-Audit-Verified", "true")
        next.ServeHTTP(w, r)
    })
}
```

**Python（Flask 中间件 / Nginx 脚本）：**

```python
# 依赖：cryptography（pip install cryptography）
# 或 Python 3.8+ 内置（无额外依赖，但需手动实现 Ed25519）

from cryptography.hazmat.primitives.asymmetric import ed25519
from cryptography.exceptions import InvalidSignature
import base64
import json
import time

LUBAN_PUBLIC_KEY = "MCowBQYDK2VwAyEA..."  # 从鲁班控制台下载

pub_key = ed25519.Ed25519PublicKey.from_public_bytes(
    base64.b64decode(LUBAN_PUBLIC_KEY)
)

def verify_luban_audit(headers):
    """返回 (is_valid, audit_data)"""
    audit_header = headers.get("X-Luban-Audit")
    signature_header = headers.get("X-Luban-Signature")

    if not audit_header or not signature_header:
        return None, None  # 非鲁班请求

    # 1. 防重放
    audit = json.loads(audit_header)
    if time.time() * 1000 - audit["ts"] > 300_000:
        return False, "expired"

    # 2. 提取签名
    signature = base64.b64decode(signature_header.replace("ed25519=", ""))

    # 3. 验证签名
    try:
        pub_key.verify(signature, audit_header.encode("utf-8"))
        return True, audit
    except InvalidSignature:
        return False, "invalid signature"
```

**三维度分析：**

**维度一：企业传统系统改造极小**

系统管理员在创建系统时，可选择「验证模式」：

| 验证模式 | 说明 | 企业改造量 |
|------|------|:--:|
| **无验证** | 鲁班正常调用，企业无需任何改造 | **零** |
| **Ed25519 签名验证** | 企业网关加 Filter 验证 `X-Luban-Signature` 签名头，防伪造 | **~30 行代码** |

无论选择哪种模式，鲁班都会在请求头中携带 `X-Luban-Audit`（审计信息），企业可选择性读取写入日志。

关键点：**鲁班不要求企业系统提供任何凭证（API Key / Token / 密码）。企业如需验证，只需下载鲁班生成的公钥，在网关加一个签名验证 Filter 即可。验证通过 = 请求来自鲁班 = 认证通过。**

**维度二：用户好用**

- 外部开发者：只需鲁班注册 → 生成 Key → 申请工具权限 → 审批通过 → 直接用。全程不需要知道企业系统的认证细节
- 企业普通员工：Agent 对话输入自然语言，核心 Agent 自动处理签名认证，完全透明
- 系统管理员：创建系统时自动生成公私钥对，拿公钥回本地系统配置验证代码，一次配置即可

**维度三：安全**

```
┌─────────────────────────────────────────────────────────────────┐
│  纵深防御：                                                       │
│                                                                 │
│  第一层：外部开发者 → 鲁班                                         │
│    • API Key（lb_xxxx...），SHA-256 哈希存储                       │
│    • 按 API 粒度审批权限，未经审批的工具不可调用                     │
│    • 管理员可随时禁用/撤销 Key 或单个权限                           │
│                                                                 │
│  第二层：鲁班 → 企业 API                                          │
│    • Ed25519 私钥签名，公钥验证 → 签名即认证                        │
│    • 私钥 AES-256 加密存储，仅在签名时解密，用完即弃                 │
│    • 私钥对开发者完全不可见，永不出鲁班                             │
│    • X-Luban-Audit 头包含调用者身份，企业端可审计                   │
│                                                                 │
│  第三层：企业 API 自身权限                                         │
│    • 企业 API 验证签名 → 签名有效 = 请求来自鲁班，放行              │
│    • 企业可限制鲁班可访问的接口范围                                 │
│    • 企业可审计 X-Luban-Audit 头，发现异常可追溯到具体开发者          │
└─────────────────────────────────────────────────────────────────┘
```

**为什么公私钥对就是认证，不需要额外凭证？**

| 方案 | 企业改造 | 凭证管理 | 安全 | 结论 |
|------|:--:|:--:|:--:|------|
| **公私钥签名（推荐）** | 加 ~10 行签名验证代码 | 零凭证，公钥明文存储 | 私钥不外泄 | Sprint 1 采用 |
| 企业再签一个 API Key 给鲁班 | 零改造 | 需要管理额外的 Key | 多一个泄露面 | 冗余 |
| 开发者自带凭证透传 | 零改造 | 每个开发者管凭证 | 凭证分散，泄露面大 | 不推荐 |

### 2.3 SQL 执行器

**优先级：P0**

复用现有 Query 体系，让鲁班能通过工具调用数据库查询。

现有 Query 体系：
  Datasource → Query → 执行 SQL → 返回结果

SQL 执行器（新增）：
  创建工具时关联现有 Query 的 ID
  → 调用工具 → SQL 执行器 → QueryService.execute(queryId, params) → 返回结果

**功能点：**

| # | 功能 | 说明 |
|---|------|------|
| 1 | 关联 Query | 创建 SQL 工具时，选择已有的 Query |
| 2 | 参数替换 | 将传入的参数替换到 SQL 模板中（`${param}` → 实际值） |

- 如果现有 `QueryService` 没有此方法，新增即可

### 2.4 工具注册表（以企业系统为维度组织）

**优先级：P0**

统一管理所有工具（HTTP 类型、SQL 类型、MCP 透传类型）。**工具按「企业系统」聚合，一个系统 = 一个 `tool_group`。** 这里的「工具」本质是企业 API 的注册和描述。

**为什么按系统聚合：**

```
企业系统全景：
  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ MES 系统  │  │ ERP 系统  │  │ 数据平台   │  │ WMS 系统  │
  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
       │              │              │              │
  ┌────┴────┐    ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
  │ HTTP 工具│    │ HTTP 工具│    │ MCP 工具 │    │ HTTP 工具│
  │ SQL 工具 │    │ SQL 工具 │    │ SQL 工具 │    │ HTTP 工具│
  └─────────┘    └─────────┘    └─────────┘    └─────────┘

好处：
  • 同一系统的工具共享默认配置（Base URL、鉴权），减少重复
  • 管理界面按系统分组展示，快速定位，不会 100 个工具混在一起
  • 权限控制可到系统级别（某用户只能看 MES 系统的工具）
  • 新工具创建时，先选系统，系统默认配置自动填充
```

**数据库表：**

### 2.5 MCP 网关（⭐ 将企业工具暴露为 MCP）

**优先级：P1**

对外暴露 MCP Server，让外部 Agent 能通过 MCP 协议调用鲁班注册的企业工具。**这是「将传统 API 转化为 MCP 工具」的基础设施。**

**注意：MCP Server 模式与 A2A 模式的区别：**

Sprint 1 同时支持两种 Agent 对外交互模式，满足不同场景：

```
Sprint 1 实现              后续 Sprint 实现
─────────────────────      ─────────────────
MCP Server 模式             A2A 模式
外部 Agent 直接调工具       外部 Agent 委托任务给鲁班

Claude Desktop             Claude Desktop
  │                          │
  │ MCP 协议                  │ A2A 协议
  │ tools/list                │ tasks/send
  │ tools/call                │ "帮我查这个月销售额"
  ▼                          ▼
鲁班 MCP 网关               鲁班 A2A 端点
  │                          │
  │ 返回工具列表              │ 鲁班 Agent 自主规划
  │ 外部 Agent 决定调哪个     │ 选择工具、调用、组合
  ▼                          ▼
工具执行器                  工具执行器 + Agent 推理
```

**MCP Server 模式**（Sprint 1 实现）：
- 外部 Agent 直接看到工具列表，自己决定调用哪个
- 适合简单、确定的工具调用场景
- 鲁班是「工具代理」

**A2A 模式**（后续 Sprint 扩展）：
- 外部 Agent 将任务委托给鲁班，鲁班 Agent 自主规划执行
- 适合复杂、多步骤的问数场景
- 鲁班是「服务提供者」

**Sprint 1 策略**：先实现 MCP Server 模式（最快的交付路径），同时预留 A2A 端点接口，为后续 Sprint 的 A2A 模式做准备。

**功能点：**

| # | 功能 | 说明 |
|---|------|------|
| 1 | `initialize` 握手 | 返回 serverInfo（名称、版本），协商能力 |
| 2 | `tools/list` 工具发现 | 返回当前 Agent 可用的工具列表（含名称、描述、参数 Schema） |
| 3 | `tools/call` 工具调用 | 接收工具名 + 参数，调用执行器，返回结果 |

| 6 | 会话管理 | 管理 sessionId → API Key 映射，支持超时断开 |

### 2.6 API Key 认证（生成 + 权限申请 + 审批）

**优先级：P0**

为外部连接（MCP 网关 + 后续 A2A 端点）提供令牌认证。**每个外部开发者拥有一把 Key，Key 本身可随时生成，不审批。开发者用这把 Key 为具体 API/工具申请调用权限，审批通过后 Key 才具备该工具的调用权。权限按 API 粒度审批，逐次累加。**

**核心模型：**

```
┌─────────────────────────────────────────────────────────────────────┐
│  一个开发者 → 一把 Key（生成即用，无需审批）                            │
│       │                                                              │
│       ├── 权限申请 1：MES系统 → query_device_status（审批通过 ✓）       │
│       ├── 权限申请 2：MES系统 → create_work_order（审批通过 ✓）         │
│       ├── 权限申请 3：数据平台 → query_sales（待审批）                   │
│       └── 权限申请 4：WMS系统 → query_inventory（驳回 ✗，权限不足）     │
│                                                                      │
│  Key 的有效权限 = 审批通过的所有申请之和                                │
│  → { query_device_status, create_work_order }                        │
└─────────────────────────────────────────────────────────────────────┘
```

**为什么不能用 JWT：**

- JWT 需要登录态，外部 Agent 是无状态的 API 调用
- JWT 有有效期，外部 Agent 需要长期稳定的连接
- JWT 绑定用户，需区分「企业普通员工」和「外部开发者」两种身份

**数据模型：**

```sql
-- 开发者拥有的 Key（生成即用，无需审批）
CREATE TABLE api_key (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    key_hash        VARCHAR(64) NOT NULL UNIQUE,     -- SHA-256(原始 Key)，生成时即写入
    key_prefix      VARCHAR(12) NOT NULL,            -- "lb_xxxxxxxx" 前 12 位，用于展示
    name            VARCHAR(128) NOT NULL,           -- Key 名称，如"张三的Key"
    owner_id        BIGINT NOT NULL,                 -- 拥有者（员工）
    status          VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',  -- ACTIVE / DISABLED / REVOKED
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at      TIMESTAMP NULL,                  -- 可选过期时间
    last_used_at    TIMESTAMP NULL,                  -- 最后使用时间
    
    INDEX idx_owner_id (owner_id),
    INDEX idx_status (status)
);

-- 权限审批（走内置平台流程）：
-- 开发者提交申请 → 创建「工具权限申请」流程实例 → 系统管理员在「我的工作」中审批
-- 审批通过后，api_key 与 tool 的关联关系写入。Key 的有效权限 = 该 Key 关联的所有审批通过的工具。

**Key 格式：**

```
lb_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
│    └─ 32 位随机字符串，生成时即由系统产生
└─ 前缀，便于识别
```

**权限计算规则：**

```
Key 的有效权限 = 该 Key 已完成审批且关联的所有工具
例：Key id=1 关联 3 个已审批通过的工具 → 可调用 3 个工具
    Key id=1 有 1 条 PENDING 记录   → 该工具暂不可用，不影响其他工具
    Key id=1 有 1 条 REJECTED 记录  → 该工具不可用
```

**认证流程：**

```
1. 外部 Agent 连接 /mcp/sse
2. 携带 Header: X-API-Key: lb_xxxxxxxx...
3. McpApiKeyFilter 拦截：
   a. 提取 X-API-Key
   b. SHA-256(原始 Key) → 与 key_hash 比对
   c. 检查 api_key.status == ACTIVE
   d. 检查 expires_at 未过期
   e. 查询该 Key 关联的所有已审批通过的工具 → 得到可调用工具列表
   f. 通过 → 创建 sessionId → 绑定 ApiKey + 权限列表 → 返回 sessionId
   g. 不通过 → 返回 401
4. 后续所有 /mcp/messages 请求：
   a. 从 sessionId 恢复 ApiKey 和权限列表
   b. 校验 session 未过期
   c. tools/list 时只返回有权限的工具
   d. tools/call 时校验工具在权限列表中，否则返回 403
   e. 处理 JSON-RPC 请求
```

**完整生命周期：**

```
外部开发者                              系统管理员
    │                                      │
    │ ① 生成 Key                           │
    │ POST /api/v1/api-keys/generate       │
    │ ← 返回完整 Key（仅展示一次）            │
    │ 立即复制保存                          │
    │                                      │
    │ ② 为 Key 申请权限（可多次）             │
    │ POST /api/v1/api-keys/{id}/permissions│
    │ {                                    │
    │   "tool_id": 5,                     │
    │   "purpose": "飞书群展示生产数据"      │
    │ }                                    │
    │                                      │ ③ 查看待审批权限申请
    │                                      │ GET /api/v1/permissions/review
    │                                      │ 列表：申请人、Key名称、工具、用途
    │                                      │
    │                                      │ ④ 审批
    │                                      │ ├─ 通过 → 权限即时生效
    │                                      │ │  Key 可调用该工具
    │                                      │ └─ 驳回 → 填写原因
    │                                      │    开发者可重新申请
    │                                      │
    │ ⑤ 再次申请其他工具权限                 │ ⑥ 再次审批
    │ 权限逐步累加...                        │
    │                                      │
    │ ⑦ 使用 Key 调用                       │ ⑧ 可随时禁用/启用/撤销整个 Key
    │ 只可调用已审批通过的工具                │ 也可撤销单个工具的权限
```

**API 端点：**

| 方法 | 路径 | 说明 | 角色 |
|------|------|------|------|
| POST | `/api/v1/api-keys/generate` | 生成 API Key（返回完整 Key，仅此一次） | 外部开发者 |
| GET | `/api/v1/api-keys/my` | 查看我的 Key 列表和状态 | 外部开发者 |

### 2.9 鲁班调用企业已有 MCP —— MCP Client 模式（⭐ 问数核心）

**优先级：P0**

鲁班作为 MCP Client，连接企业已部署的 MCP Server，自动发现工具并注册到工具注册表。**这是「自然语言问数」场景的核心能力**——企业通常已有数据平台通过 MCP 暴露查询能力，鲁班需要对接这些 MCP 而非重复建设。

**与 2.4 MCP 网关的区别：**

```
2.4 MCP 网关（Server 模式）：鲁班 ← 被外部 Agent 调用
    Claude Desktop → MCP 协议 → 鲁班 MCP 网关 → 工具执行器

2.8 MCP Client 模式：鲁班 → 调用企业 MCP
    鲁班 Agent → MCP Client → 企业 MCP Server → 企业数据平台
```

**使用场景：问数**

```
用户："这个月销售额多少？"
  │
  ▼
鲁班 Agent（ReAct）
  │
  │ 识别需要使用 query_sales 工具
  ▼
工具注册表 → 查找 query_sales → 类型 MCP_PASSTHROUGH → 来源：企业数据平台 MCP
  │
  ▼
MCP Client 执行器 → 连接企业 MCP → tools/call → 返回数据
  │
  ▼
Agent 将数据转化为自然语言 → "本月销售额 125 万，环比增长 12%"
```

**数据模型：**

新增 `mcp_server_registry` 表，管理企业 MCP Server 连接信息：

### 2.10 工具暴露策略 —— 三级渐进式（⭐ 应对工具膨胀的关键设计）

**优先级：P0**

**问题：** 当企业系统越来越多，接入的 API、MCP 越来越多（假设 5 个系统 × 20 个工具 = 100 个工具），如果把所有工具的 JSON Schema 一次性塞进 LLM prompt，会导致：

1. **Prompt 过长**：仅工具定义就占 ~20,000 tokens，大量上下文被浪费
2. **选择准确率下降**：LLM 面对 100 个工具时选择准确率急剧下降（公认的 "tool selection degradation"）
3. **推理成本高**：每次对话都携带全部工具定义，token 消耗巨大

**方案：方案 C —— 混合模式（系统路由 + 语义检索）**

核心思路：**不把所有工具一次性塞进 prompt，而是按需加载。**

```
三级渐进式工具暴露

Tier 1：系统层（始终在 prompt 中）
┌───────────────────────────────────────────────────────────┐
│ 可用系统：                                                  │
│   • MES系统 - 生产执行系统，查询设备状态、产量、维保工单     │
│   • 数据平台 - 企业数据仓库，查询销售额、库存、订单          │
│   • ERP系统 - 企业资源计划，查询采购、财务、人事            │
│   • WMS系统 - 仓储管理，查询库存、出入库记录                │
│                                                            │
│ 约占 200 tokens，永远在 Agent 的 system prompt 中           │
└───────────────────────────────────────────────────────────┘
         │
         │ 用户："这个月销售额多少？"
         │ LLM 判断：涉及「数据平台」系统
         ▼
Tier 2：系统内工具列表（按需加载）
┌───────────────────────────────────────────────────────────┐
│ 数据平台 可用工具（语义检索 top-5）：                        │
│   • query_sales - 查询销售额（按时间、产品、区域）           │
│   • query_inventory - 查询库存                              │
│   • query_orders - 查询订单                                 │
│   • query_customers - 查询客户                              │
│   • query_finance - 查询财务                                │
│                                                            │
│ 约占 150 tokens，仅当选中该系统后加载                        │
└───────────────────────────────────────────────────────────┘
         │
         │ LLM 判断：需要 query_sales
         ▼
Tier 3：工具完整 Schema（调用时加载）
┌───────────────────────────────────────────────────────────┐
│ query_sales 完整定义：                                      │
│   input_schema: {                                          │
│     startDate: string (必填, 开始日期)                      │
│     endDate: string (必填, 结束日期)                        │
│     product: string (可选, 产品名称)                        │
│     region: string (可选, 区域)                             │
│   }                                                        │
│                                                            │
│ 约占 200 tokens，仅当确定调用该工具时加载                    │
└───────────────────────────────────────────────────────────┘

总消耗：200 + 150 + 200 = 550 tokens（vs 100 工具全量 20,000 tokens）
```

**与核心 Agent 的关系：**

三级渐进式工具暴露是核心 Agent 调用大模型时的上下文管理策略。核心 Agent 在 ReAct 循环中，每次调用大模型只携带当前 Tier 所需的上下文：

```
核心 Agent（后端，ReAct 循环）            后端 API
─────────────────────────────      ─────────────────────
                                  ┌─────────────────────┐
Step 1: LLM 调用（Tier 1 上下文）  │ GET /api/v1/tools/   │
  system prompt 包含系统列表       │ systems             │
  → 大模型输出：选中系统 = "数据平台"│ 返回系统列表          │
                                  │ （名称+描述+hint）    │
                                  └─────────────────────┘
                                  ┌─────────────────────┐
Step 2: LLM 调用（Tier 2 上下文）  │ GET /api/v1/tools/   │
  system prompt + 数据平台工具列表  │ search?system=数据平台│
  → 大模型输出：选中工具=query_sales│ &query=销售额         │
                                  │ 返回语义检索 top-5     │
                                  │ （名称+描述）          │
                                  └─────────────────────┘
                                  ┌─────────────────────┐
Step 3: LLM 调用（Tier 3 上下文）  │ GET /api/v1/tools/   │
  system prompt + query_sales     │ {id}/schema          │
  完整 input_schema                │ 返回完整 JSON Schema  │
  → 大模型输出：参数填充完成        │                      │
                                  └─────────────────────┘
                                  ┌─────────────────────┐
Step 4: 工具调用                   │ POST /api/v1/tools/  │
  → 调用执行器，返回结果            │ call                 │
                                  │ 执行工具，返回结果     │
                                  └─────────────────────┘
```

**关键点：**
- 核心 Agent 的 ReAct 循环不变，但每次 LLM 调用携带的上下文是动态的、按需加载的
- 从「一次性加载所有工具」变为「三次 LLM 调用、逐步缩小范围」
- 后端提供三个 API 支撑：系统列表、工具检索、Schema 获取
- 语义检索在 Tier 2 使用，将用户查询向量化，在选中系统的工具库中检索 top-5

**Sprint 1 直接实现完整方案 C（不分阶段）：**

| 层级 | 实现方式 | Sprint |
|------|------|:--:|
| Tier 1：系统路由 | `tool_group` 的 `system_prompt_hint` 字段直接出现在核心 Agent 的 system prompt 中 | Sprint 1 |
| Tier 2：语义检索 | 工具描述向量化，按用户查询在选中系统内检索 top-5 | Sprint 1 |
| Tier 3：Schema 加载 | 按需获取完整 input_schema | Sprint 1 |

> **不分阶段的原因：** 三级渐进式是一个整体设计，Tier 1 不加 Tier 2 语义检索，在小工具量时看不出效果，在大工具量时又不够用。Sprint 1 直接实现完整方案，确保架构从一开始就正确。

**数据库变更（Sprint 1）：**

`tool_group` 表新增字段：

```sql
ALTER TABLE tool_group ADD COLUMN system_prompt_hint VARCHAR(512);
-- 示例值："当用户询问生产、设备、产量、工单相关问题时使用此系统"
-- 该字段直接出现在 Tier 1 的核心 Agent system prompt 中，帮助大模型做系统选择
```

`tool_definition` 表新增字段（用于语义检索）：

```sql
ALTER TABLE tool_definition ADD COLUMN embedding VECTOR(1536);
-- 工具描述的向量化表示，用于 Tier 2 语义检索
-- 创建/更新工具时自动生成，默认使用 OpenAI text-embedding-3-small
```

**API 端点（Sprint 1）：**

| 方法 | 路径 | 说明 | 对应 Tier |
|------|------|------|:--:|
| GET | `/api/v1/tools/systems` | 返回所有系统列表（名称、描述、prompt_hint），供 Agent 做系统选择 | Tier 1 |
| GET | `/api/v1/tools/search?systemId=1&query=销售额` | 在指定系统内检索工具（语义检索 top-5，Sprint 1 实现） | Tier 2 |
| GET | `/api/v1/tools/{id}/schema` | 返回工具的完整 JSON Schema（input_schema + output_schema） | Tier 3 |

**Sprint 1 预期效果：**

```
假设 2 个系统、5 个工具（Sprint 1 规模）：

现有方式：                三级渐进式：
  prompt 含 5 个工具        Tier 1: 2 个系统（~100 tokens）
  全量 Schema              Tier 2: 选中系统的工具（~80 tokens）
  ~1000 tokens              Tier 3: 1 个工具 Schema（~150 tokens）
                           ─────────────────────────────
  减少不明显                总计 ~330 tokens（vs 1000）

但为后续扩展奠定了基础：
  5 个系统 × 20 个工具 = 100 工具时：
    现有方式：~20,000 tokens
    三级渐进式：~550 tokens
    节省 97%
```

## 三、非功能需求

### 3.1 性能

| 指标 | 要求 |
|------|------|
| SSE 连接建立 | < 500ms |
| tools/list 响应 | < 200ms |
| HTTP 工具调用 | < 10s（含外部 API 调用） |
| SQL 工具调用 | < 30s |
| 并发 SSE 连接 | 支持 100 个同时连接 |

### 3.2 安全

| 要求 | 说明 |
|------|------|
| API Key 哈希存储 | 数据库只存 SHA-256 哈希，不存明文 |
| API Key 仅展示一次 | 生成后立即展示完整 Key，后续只能看到前缀 |
| Session 隔离 | 不同 session 的请求互不影响 |
| 输入校验 | 所有参数校验，防止 SQL 注入（使用参数化查询） |
| SQL 只读 | 强制执行 SELECT 语句，拒绝写操作 |
| 私钥加密存储 | 每个系统的 Ed25519 私钥使用 AES-256 加密存储，仅在签名时解密，用完即弃 |
| 审计头注入 | 鲁班调用企业 API 时注入 `X-Luban-Audit` + `X-Luban-Signature`（Ed25519 私钥签名），企业端用公钥验证签名。**签名即认证，不需要额外 API Key** |
| 防重放 | `X-Luban-Audit` 含 `ts` 时间戳，企业 API 拒绝超过 5 分钟的请求，防止签名被截获后重放 |
| 私钥安全 | 每个系统的 Ed25519 私钥 AES-256 加密存储，仅在签名时解密使用，永不出鲁班 |
| 密钥隔离 | 外部开发者的 API Key 和系统的 Ed25519 私钥分属不同安全域，互不穿透 |

### 3.3 可观测性

| 要求 | 说明 |
|------|------|
| 连接日志 | 记录每次 SSE 连接建立（来源 IP、API Key 前缀、时间） |
| 调用日志 | 记录每次 tools/call（工具名、参数、耗时、结果） |
| 错误日志 | 记录所有异常，含完整堆栈 |
