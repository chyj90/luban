# 自动洞察（查数 → 懂数）行动计划

## 一、现状盘点

### 1.1 已有基础设施

| 能力 | 状态 | 说明 |
|------|------|------|
| 单轮 NL2SQL | ✅ 已稳定 | FAISS 概念检索 → LLM 生成 SQL → 执行 → 返回 |
| ReAct Agent 循环 | ✅ 已就绪 | AgentService 中 buildAgentNode → buildNl2sqlExecutorNode 循环 |
| 概念本体 | ✅ 已就绪 | Concept + ConceptRelation + ConceptMapping + ConceptJoinMapping |
| 本体推理 | ✅ 已就绪 | OntologyService.analyzeContext 支持概念扩展（maxDepth=2） |
| 关系类型 | ✅ 已就绪 | ConceptRelation.relationType 字段，当前用于 COMPUTED_FROM |
| 会话上下文 | ✅ 已就绪 | conversationHistories 保存完整对话历史，每次注入 prompt |
| 前端 Chat UI | ✅ 已就绪 | 流式 SSE 输出，支持 thinking / answer 分段 |
| Python 服务 | ✅ 已就绪 | `http://localhost:8765`，提供 embedding / FAISS / parse-file 端点 |

### 1.2 当前 Agent 流程

**现有 StateGraph 节点**（`AgentService.compileReActGraph`）：

```
agent → (tool_executor | nl2sql_executor) → agent → ... → final_answer
```

当前仅注册 4 个节点：`agent`、`tool_executor`、`nl2sql_executor`、`final_answer`。Router 仅支持 4 种路由：`tool_call`、`nl2sql`、`final_answer`、`continue`。

**现有 `buildAgentNode` 的 `parseResponse`**：只处理 `final_answer`、`tool_call`、`nl2sql` 三种类型，其他类型落入 else 分支被当作 `final_answer` 处理。**新增 `code_mode` 和 `ontology_action` 类型后，必须增加对应的解析分支。**

**现有 `buildSystemPrompt`**：只告诉 LLM 三种选择（API 工具/SQL/直接回答）。**新增 `code_mode` 和 `ontology_action` 后，必须更新 System Prompt 模板。**

**当前流程**：
```
用户提问 → FAISS 概念检索 → buildUnifiedContext（概念+表+JOIN）
  → LLM 决策（nl2sql / tool_call / final_answer）
  → 执行 SQL → LLM 总结 → final_answer
```

**差距**：当前 LLM 只有一次决策机会，如果第一轮 SQL 结果不够，LLM 不会自动再查一轮。虽然有 ReAct 循环框架，但 prompt 没有引导 LLM 做"先看趋势 → 再下钻"的多轮推理。

### 1.3 当前关系模型

```java
// ConceptRelation 实体
Long sourceConceptId;    // 源概念
Long targetConceptId;    // 目标概念
String relationType;     // 关系类型，如 COMPUTED_FROM
String expression;       // 表达式
String description;      // 描述
```

**差距**：当前 relationType 只有 COMPUTED_FROM（计算来源），缺少下钻维度关系的定义，如 DRILLS_INTO（可下钻到）、DRILLED_FROM（可被下钻）。

### 1.4 现有关系架构

```
行业（Industry）
  └── IndustryRelation（该行业允许的关系类型清单，is_transitive/is_symmetric）
        └── ConceptRelation（具体概念间的关系实例）
```

- **IndustryRelation**：定义某行业下允许使用哪些关系类型，如制造业的 `has_supplier`、`manufactured_by`，电商的 `belongs_to_category`、`bundled_with`
- **ConceptRelation**：概念间关系实例，`relationType` 必须是该行业 IndustryRelation 清单中已注册的类型
- **导入反补**：导入本体时，Python 服务从数据中推断关系类型，发现新类型自动反补到 IndustryRelation

### 1.5 平台内置关系 vs 行业自有关系

自动洞察需要的关系类型分两类，归属不同：

| 关系类型 | 性质 | 归属 | 说明 |
|---------|------|------|------|
| `DRILLS_INTO` | 下钻维度，纯分析导航 | **平台内置** | 所有行业默认可用，不可删除 |
| `DRILLED_FROM` | 上卷维度，DRILLS_INTO 的逆 | **平台内置** | 自动推导，无需手动配置 |
| `CORRELATED` | 关联维度，交叉分析提示 | **平台内置** | 所有行业默认可用，不可删除 |
| `ANOMALY_THRESHOLD` | 异常阈值，触发下钻的条件 | **不做成关系** | 做成概念属性（见 2.2.1） |
| `has_supplier`、`manufactured_by` 等 | 行业语义关系 | 行业自有 | 现状不变，导入时反补 |

**实现方式**：
- `IndustryRelation` 新增 `is_builtin` 字段，标记平台内置关系
- 平台启动时自动为所有行业注入 3 个内置关系类型（如不存在）
- 内置关系不可删除，行业自有关系正常管理
- 行业导入时发现的关系类型仍然正常反补，与内置关系共存

## 二、Phase 2：维度下钻引擎

### 2.1 目标

用户问"上个月退货率为什么涨了"，AI 自动完成：
1. **趋势确认**：查询上个月退货率趋势，确认是否真的异常
2. **按产品线拆解**：发现产品 A 退货率飙升
3. **按地区拆解**：发现华东区是重灾区
4. **按批次拆解**：发现批次 2024-B3 有问题
5. **根因输出**：汇总分析，给出自然语言结论

**核心指标**：5 个真实场景，3 轮以内定位根因，准确率 ≥ 80%。

### 2.2 技术方案

#### 2.2.1 维度关系定义

**平台内置关系**（自动下钻用）：

在现有 ConceptRelation 基础上，新增 3 个平台内置关系类型：

| 关系类型 | 含义 | 示例 | 归属 |
|---------|------|------|------|
| DRILLS_INTO | 可下钻到子维度 | 退货率 → 产品线 → 地区 → 批次 | 平台内置 |
| DRILLED_FROM | 可被上卷（自动推导） | 批次 → 地区 → 产品线 → 退货率 | 平台内置 |
| CORRELATED | 关联维度，交叉分析提示 | 退货率 ↔ 供应商合格率 | 平台内置 |

**数据库变更**：
- `industry_relation` 表新增 `is_builtin` 字段（BOOLEAN, DEFAULT FALSE），标记平台内置关系
- 平台启动时自动为所有行业注入 3 个内置关系类型（如不存在）
- 内置关系不可删除，行业自有关系（导入反补的）正常管理

**前端配置**：在概念关系编辑页面，维度关系类型（DRILLS_INTO、CORRELATED）以独立分组展示，与行业自有关系区分。

**异常阈值配置**（不做成关系）：

`ANOMALY_THRESHOLD` 不适合放在 `concept_relation` 表中，因为它是概念的属性而非两个概念间的关系。改为在 `concept` 表新增字段：

```sql
ALTER TABLE concept ADD COLUMN anomaly_threshold_expr VARCHAR(64);
ALTER TABLE concept ADD COLUMN anomaly_threshold_desc VARCHAR(256);
```

| 字段 | 类型 | 示例 | 说明 |
|------|------|------|------|
| anomaly_threshold_expr | VARCHAR(64) | `> 5%` | 异常判定表达式 |
| anomaly_threshold_desc | VARCHAR(256) | `退货率超过5%判定为异常` | 异常说明 |

Agent 在 buildUnifiedContext 时，将概念的异常阈值信息注入 prompt，LLM 据此判断是否需要触发下钻。

#### 2.2.2 Agent 循环改造（基于 LangGraph）

当前 Agent 循环基于 langgraph4j 的 StateGraph + 条件路由：

```
节点：agent → (nl2sql_executor | tool_executor) → agent → ... → final_answer
路由：AgentNode 产出的 next_action 决定走哪条边
```

**改造原则：充分利用 LangGraph 能力，不手搓循环逻辑。**

LangGraph 已提供的能力：

| 能力 | 说明 | 当前使用 |
|------|------|---------|
| StateGraph | 状态图定义，节点 + 边 | ✅ 已用 |
| Conditional Edge | 条件路由，基于 state 选择下一节点 | ✅ 已用（routerEdge） |
| AgentState | 增量状态更新，Map 支持 | ✅ 已用 |
| 消息累积 | 每轮产出追加到 messages | ✅ 已用 |
| MAX_ITERATIONS | 防止死循环，超限强制终止 | ✅ 已用 |

**改造内容**：

1. **新增 `code_executor` 节点**：处理 LLM 生成的 Python 代码（大数据量计算、统计分析）
2. **新增 `ontology_advisor` 节点**：AI 驱动的本体管理，自动建议概念/关系/映射调整，需超管权限
3. **Router 增加 `code_mode` 路由**：AgentNode 产出 `next_action = "code_mode"` 时路由到 code_executor
4. **Router 增加 `ontology_action` 路由**：AgentNode 产出 `next_action = "ontology_action"` 时路由到 ontology_advisor
5. **下钻逻辑融入 Prompt**：`drill_down` 不是新的节点类型，而是 AgentNode 的推理策略——LLM 判断需要下钻时，产出 `next_action = "nl2sql"` 并附带下钻维度的 SQL，自然进入下一轮循环
6. **根因分析融入 final_answer**：`root_cause` 不是新的节点类型，而是 final_answer 的一种输出格式

改造后的 StateGraph：

```
                          ┌─────────────────┐
         tool_call        │  tool_executor   │
     ┌───────────────────▶│  (现有，不变)     │──────┐
     │                    └─────────────────┘      │
     │                                             │
     │   nl2sql           ┌─────────────────┐      │
     ├───────────────────▶│ nl2sql_executor  │──────┤
     │                    │  (现有，不变)     │      │
┌────┴──────┐             └─────────────────┘      │
│   agent   │                                      ▼
│ (LLM 决策) │◀─────────────── 循环 ────────────────┘
└────┬──────┘
     │   code_mode         ┌─────────────────┐
     ├───────────────────▶│  code_executor   │──────┐
     │                    │  (新增)          │      │
     │                    └─────────────────┘      │
     │                                             │
     │   ontology_action   ┌─────────────────┐      │
     ├───────────────────▶│ ontology_advisor │──────┤
     │                    │  (新增,超管)      │      │
     │                    └─────────────────┘      │
     │                                             ▼
     │   final_answer      ┌─────────────────┐  循环
     └───────────────────▶│  final_answer    │──▶ END
                          └─────────────────┘
```

**关键点**：下钻不是新节点，而是 LLM 在多轮推理中自然产生的行为——Agent 看到异常 → 决定查维度 → 产出 nl2sql → 拿到结果 → 再分析 → 最终给出 root_cause 类型的 final_answer。LangGraph 的 StateGraph 天然支持这种多轮迭代，无需额外编码。

#### 2.2.3 Prompt 设计

当前 Prompt 只告诉 LLM 三种选择（nl2sql / tool_call / final_answer）。需要增加下钻模式和代码模式：

**新增 action 类型：`code_mode`**

当查询结果数据量较大（如返回数百行），或需要复杂统计计算（相关性分析、回归、聚类）时，LLM 可以选择 code_mode，生成 Python 代码在服务端执行：

```
## 代码执行模式（code_mode）

适用场景：
- 数据量超过 100 行，不适合在对话中展示
- 需要统计分析：相关性、回归、聚类、异常检测
- 需要数据可视化：趋势图、分布图、热力图
- 需要复杂计算：多表 JOIN 后的二次聚合

代码执行格式：
{
  "type": "code_mode",
  "reasoning": "退货数据有 500 行，需要按产品线做方差分析",
  "code": "import pandas as pd\nimport json\n\ndf = pd.DataFrame(json.loads(data))\nresult = df.groupby('product_line')['return_rate'].agg(['mean', 'std']).to_dict()\nprint(json.dumps(result, ensure_ascii=False))",
  "expected_output": "各产品线退货率的均值和标准差"
}
```

**注意**：`code_mode` 不替代 `nl2sql`。SQL 负责数据查询，Python 负责数据分析和计算。数据量小时 LLM 直接用 nl2sql 结果推理即可，数据量大或需要复杂计算时才走 code_mode。

**下钻分析模式（融入 nl2sql）**

当查询结果显示异常值（如退货率超过阈值），LLM 选择下钻分析，产出 `next_action = "nl2sql"` 并附带下钻维度的 SQL：

```
## 下钻分析模式

当查询结果显示异常值（如退货率超过阈值），你可以选择下钻分析：
- 先查看整体趋势，确认异常
- 按维度逐层下钻（产品 → 地区 → 批次）
- 每轮下钻聚焦一个维度，不要在单轮中同时下钻多个维度

下钻时使用 nl2sql action，附带下钻 SQL：
{
  "type": "nl2sql",
  "reasoning": "退货率整体上升 15%，超过阈值 5%，需要按产品线下钻分析",
  "drill_dimension": "产品线",
  "drill_concept_id": 12,
  "sql": "SELECT product_line, SUM(return_qty)/SUM(order_qty) as return_rate FROM ... GROUP BY product_line"
}
```

**根因分析模式（融入 final_answer）**

当所有下钻维度耗尽或 LLM 判断已有足够信息时，产出 `next_action = "final_answer"`，格式为 root_cause：

```json
{
  "type": "final_answer",
  "answer_type": "root_cause",
  "reasoning": "经过 3 轮下钻：整体退货率上升 → 产品A飙升 → 华东区集中 → 批次2024-B3问题",
  "root_cause": "批次 2024-B3 在华东区集中出现质量问题，导致产品A退货率从2%飙升到12%",
  "evidence": [
    {"round": 1, "finding": "整体退货率从 3.2% 上升到 5.8%"},
    {"round": 2, "finding": "产品 A 退货率 12%，其他产品正常"},
    {"round": 3, "finding": "华东区退货率 18%，批次 2024-B3 占比 80%"}
  ],
  "suggestion": "建议暂停批次 2024-B3 发货，联合质检部门追溯该批次生产记录"
}
```

**本体管理模式（`ontology_action`）**

当用户提出本体管理需求（如"帮我补充缺失的下钻维度"、"这个表字段映射不对，帮我修正"），或 LLM 在分析过程中发现本体配置缺陷（缺少概念、关系不完整、映射错误），可选择 `ontology_action` 生成本体变更建议：

```
## 本体管理模式（ontology_action）

适用场景：
- 用户明确要求管理本体："帮我加一个概念"、"配置下钻关系"
- 分析过程中发现本体缺失：查询结果无法关联到概念、下钻维度链断裂
- 映射配置错误：SQL 生成后执行失败，发现表/字段映射不匹配

权限要求：仅超级管理员可使用。非超管用户触发时，返回权限不足提示。

响应格式：
{
  "type": "ontology_action",
  "action": "suggest",
  "reasoning": "分析过程中发现'退货率'概念缺少按批次下钻的维度关系，建议补充",
  "trigger": "user_request" | "auto_detect",
  "changes": [
    {
      "operation": "ADD_CONCEPT",
      "concept": {
        "name": "批次合格率",
        "description": "批次产品的质检合格率",
        "industryId": 1,
        "anomalyThresholdExpr": "< 95%",
        "anomalyThresholdDesc": "合格率低于95%判定为异常"
      }
    },
    {
      "operation": "ADD_RELATION",
      "relation": {
        "sourceConceptName": "退货率",
        "targetConceptName": "批次合格率",
        "relationType": "CORRELATED",
        "description": "退货率与批次合格率关联分析"
      }
    },
    {
      "operation": "UPDATE_MAPPING",
      "mapping": {
        "conceptName": "退货率",
        "tableName": "returns",
        "columnName": "return_qty",
        "attributeName": "退货数量",
        "mappingType": "direct",
        "reason": "原映射缺少退货数量字段，导致退货率计算不完整"
      }
    }
  ]
}
```

**支持的操作类型**：

| operation | 说明 | 示例 |
|-----------|------|------|
| ADD_CONCEPT | 新增概念 | 补充缺失的业务概念 |
| UPDATE_CONCEPT | 修改概念（名称、描述、异常阈值） | 修正概念描述或阈值 |
| DELETE_CONCEPT | 删除概念（需确认无依赖） | 移除冗余概念 |
| ADD_RELATION | 新增概念间关系（DRILLS_INTO/CORRELATED） | 补充下钻维度链 |
| DELETE_RELATION | 删除概念间关系 | 移除错误的关系 |
| ADD_MAPPING | 新增概念-表字段映射 | 补充缺失的字段映射 |
| UPDATE_MAPPING | 修改映射（表名、字段名、表达式） | 修正错误的映射 |
| DELETE_MAPPING | 删除映射 | 移除冗余映射 |
| ADD_JOIN_MAPPING | 新增表间 JOIN 关系 | 补充跨表查询关联 |
| UPDATE_JOIN_MAPPING | 修改 JOIN 条件 | 修正 JOIN 条件 |
| DELETE_JOIN_MAPPING | 删除 JOIN 关系 | 移除冗余 JOIN |

**关键约束**：
- 所有变更**不会自动生效**，而是生成建议列表，等待用户在 UI 上审核确认
- 每次最多建议 5 条变更，避免信息过载
- 变更建议必须附带 `reasoning`，说明为什么需要这个变更
- LLM 可以基于分析过程中的"错误经验"（SQL失败、概念缺失）自动触发 `auto_detect` 模式

#### 2.2.4 code_executor 节点设计

新增节点，用于执行 LLM 生成的 Python 代码。与 nl2sql_executor 并列，执行完毕后回到 agent 继续推理。

**复用现有 Python 服务**：

当前已有 Python embedding service（`http://localhost:8765`），提供以下能力：

| 端点 | 用途 | 当前使用者 |
|------|------|-----------|
| `/v1/embeddings` | 文本向量化 | FaissService、ToolEmbeddingService |
| `/v1/faiss/*` | FAISS 向量检索 | FaissService |
| `/v1/parse-file` | 执行 Python 解析代码 | ConceptImportService |

code_executor 复用 Python 服务，新增 `/v1/execute-code` 端点：

**Java 侧调用方式**（参考 ConceptImportService.executePythonCode 模式）：

```java
// CodeExecutorService.java（新增）
public String executeCode(String code, String data) {
    Map<String, Object> body = Map.of(
        "code", code,
        "data", data  // nl2sql 查询结果 JSON
    );
    HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create(pythonServiceUrl + "/v1/execute-code"))
        .header("Content-Type", "application/json")
        .POST(HttpRequest.BodyPublishers.ofString(jsonMapper.writeValueAsString(body)))
        .timeout(Duration.ofSeconds(30))
        .build();
    HttpResponse<String> resp = httpClient.send(request, HttpResponse.BodyHandlers.ofString());
    return resp.body();  // stdout 输出
}
```

**Python 侧新增端点**（`/v1/execute-code`）：

```python
@app.post("/v1/execute-code")
async def execute_code(request: ExecuteCodeRequest):
    # 1. 代码审计：扫描禁止模式
    forbidden = ["os.system", "subprocess", "eval", "exec", "open(", "__import__"]
    for pattern in forbidden:
        if pattern in request.code:
            raise HTTPException(400, f"禁止使用 {pattern}")
    
    # 2. 准备执行环境
    import pandas as pd, numpy as np, json
    data = json.loads(request.data)  # nl2sql 查询结果
    
    # 3. 执行用户代码
    import io, sys
    old_stdout = sys.stdout
    sys.stdout = io.StringIO()
    try:
        exec(request.code, {"pd": pd, "np": np, "data": data, "json": json})
        result = sys.stdout.getvalue()
    finally:
        sys.stdout = old_stdout
    
    return {"success": True, "output": result}
```

**code_executor 执行流程**：

```
1. AgentNode 产出 next_action = "code_mode"，附带 code 和 reasoning
2. Router 路由到 code_executor 节点
3. code_executor 从 AgentState 获取：
   - code: LLM 生成的 Python 代码
   - nl2sql_result: 上一轮 SQL 查询结果（JSON）
4. 调用 Python 服务的 /v1/execute-code
5. 捕获 stdout 输出
6. 将结果写回 AgentState.messages
7. 返回 agent 节点继续推理
```

**安全策略（由 Python 服务负责）**：

| 策略 | 实现 |
|------|------|
| 代码审计 | 执行前扫描禁止模式（os.system、subprocess、eval、exec、open 写入、__import__） |
| 超时控制 | 30 秒超时 |
| 数据隔离 | 只读接收 nl2sql 结果，禁止访问文件系统/网络/数据库 |
| 预装库 | pandas、numpy、scipy、matplotlib（只输出数据，不输出图片） |

**数据结构**：

```java
// AgentState 中注入的数据
state.put("nl2sql_result", lastQueryResult);   // 上一轮 SQL 查询结果（JSON）
state.put("code", llmGeneratedCode);            // LLM 生成的 Python 代码
state.put("code_result", executionOutput);      // Python 执行结果（stdout）
```

**注意**：code_executor 的输入数据来自上一轮 nl2sql 的结果。典型流程是：`nl2sql（查数据）→ code_executor（分析数据）→ agent（解读结果）→ final_answer`。

#### 2.2.5 ontology_advisor 节点设计

新增节点，用于 AI 驱动的本体管理。LLM 生成概念/关系/映射的变更建议，由用户审核确认后执行。

**设计目标**：手动在 UI 上逐条配置概念、关系、映射非常繁琐（6 个场景需要 102 条 Mapping），通过 AI 自动分析现有本体并提出建议，用户只需审核确认即可。

**数据源感知**：

不同行业的本体配置在不同数据源上（如零售电商用 `test_db`，运营商用 `carrier_db`），ontology_advisor 必须能感知数据源结构才能生成正确的映射。

LLM 触发 `ontology_action` 时，AgentNode 自动注入当前上下文中的数据源元信息：

```json
{
  "available_datasources": [
    {
      "id": 1,
      "name": "零售电商库",
      "tables": [
        {"name": "orders", "columns": ["order_id", "product_id", "customer_id", "order_date", "status"]},
        {"name": "returns", "columns": ["return_id", "order_id", "product_id", "return_qty", "return_reason"]}
      ]
    },
    {
      "id": 2,
      "name": "运营商网络库",
      "tables": [
        {"name": "dedicated_lines", "columns": ["line_id", "name", "line_type", "src_station", "dst_station"]},
        {"name": "alarms", "columns": ["alarm_id", "source_type", "source_id", "severity", "alarm_time"]}
      ]
    }
  ]
}
```

**注入方式**：在 `buildAgentNode()` 中，每次调用 LLM 前查询当前用户可访问的数据源列表及其表结构，拼入 System Prompt。LLM 据此判断哪些表属于哪个数据源，生成 ConceptMapping 时自动关联正确的 `datasource_id`。

**用户如何指定数据源**：用户在对话中明确指定即可，例如：
- "数据源用零售电商库" → LLM 匹配 `available_datasources` 中 name 最相近的数据源
- "为运营商网络库配置专线告警本体" → LLM 定位到 `id=2` 的数据源，只读其表结构

**权限控制**：

| 角色 | 权限 |
|------|------|
| 超级管理员 | ✅ 可触发 ontology_action，可审核通过/拒绝变更 |
| 普通用户 | ❌ 触发时返回"权限不足，仅超级管理员可使用本体管理功能" |

权限校验在 **ontology_advisor 节点执行前**进行，后端通过 `SecurityContext` 获取当前用户角色：

```java
// OntologyAdvisorNode.java
public Map<String, Object> execute(AgentState state) {
    User currentUser = SecurityContext.getCurrentUser();
    if (!"SUPER_ADMIN".equals(currentUser.getRole())) {
        state.put("ontology_result", Map.of("error", "权限不足"));
        return Map.of("next_action", "agent");
    }
    // 执行变更建议...
}
```

**执行流程**：

```
1. AgentNode 产出 next_action = "ontology_action"，附带 changes 列表
2. Router 路由到 ontology_advisor 节点
3. ontology_advisor 校验超管权限 → 不通过则返回 agent 并提示
4. 解析 changes 列表，生成变更预览（before/after 对比）
5. 变更建议暂存到 AgentState，推送 SSE 事件到前端
6. 前端展示变更建议 UI（Diff 视图），等待用户确认
7. 用户确认后，前端调用 /api/ontology/apply-changes 接口
8. 后端逐个执行变更（事务包裹），返回结果
9. 结果写回 AgentState，返回 agent 节点
```

**数据结构**：

```java
// AgentState 中注入的数据

state.put("ontology_change_status", "PENDING");           // PENDING / APPROVED / REJECTED

```

**变更执行逻辑**（`OntologyChangeService.java`）：

```java
@Transactional
public List<ChangeResult> applyChanges(List<OntologyChange> changes) {
    List<ChangeResult> results = new ArrayList<>();
    for (OntologyChange change : changes) {
        switch (change.getOperation()) {
            case ADD_CONCEPT:
                Concept concept = conceptRepository.save(change.toConcept());
                results.add(ChangeResult.success(change.getId(), concept.getId()));
                break;
            case ADD_RELATION:
                ConceptRelation relation = relationRepository.save(change.toRelation());
                results.add(ChangeResult.success(change.getId(), relation.getId()));
                break;
            case UPDATE_MAPPING:
                ConceptMapping mapping = mappingRepository.findById(change.getMappingId())
                    .orElseThrow();
                change.applyTo(mapping);
                mappingRepository.save(mapping);
                results.add(ChangeResult.success(change.getId(), mapping.getId()));
                break;
            // ... 其他操作类型
        }
    }
    return results;
}
```

**关键约束**：
- 变更建议**不会自动生效**，必须用户在前端确认
- 变更执行使用**数据库事务**，全部成功或全部回滚
- 删除操作需检查依赖：删除概念前检查是否有关系引用，有则提示
- 变更历史记录到 `ontology_change_log` 表，支持审计追溯

**删除操作依赖检查规则**：

| 操作 | 需检查的依赖 |

**`available_datasources` 注入时机与格式转换**：

注入位置：在 `buildUnifiedContext` 中，FAISS 概念检索完成后、LLM 调用前。`DatasourceService.getStructure(datasourceId)` 返回原始表结构（包含 `name`、`type`、`nullable`、`primaryKey`），需转换为精简格式：

```java
// DatasourceService 新增方法
public List<DatasourceMeta> getAvailableDatasources(List<Long> datasourceIds) {
    return datasourceIds.stream().map(id -> {
        Datasource ds = datasourceRepository.findById(id).orElseThrow();
        List<TableMeta> tables = ds.getTables().stream().map(table -> {
            List<String> columns = table.getColumns().stream()
                .map(ColumnMeta::getName)
                .collect(Collectors.toList());
            return new TableMeta(table.getName(), columns);
        }).collect(Collectors.toList());
        return new DatasourceMeta(ds.getId(), ds.getName(), tables);
    }).collect(Collectors.toList());
}
```

转换后在 `buildUnifiedContext` 中拼入 System Prompt 的 `available_datasources` 字段。

**多数据源场景下自动推断**：

如果用户未显式指定数据源（如"帮我分析退货率"），LLM 需根据以下规则自动选择：
1. 根据 FAISS 匹配的概念的 `ConceptMapping.datasourceId` 反查关联的数据源
2. 如果多个数据源都有相关概念，优先使用最近配置的数据源
3. 在 System Prompt 中增加规则："如果用户未指定数据源，默认使用当前上下文已关联的数据源"

**`code_mode` 降级逻辑**：

在 `buildAgentNode` 中，每次调用 LLM 前检测 Python 服务健康状态（`GET /v1/health`）：
- 服务可用：System Prompt 中包含 `code_mode` 说明，LLM 可选择使用
- 服务不可用：System Prompt 中移除 `code_mode` 说明，LLM 自动回退到 `nl2sql` 进行数据分析
- 健康检查超时（3s）：视为不可用，记录 WARN 日志

#### 场景 1：退货率异常

**问题**："上个月退货率为什么涨了？"

**预设根因**：产品线 A 在华东区的批次 B3 出现质量问题，导致该批次退货率从 2% 飙升到 12%。

**期望下钻路径**：整体退货率 → 按产品线下钻 → 按地区下钻 → 按批次下钻

| 要素 | 内容 |
|------|------|
| **概念本体** | 退货率（根概念）、产品线、地区、客户、批次、订单 |
| **维度关系** | 退货率 DRILLS_INTO 产品线，产品线 DRILLS_INTO 地区，地区 DRILLS_INTO 批次 |
| **关联关系** | 退货率 CORRELATED 客户投诉率（交叉验证） |
| **异常阈值** | 退货率 anomaly_threshold_expr: `> 5%` |
| **数据库表** | `orders`（订单ID、产品线ID、地区ID、批次ID、客户ID、订单日期、状态）`returns`（退货ID、订单ID、退货日期、退货原因、退货数量） |

#### 场景 2：产能下降

| 要素 | 内容 |

| **维度关系** | 产能 DRILLS_INTO 产品线，产品线 DRILLS_INTO 工单，工单 DRILLS_INTO 设备 |
| **关联关系** | 产能 CORRELATED 设备故障率 |

#### 场景 6：跨省专线故障定位（运营商）

**问题**："北京到上海的OTN专线业务中断了，是什么原因？"

**预设根因**：济南-徐州段光缆在济南站收光功率过低（-28dBm，正常值 -15~-20dBm），导致该段OTN传输中断，进而引发上层IP VPN业务告警。

**网络层次关系**：
```
IP层 (Layer 3)    → VPN专线: 北京-上海 IP VPN (承载于 OTN)
    ↓ 承载于
传输层 (Layer 2)  → OTN专线: 北京-上海 OTN (承载于 光缆)
    ↓ 承载于
光缆层 (Layer 1)  → 光缆段: 北京→济南→徐州→南京→上海
```

**告警传播链**：光缆层收光功率过低 → 传输层OTN信号丢失 → IP层BGP邻居Down，层层上报

### 3.2 验收标准

| 指标 | 目标 | 测量方法 |
|------|------|---------|
| 下钻准确率 | ≥ 80% | 5 个场景中 4 个能在 3 轮内定位正确根因 |
| 平均下钻轮数 | ≤ 3 轮 | 统计每个场景的下钻轮数 |
| 维度选择合理性 | 与人预设路径一致 | 人工评估 |
| 根因可解释性 | 证据链清晰，无幻觉 | 人工评估 |
| 降级表现 | 无法下钻时给出合理单轮分析 | 不产生错误结论 |

### 3.3 验证方法

**A. 本体配置验证（ontology_advisor）**

1. 在测试数据库中准备好 5 个场景的数据
2. 超管用户通过对话与 LLM 交互，例如："帮我配置零售电商行业的自动洞察本体，包含退货率、产能、客诉率、库存、成本五个概念"
3. LLM 自动分析表结构，生成概念、映射、JOIN 关系、维度关系建议
4. 前端展示变更建议 Diff 卡片，超管逐条审核 Approve/Reject
5. 验证指标：
   - 概念覆盖率：自动生成的配置是否覆盖所有场景的概念（零售电商 5 场景 28 个概念 + 运营商 1 场景 11 个概念，共 39 个）
   - 映射准确率：ConceptMapping 的 table_name/column_name 是否正确
   - JOIN 关系完整性：ConceptJoinMapping 是否覆盖所有跨表查询
   - 下钻维度链完整性：ConceptRelation 的 DRILLS_INTO 链是否闭合

**B. 下钻分析验证**

1. 本体配置完成后，用自动化脚本逐一提问 5 个场景的问题
2. 记录每轮 SQL、结果、LLM 选择的下钻维度和最终根因结论
3. 人工对比预设根因，评估准确率
4. 统计：下钻准确率、平均轮数、幻觉率

## 四、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| LLM 下钻维度选择不合理 | 下钻到无关维度，浪费轮数 | Prompt 中明确维度优先级，每轮只下钻一个维度 |
| 下钻轮数过多 | 响应太慢，用户体验差 | 最大 3 轮限制，超时强制输出中间结论 |
| 数据不足导致无法下钻 | LLM 强行编造结论 | 数据不足时明确告知用户，不编造 |
| 维度关系配置错误 | 下钻路径错误，根因结论偏 | 提供维度关系测试工具，上线前人工审核 |
| 异常阈值不准确 | 漏报或误报 | 阈值可配置，支持业务方自行调整 |
| Python 服务不可用 | code_mode 降级 | `buildAgentNode` 每次调用前检查 `GET /v1/health`（3s 超时），不可用时从 System Prompt 中移除 `code_mode` 说明，LLM 自动回退到 nl2sql |
| 恶意代码注入 | 安全风险 | Python 服务端代码审计 + 禁止模式扫描 + 30s 超时 |
| 本体变更误操作 | AI 建议的错误配置被误通过 | 变更前展示 Diff 对比，超管逐条审核，支持回滚 |
| 非超管越权 | 普通用户触发本体管理 | 后端 ontology_advisor 节点强制校验角色，非超管直接拒绝 |
| 本体变更冲突 | 多人同时修改本体 | 变更建议暂存 session 级别，执行时乐观锁检查版本号 |
