## 四-二、Plan 模型扩展

每个 Agent 的 Plan 独立存储，Plan tab 同时展示所有 Agent 的当前计划。
支持 **父子 Plan 嵌套**：主智能体的某个步骤可以展开查看子智能体的 Plan。

```typescript
// types/agent.ts 扩展
interface Plan {
  id: string;
  agentId: string;         // 新增：所属 Agent ID
  agentName: string;       // 新增：所属 Agent 显示名
  agentIcon: string;       // 新增：所属 Agent 图标
  steps: Step[];
  createdAt: number;
  status: 'draft' | 'pending' | 'confirmed' | 'executing' | 'completed' | 'rejected' | 'stopped';
  // 子 Plan 关联
  parentPlanId?: string;   // 新增：父 Plan ID（子 Plan 指向父）
  parentStepId?: string;   // 新增：父 Step ID（子 Plan 指向父 Plan 的哪个步骤）
}

interface Step {
  id: string;
  description: string;
  status: StepStatus;       // 'pending' | 'running' | 'done' | 'error'
  toolName?: string;
  result?: string;
  order: number;
  // 子 Plan 展开
  subPlanId?: string;       // 新增：关联的子 Plan ID（该步骤触发的子 Agent Plan）
}
```

**父子 Plan 关联规则**：
```
主智能体 Plan 的 Step B（如"协调数据辅助智能体获取查询"）→ 展开 → 数据辅助智能体的 Plan
  Step.subPlanId = dataAssistantPlan.id
  dataAssistantPlan.parentPlanId = mainPlan.id
  dataAssistantPlan.parentStepId = StepB.id

关联时机：
  主智能体在执行 Step B 期间，通过 @数据辅助智能体 触发子 Agent
  → 系统记录当前执行的 Step ID（Step B）
  → 数据辅助智能体创建 Plan 时，自动关联到 Step B

Plan tab 中，主智能体的 Step B 显示为可展开项（▶ 图标）
展开后嵌套显示数据辅助智能体的完整 Plan（步骤 + 状态）
```

**Plan 生命周期规则**：
```
每个 Agent 同一时刻最多有一个 "活跃" Plan（非 rejected/stopped）。
当 Agent 创建新 Plan 时，该 Agent 的旧 Plan 自动标记为 completed。
子 Plan 的生命周期独立于父 Plan：父 Plan 结束不影响子 Plan 的展示。
Plan tab 展示所有 Agent 的当前 Plan（最新一个非 rejected 的）。

Plan 状态迁移：
  draft → (用户确认) → confirmed → executing → completed
    ↓                     ↓            ↓
  rejected              stopped      stopped
                                        ↓
                                (用户补充描述) → 重新 planning → 新 Plan
```

**Store 变更**：
```
plans: Plan[] 中可能包含多个 Agent 的 Plan，每个 Agent 最新一个。
currentPlanId 不再单一，改为按 agentId 索引。
Plan tab 渲染时遍历 plans 数组，按 agentId 分组展示。
子 Plan 不单独渲染为顶层卡片，而是嵌入父 Plan 对应步骤的展开区域。
仅当子 Plan 的父 Plan 仍存在于列表中时，子 Plan 才嵌入展示。
```

## 四-三、Plan 注意力机制（LLM 驱动）

用户可能中途转移注意力开始新话题，之后再回来继续原计划。
**由大模型来判断用户当前消息属于哪个 Plan**，而不是前端做关键词匹配。

Plan 不再需要 `paused` 状态——`focusPlanId` 即表示当前注意力所在。
所有 `executing` 的 Plan 都是"未完成"，LLM 自行决定继续哪个。

### 核心思路

```
将所有未完成的 Plan 作为上下文发给大模型
大模型在规划阶段自行判断：
  1. 继续某个已有 Plan → 生成延续该 Plan 的步骤
  2. 创建新 Plan → focusPlanId 切换到新 Plan
  3. 不使用 Plan → 简单问答，直接回复

前端只负责：
  - 收集未完成 Plan 并格式化
  - 注入到 system prompt 中
  - 根据大模型的行为更新 focusPlanId
```

### Plan 状态（简化）

```typescript
interface Plan {
  id: string;
  agentId: string;
  agentName: string;
  agentIcon: string;
  steps: Step[];
  createdAt: number;
  status: 'draft' | 'pending' | 'confirmed' | 'executing' | 'completed' | 'rejected' | 'stopped';
  // 不再需要 paused 状态——focusPlanId 替代
  parentPlanId?: string;
  parentStepId?: string;
}
```

**`focusPlanId` 替代 `paused` 状态**：
- `focusPlanId === plan.id` → 用户正在关注这个 Plan（Plan tab 中蓝色高亮）
- `focusPlanId !== plan.id && status === 'executing'` → 用户暂时没关注，但 Plan 未完成（Plan tab 中灰色调）
- `status === 'completed'` → 已完成

### System Prompt 注入

发送用户消息前，将所有 `executing` 的 Plan 注入到 system prompt 中：

```
## 未完成的计划

以下是当前所有未完成的计划，请根据用户消息判断应该继续哪个计划：

### Plan: 用户管理页面 (当前焦点)
- Agent: 主智能体
- 步骤:
  1. ✅ 分析用户需求，制定方案
  2. ⬜ 协调数据辅助智能体获取查询
  3. ⬜ 创建用户管理页面
  4. ⬜ 绑定查询到页面组件

### Plan: 订单报表页面
- Agent: 主智能体
- 步骤:
  1. ✅ 分析订单报表需求
  2. ⏳ 创建订单统计页面

## 决策规则

收到用户消息后，你必须判断：
1. 如果用户消息与某个未完成计划的目标相关 → 继续该计划，在计划描述中写明"继续「计划名称」"
2. 如果用户消息是全新需求，与所有未完成计划都不相关 → 创建新计划（系统自动切换焦点）
3. 如果用户消息是简单问答、闲聊、或不需要多步骤执行的指令 → 直接回复，不使用计划
```

**注入时机**：在 `AgentFactory.createAgent()` 构建 system prompt 时，动态拼接所有 `executing` 的 Plan 列表。

### 注意力判断流程（LLM 驱动）

```
用户发送消息
  │
  ├─ 用户显式指定？"继续用户管理" / "切到订单页面"
  │   → 前端精确匹配 Plan 名称，切换 focusPlanId（不消耗 LLM Token）
  │   → 匹配成功 → focusPlanId 切换到该 Plan
  │   → 匹配失败 → 提示用户选择
  │
  └─ 无显式指令 → 调用 Agent（system prompt 包含所有 executing Plan）
      │
      └─ 大模型 Planning 阶段自行判断
          ├─ plan.created + "继续「XXX」" → 合并到已有 Plan
          │
          ├─ plan.created + 全新 Plan → focusPlanId 切换到新 Plan
          │
          └─ 无 plan.created（直接回复文本）→ 不影响任何 Plan
```

### Plan 创建时的自动关联

LLM 创建新 Plan 时，eventAdapter 通过"继续「XXX」"模式判断是否合并：

```
if (plan.created 的步骤描述包含 "继续「XXX」") {
  找到名称匹配的已有 Plan → 复用 Plan ID，追加步骤
} else {
  创建新 Plan，focusPlanId 切换到新 Plan
}
```

### Plan 切换方式

| 方式 | 触发 | 行为 |
|---|---|---|
| **显式切换** | 用户输入"继续XXX"、"切到XXX" | 前端精确匹配，切换 focusPlanId，不消耗 LLM |
| **Plan tab 点击** | 点击进行中 Plan 的"聚焦"按钮 | 前端切换 focusPlanId，不消耗 LLM |
| **LLM 判断** | 用户自然发消息，无显式指令 | LLM 根据 system prompt 自行决定继续或新建 |
| **@Agent 触发** | 用户 @某个 Agent | 该 Agent 的 executing Plan 注入到 system prompt |

## 五、聊天路由逻辑

ChatRouter 是消息分发的核心，处理两种触发路径：

### 路径一：用户主动 @提及（直接路由）

```
用户输入 "@数据辅助智能体 帮我看看有哪些数据源"
  → 前端解析 @mentions → ['数据辅助智能体']
  → ChatRouter 查找 agentRegistry → 匹配到 data-assistant
  → 创建 DBA AgentRuntime，直接运行
  → 消息存储: { agentId: 'data-assistant', targetAgent: 'data-assistant' }
```

```
用户输入 "帮我做用户管理页面"（无 @）
  → 无 @ → 发给默认 agent (main-agent)
  → 消息存储: { agentId: null, targetAgent: 'main-agent' }
```

### 路径二：主智能体 find_query 工具调用（间接路由）

```
用户输入 "帮我做用户管理页面"
  → ChatRouter 路由到 main-agent
  → 主智能体 LLM 判断需要数据 → 调用 find_query 工具
  → find_query.execute() 内部：
      1. 构建 DBA system prompt
      2. 调用 ChatRouter.routeTo('data-assistant', dbaPrompt)
      3. ChatRouter 创建 DBA AgentRuntime
      4. DBA 创建查询 → 调试 → 返回结果
      5. find_query 返回结构化结果给主智能体
```

### 路径三：用户主动 @ + 主智能体被动触发（混合）

```
用户输入 "@数据辅助智能体 用户管理页面需要查询什么"
  → ChatRouter 直接路由到 DBA
  → DBA 回答后，如需主智能体配合：
    输出 "@主智能体 查询已就绪，可以创建页面了"
  → ChatRouter 解析 @ → 自动切回 main-agent
```

### 路由状态机

```
                    ┌──────────────┐
         用户发消息(无@)   │  用户发消息(@DBA)  │  find_query 工具调用
         ┌──────────────┼──────────────┐
         ▼              │              ▼
  ┌───────────────┐     │     ┌───────────────┐
  │  MAIN_AGENT   │     │     │ DATA_ASSISTANT │
  └───────┬───────┘     │     └───────┬───────┘
          │ 消息含      │             │ 消息含
          │ @DBA        │             │ @主智能体
          ▼             │             ▼
  ┌───────────────┐     │     ┌───────────────┐
  │ DATA_ASSISTANT│─────┘     │  MAIN_AGENT   │  ← 循环
  └───────────────┘           └───────────────┘
```

### ChatRouter 核心逻辑

```typescript
class ChatRouter {
  private agentRegistry: Map<string, AgentDefinition>;
  private sharedMessages: Message[]; // 共享聊天记录

  async route(userInput: string, mentions?: string[]): Promise<RouteResult> {
    // 1. 用户主动 @ 某智能体
    if (mentions?.length) {
      const targetAgent = this.agentRegistry.get(mentions[0]);
      return this.executeAgent(targetAgent, userInput);
    }

    // 2. 默认 → 主智能体
    return this.executeAgent(this.agentRegistry.get('main-agent'), userInput);
  }

  // find_query 工具内部调用此方法
  async routeTo(agentId: string, systemPrompt: string, task: string): Promise<QueryResult> {
    const agent = this.agentRegistry.get(agentId);
    const runtime = this.createRuntime(agent, systemPrompt);
    return await runtime.run(task);
  }
}
```

## 六、记忆隔离与 LLM 请求拼接

每个 Agent 拥有独立的 `AgentRuntime` 实例：

```typescript
class AgentRuntime {
  private agentId: string;
  private privateMessages: Message[] = [];  // 私有记忆：system prompt + 工具调用结果
  private systemPrompt: string;
  private tools: ToolDefinition[];

  // 构建 LLM 请求的消息列表
  buildMessages(sharedMessages: Message[]): Message[] {
    return [

        m.role === 'user' ||                            // 所有用户消息
        (m.role === 'assistant' && !m.toolCalls)        // agent 公开文本（不含工具调用）
      ),
    ];
  }
}

## 七-附一、触发机制：find_query 工具

主智能体通过 `find_query` **工具调用**触发 DBA。ChatRouter 负责实际的路由分发——`find_query` 工具内部调用 `ChatRouter.routeTo('data-assistant', ...)` 来创建 DBA AgentRuntime。主智能体自身不持有 `create_query`/`run_query` 等工具，`find_query` 是访问 DBA 的**唯一入口**。

### 与 ChatRouter 的关系

```
用户输入 → ChatRouter.route() → main-agent 运行
                                  ↓
                            main-agent LLM 调用 find_query 工具
                                  ↓
                            find_query.execute() 内部:
                              ChatRouter.routeTo('data-assistant') → DBA 运行
                                  ↓
                            find_query 返回结构化结果 → main-agent 继续
```

- **用户主动 @DBA**：ChatRouter 直接解析 @mentions，路由到 DBA（路径一）
- **主智能体调用 find_query**：ChatRouter 通过 routeTo() 间接创建 DBA（路径二）
- 两种路径最终都通过 ChatRouter 统一管理 AgentRuntime 生命周期

### 为什么用工具而非文本 @

| | 文本 @ | find_query 工具 |
|---|---|---|
| 触发方式 | LLM 输出 "@数据辅助智能体" | LLM 调用 function call |
| 参数传递 | 自然语言，可能遗漏 | 结构化 JSON，必填校验 |
| 返回结果 | 自然语言，需解析 | 结构化查询列表 |
| 可靠性 | 依赖 LLM 记住格式 | 工具定义保证格式 |
| 可测试性 | 难以测试 | 可以 mock 工具 |

### 完整流程

```
用户: "帮我做一个用户管理页面"
  ↓
主智能体 LLM:
  → 分析需求：需要用户列表、搜索、筛选
  → 调用 find_query({
      task_type: "B单页面",
      target_page: "用户管理页面",
      requirements: [
        "全量用户列表，支持分页",
        "按姓名模糊搜索",
        "按状态（启用/禁用）筛选"
      ]
    })
  ↓
find_query 工具 execute():
  1. dispatch({ type: 'FIND_QUERY_START' })  → UI 显示 DBA 正在工作
  2. 构建 DBA system prompt（含当前应用 ID、需求描述）
  3. 创建 DBA AgentRuntime，调用 run()
  4. DBA: 查看数据源 → 获取表结构 → 创建查询 → 调试
  5. 等待 DBA 完毕，收集结果
  6. dispatch({ type: 'FIND_QUERY_COMPLETE' })
  ↓
find_query 返回给主智能体 LLM:
  {
    success: true,
    message: "数据辅助智能体已创建 3 个查询",
    queries: [
      { id: 5, name: "ListUsers", description: "全量用户列表" },

  ↓

```

## 七-附二、Query 作用域：从页面级改为应用级

### 现状

Query 通过 `pageId` 绑定到页面，属于**页面级**作用域。每个 Query 只对创建它的页面可见。

```
Query.pageId → Page.id → Page.applicationId
```

### 问题

页面级作用域在多智能体场景下造成不必要的复杂度：

- DBA 创建 Query 时需要知道"为哪个页面建"，但 DBA 不关心页面
- 多页面应用共享同一个查询（如"用户列表页"和"用户详情页"都需要 GetUser）时，必须创建两次
- `list_queries` 需要传 `pageId`，DBA 需要额外维护页面上下文

### 方案

改为**应用级**作用域。Query 属于应用，通过 `CodePage.queryIds` 绑定到页面。

```
Query.applicationId → Application.id
CodePage.queryIds → [Query.id, ...]  // 页面引用哪些 Query
```

**对 DBA 的影响**：
- `create_query` 不再需要 `pageId`，改为 `applicationId`
- `list_queries` 按 `applicationId` 查询，返回应用下所有 Query
- DBA 只需关注：应用内有哪些 Query、是否需要新建/修改/删除

**对主智能体的影响**：
- `list_queries` 返回应用全局 Query 列表，主智能体可以跨页面引用
- 创建页面时绑定的 `queryIds` 是引用关系，Query 本身是全局的

### 数据库变更

```sql
-- MySQL / PostgreSQL 通用

-- 1. 添加 application_id 列（先允许 NULL）
ALTER TABLE queries ADD COLUMN application_id BIGINT;

-- 2. 从 pages 表回填 application_id
UPDATE queries q
JOIN pages p ON q.page_id = p.id
SET q.application_id = p.application_id;

-- 3. 设置 NOT NULL 约束
ALTER TABLE queries MODIFY COLUMN application_id BIGINT NOT NULL;

-- 4. 删除旧的 page_id 列
ALTER TABLE queries DROP COLUMN page_id;
```

### 代码变更清单

| 层 | 文件 | 变更 |
|---|---|---|
| 实体 | `entity/Query.java` | `pageId` → `applicationId`，列名 `application_id` |
| 仓库 | `repository/QueryRepository.java` | `findByPageId` → `findByApplicationId`，删除 `deleteByPageId` |
| DTO | `dto/CreateQueryRequest.java` | `pageId` → `applicationId` |

| 前端 API | `api/query.ts` | `listQueries(pageId)` → `listQueries(applicationId)` |

## 十二、Plan Tab 实现细节

### 数据流

```
@dudko.dev/agent-web 事件
  → eventAdapter.ts (根据 event.type 分发)
    → plan.created: 
        addPlan({ agentId, agentName, agentIcon, parentPlanId, parentStepId, steps })
        + 如果 parentStepId 存在，updateStep(parentPlanId, parentStepId, { subPlanId })
    → step.start: updateStep(planId, stepId, { status: 'running' })
    → step.complete: updateStep(planId, stepId, { status: 'done', result })
    → step.tool-result(!ok): updateStep(planId, stepId, { status: 'error' })
  → agentStore (zustand)
    → plans: Plan[] 更新（含父子关联）
  → AgentPanel Plan tab 自动重渲染
```

### 父子 Plan 关联机制

```typescript
// eventAdapter.ts 中维护的上下文
let currentStepContext: { planId: string; stepId: string } | null = null;

// step.start 时记录当前步骤
case 'step.start':
  currentStepContext = { planId: currentPlanId, stepId: event.step.id };
  break;

// 检测到 @提及触发子 Agent 时，步骤上下文自动传递
// 子 Agent 的 plan.created 事件中携带 parentPlanId + parentStepId

// plan.created 时建立关联
case 'plan.created':
  const plan = { ...event.plan, agentId, agentName, agentIcon };
  if (currentStepContext) {
    plan.parentPlanId = currentStepContext.planId;
    plan.parentStepId = currentStepContext.stepId;
    // 更新父步骤的 subPlanId
    updateStep(currentStepContext.planId, currentStepContext.stepId, { subPlanId: plan.id });
  }
  addPlan(plan);
  break;
```

### Store 逻辑

```typescript
// stores/agentStore.ts
addPlan: (plan: Plan) => {
  set((state) => {
    // 移除同一 Agent 的旧 Plan
    const filtered = state.plans.filter((p) => p.agentId !== plan.agentId);
    return { plans: [...filtered, plan] };
  });
},

updateStep: (planId: string, stepId: string, updates: Partial<Step>) => {
  set((state) => ({
    plans: state.plans.map((p) =>
      p.id === planId
        ? {
            ...p,
            steps: p.steps.map((s) =>
              s.id === stepId ? { ...s, ...updates } : s,
            ),
          }
        : p,
    ),
  }));
},
```

// PlanCard 组件
function PlanCard({ plan, allPlans }: { plan: Plan; allPlans: Plan[] }) {
  const [collapsed, setCollapsed] = useState(false);
  const [expandedSteps, setExpandedSteps] = useState<Set<string>>(new Set());

  const toggleStep = (stepId: string) => {
    setExpandedSteps(prev => {
      const next = new Set(prev);
      prev.has(stepId) ? next.delete(stepId) : next.add(stepId);
      return next;
    });
  };

  return (
    <div className={`ap-plan-card ${plan.status}`}>
      <div className="ap-plan-card-header" onClick={() => setCollapsed(!collapsed)}>
        <span>{plan.agentIcon} {plan.agentName}</span>
        <span className="ap-plan-card-status">
          {plan.status === 'executing' ? '进行中' : plan.status === 'completed' ? '已完成' : plan.status}
        </span>
      </div>
      {!collapsed && (
        <div className="ap-plan-steps">
          {plan.steps.map((step) => {
            const subPlan = step.subPlanId
              ? allPlans.find(p => p.id === step.subPlanId)
              : null;
            const isExpanded = expandedSteps.has(step.id);

            return (
              <div key={step.id}>
                <div className={`ap-plan-step ${step.status}`}>
                  <span className="ap-plan-step-icon">
                    {step.status === 'done' ? '✅' : step.status === 'running' ? '⏳' : step.status === 'error' ? '❌' : '⬜'}
                  </span>
                  <span className="ap-plan-step-desc">{step.description}</span>
                  {subPlan && (
                    <button className="ap-plan-step-expand" onClick={() => toggleStep(step.id)}>
                      {isExpanded ? '▼' : '▶'}
                    </button>
                  )}
                </div>
                {subPlan && isExpanded && (
                  <div className="ap-plan-sub-plan">
                    <div className="ap-plan-sub-header">
                      {subPlan.agentIcon} 子计划：{subPlan.agentName}

                      </div>
                    ))}
                  </div>

            );

}

## 十二-附、库 Plan 与自定义 Plan 的关系

`@dudko.dev/agent-web` 库内置了 Planner，每次 `agent.run()` 都会走 `plan → execute → replan → synthesize` 循环。
而我们又设计了自定义 Plan 模型（持久化、多 Agent、注意力机制）。两者的关系需要明确。

### 核心区别

| | 库内置 Plan | 自定义 Plan |
|---|---|---|
| 生命周期 | 单次 `agent.run()` 调用内 | 跨多次 `agent.run()` 调用 |
| 持久化 | 不持久化，调用结束即消失 | 持久化到 zustand/locallStorage |
| 多 Agent | 无关，每个 Agent 独立 | 跨 Agent 关联（父子 Plan） |
| 状态 | 只有 running/completed | pending/confirmed/executing/completed/rejected |
| 注意力 | 不涉及 | 支持暂停/恢复/切换 |

**一句话**：库 Plan 是"单次执行单元"，自定义 Plan 是"跨会话项目单元"。

### 交互流程

```
┌─ 一次 agent.run() 调用 ──────────────────────────────────────┐
│                                                               │
│  1. 用户消息 + system prompt（含未完成 Plan）                   │
│     ↓                                                         │
│  2. 库 Planner 生成库 Plan（plan.created 事件）                 │
│     ↓                                                         │
│  3. eventAdapter 拦截 plan.created                            │
│     ├─ 检测 "继续「XXX」" → 合并到已有自定义 Plan               │
│     └─ 否则 → 创建新自定义 Plan，旧 Plan 暂停                   │
│     ↓                                                         │
│  4. 库执行步骤（step.start/complete 事件）                      │
│     ↓                                                         │
│  5. eventAdapter 拦截 step.* → 更新自定义 Plan 的步骤状态       │
│     ↓                                                         │
│  6. 库输出 final（final 事件）                                  │
│     ↓                                                         │
│  7. eventAdapter 拦截 final → 自定义 Plan 标记 completed        │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

### 关键桥接点

```
库事件                        自定义 Plan 操作
─────────────────────────────────────────────────
plan.created        ──────→   addPlan / updatePlan（合并步骤）
step.start          ──────→   updateStep(status: 'running')
step.complete       ──────→   updateStep(status: 'done', result)
step.tool-result(!ok) ────→   updateStep(status: 'error')
replan              ──────→   updatePlan（追加新步骤）
final               ──────→   updatePlan(status: 'completed')
error               ──────→   updatePlan(status: 'error')
```

### 一次"继续"的完整时序

```
初始状态：
  自定义 Plan: 用户管理页面 (status: executing, 非当前焦点)
    步骤: ✅ 分析需求, ⬜ 创建页面
  focusPlanId: null（或指向其他 Plan）

用户: "继续用户管理页面"
  ↓
前端显式切换 → focusPlanId 切换到该 Plan
  ↓
agent.run("继续用户管理页面", systemPrompt 包含所有 executing Plan)
  ↓
库 Planner 看到 system prompt 中的未完成 Plan
  ↓
库 plan.created → 步骤: ["继续「用户管理页面」", "创建用户管理页面"]
  ↓
eventAdapter 检测到 "继续「用户管理页面」"
  ↓
找到已有的自定义 Plan，合并步骤:
  自定义 Plan:
    ✅ 分析需求
    ⬜ 创建用户管理页面  ← 从库 Plan 合并
  ↓
库 step.start("创建用户管理页面") → step.complete(...)
  ↓
eventAdapter → updateStep → ✅ 创建用户管理页面
  ↓
库 final → eventAdapter → 自定义 Plan: completed
```

### 为什么库 Plan 不能直接替代自定义 Plan

1. **库 Plan 不持久化**：`agent.run()` 结束，库 Plan 就没了。下次打开页面，用户看不到之前的计划。
2. **库 Plan 无多 Agent 概念**：父子 Plan 关联（主智能体的步骤展开看 DBA 的 Plan）是自定义 Plan 的功能。
3. **库 Plan 无焦点概念**：注意力切换需要 `focusPlanId` 区分"当前关注"和"进行中"，库 Plan 只支持 running/completed。
4. **库 Plan 无跨 Agent 关联**：自定义 Plan 的 `agentId`/`agentName`/`agentIcon` 让 Plan tab 能按 Agent 分组展示。

**所以自定义 Plan 是库 Plan 的"持久化包装层"**，eventAdapter 是这个包装层的转换器。库 Plan 负责"这一轮做什么"，自定义 Plan 负责"整个项目做了什么、做到哪了"。

## 十二-附二、Plan 工具定义（暴露给 LLM）

库 Plan 与自定义 Plan 的桥接，除了 system prompt 告知上下文，还需要**工具让 LLM 精准操控**。
用户需求明确或变更时，LLM 应能调整 Plan 的生命周期和步骤内容。

### 工具清单

| 工具 | 作用 | 触发场景 |
|---|---|---|
| `list_unfinished_plans` | 查询所有 executing Plan | LLM 需要了解有哪些 Plan 可以继续 |
| `set_focus_plan` | 切换焦点 Plan | 用户说"先不管这个"、"先做XXX" |
| `adjust_plan` | 调整 Plan 步骤 | 用户澄清需求、变更需求、补充细节 |

**不需要 `create_plan` / `pause_plan` / `resume_plan` 工具**：
- `create_plan`：库 Planner 的 `plan.created` 事件已覆盖，避免双源冲突
- `pause_plan` / `resume_plan`：不需要，`focusPlanId` 切换即表达"暂停当前/恢复目标"，Plan 状态始终是 `executing`

import { z } from 'zod';

export const planTools = [
  {
    name: 'list_unfinished_plans',
    description: '查询所有进行中的计划（executing），用于了解当前有哪些任务在进行中',
    parameters: z.object({}), // 无参数

      const plans = ctx.getUnfinishedPlans();

        id: p.id,
        agentName: p.agentName,

        completedSteps: p.steps.filter(s => s.status === 'done').length,
        steps: p.steps.map(s => `[${s.status}] ${s.description}`).join('\n'),
      }));
    },
  },
  {
    name: 'set_focus_plan',
    description: '切换用户当前关注的计划。用户说"先做XXX"、"换一个"时调用，将注意力转移到指定计划',
    parameters: z.object({
      plan_id: z.string().describe('要切换到的计划 ID，传入 null 表示取消焦点'),
    }),
    execute: async (args, ctx) => {
      ctx.setFocusPlan(args.plan_id);
      return { success: true, message: `焦点已切换${args.plan_id ? '' : '，当前无焦点计划'}` };
    },
  },
  {
    name: 'adjust_plan',
    description: `调整计划的步骤内容。用于以下场景：
- 用户澄清需求：原步骤描述不够准确，需要细化
- 用户变更需求：需要增加/删除/修改步骤
- 用户补充细节：在某步骤上追加子步骤或约束条件
调用后库 Planner 会基于调整后的步骤重新规划执行`,
    parameters: z.object({
      plan_id: z.string().describe('要调整的计划 ID'),
      operations: z.array(z.object({
        action: z.enum(['add', 'remove', 'modify', 'reorder']),
        step_id: z.string().optional().describe('要操作的步骤 ID（remove/modify/reorder 时必填）'),
        description: z.string().optional().describe('新步骤描述（add/modify 时必填）'),
        position: z.number().optional().describe('插入位置（add 时可选，默认末尾；reorder 时必填）'),
      })).describe('调整操作列表，按顺序执行'),
    }),
    execute: async (args, ctx) => {
      const plan = ctx.getPlan(args.plan_id);
      if (!plan) return { success: false, message: '计划不存在' };

      let steps = [...plan.steps];
      for (const op of args.operations) {
        switch (op.action) {
          case 'add':
            steps.splice(op.position ?? steps.length, 0, {
              id: crypto.randomUUID(),
              description: op.description!,
              status: 'pending' as const,
              order: steps.length,
            });
            break;
          case 'remove':
            steps = steps.filter(s => s.id !== op.step_id);
            break;
          case 'modify':
            steps = steps.map(s =>
              s.id === op.step_id ? { ...s, description: op.description! } : s
            );
            break;
          case 'reorder':
            const idx = steps.findIndex(s => s.id === op.step_id);
            if (idx !== -1 && op.position !== undefined) {
              const [item] = steps.splice(idx, 1);
              steps.splice(op.position, 0, item);
            }
            break;
        }
      }
      steps = steps.map((s, i) => ({ ...s, order: i }));
      ctx.updatePlan(args.plan_id, { steps });
      return {
        success: true,
        message: `计划已调整，当前共 ${steps.length} 个步骤`,
        steps: steps.map((s, i) => `${i + 1}. [${s.status}] ${s.description}`).join('\n'),
      };
    },
  },
];
```

// agent/core/planContext.ts

/**
 * 获取所有 executing Plan 并格式化为 system prompt 片段
 * focusPlanId 用于标注哪个是当前焦点
 */
export function getUnfinishedPlansContext(plans: Plan[], focusPlanId: string | null): string {
  const unfinished = plans.filter(p => p.status === 'executing');

  if (unfinished.length === 0) return '';

  const planBlocks = unfinished.map((plan, index) => {
    const isFocus = plan.id === focusPlanId;
    const statusLabel = isFocus ? '当前焦点' : '进行中';
    const steps = plan.steps
      .map(s => {
        const icon = s.status === 'done' ? '✅' : s.status === 'running' ? '⏳' : '⬜';
        return `  ${s.order + 1}. ${icon} ${s.description}`;
      })
      .join('\n');

    return `### Plan ${index + 1}: ${plan.agentName} (${statusLabel})
- Agent: ${plan.agentName} (${plan.agentId})
- 步骤:
${steps}`;
  }).join('\n\n');

  return `## 未完成的计划

以下是当前所有未完成的计划，请根据用户消息判断应该继续哪个计划：

${planBlocks}

## 决策规则

收到用户消息后，你必须判断：
1. 如果用户消息与某个未完成计划的目标相关 → 继续该计划，在计划描述中写明"继续「计划名称」"
2. 如果用户消息是全新需求，与所有未完成计划都不相关 → 创建新计划（系统自动切换焦点）
3. 如果用户消息是简单问答、闲聊、或不需要多步骤执行的指令 → 直接回复，不使用计划`;
}
```

### Plan 创建时的自动关联

```typescript
// agent/core/eventAdapter.ts

// 检测大模型是否在"继续"某个已有 Plan
function detectPlanContinuation(
  newPlan: Plan,
  existingPlans: Plan[]
): Plan | null {
  const continuationPattern = /继续「(.+?)」/;
  const match = newPlan.steps[0]?.description?.match(continuationPattern)
    || newPlan.steps.map(s => s.description).join(' ').match(continuationPattern);

  if (match) {
    const targetName = match[1];
    return existingPlans.find(p => p.agentName?.includes(targetName))
      || existingPlans.find(p => p.steps.some(s => s.description.includes(targetName)))
      || null;
  }
  return null;
}

case 'plan.created': {
  const existingPlans = getUnfinishedPlans();
  const continuationTarget = detectPlanContinuation(newPlan, existingPlans);

  if (continuationTarget) {
    // 大模型在继续已有 Plan → 复用 Plan ID，追加步骤
    updatePlan(continuationTarget.id, {
      steps: [...continuationTarget.steps, ...newPlan.steps],
    });
    // focusPlanId 切换到该 Plan
    setFocusPlan(continuationTarget.id);
    // 不创建新 Plan
  } else {
    // 全新 Plan → 创建新 Plan，焦点自动切换
    addPlan(newPlan);
    setFocusPlan(newPlan.id);
  }
  break;
}
```

## 十四、Plan 确认与用户交互控制

### 问题背景

当前库的 Plan-Execution 模式存在三个层级的确认缺失：

```
用户: "生成一个mes系统"
  ↓
① Planner 直接生成完整 6 步计划（未经需求确认）
  ↓
② plan.created 立即 status = "confirmed"（未经用户审核）
  ↓
③ Executor 连续执行所有步骤（step1 提问后不等用户回复就进入 step2）
```

第三个问题的根因是：Planner 能看到我们的 systemPrompt（库的 `withSystem` 函数将其拼接在 `PLANNER_PROMPTED` 前面），但它把"需求不明确时必须主动提问"理解为"在计划中包含一个提问步骤"，而不是"只生成提问步骤、不规划后续"。

### 核心方案：Plan B — 整体 Plan + 子 Plan 委托

跨 Agent 的 Plan 关系采用**整体 Plan 模型**，而非 Agent 间隔离：

```
主智能体 Plan（整体计划，需用户确认）
  ├── Step 1: 确认需求
  ├── Step 2: 查询数据源 → 委托给数据助手
  │     └── 数据助手子 Plan: [查表结构, 查数据量, 创建查询]
  ├── Step 3: 创建页面
  └── Step 4: 配置路由
```

- **主智能体 Plan** 作为整体计划，需要用户确认
- 执行过程中委托给子 Agent 的步骤，自动生成**子 Plan**（无需用户确认，`parentPlanId`/`parentStepId` 关联）
- 用户停止时，停止的是整体计划，子 Plan 随之终止
- 用户补充描述时，重新规划整体计划，子 Plan 重新生成
- 用户只关心"我的任务计划是什么"，不关心是哪个 Agent 执行的

### 确认机制：Abort 分段执行

库的 `run` 方法是单次 async 调用，`[BLOCKER]` 只能停止当前步骤内的工具循环，不能阻止后续步骤执行。唯一能停止整个计划的是 `AbortSignal`。

**方案：利用 `AbortSignal` 在 `plan.created` 后立即中断，等待用户确认后再重启。**

#### 完整流程

```
用户: "生成一个mes系统"
  ↓
【第一次 run()】
  Planner 生成 N 步计划
  → plan.created 事件触发
  → eventAdapter: 设置 plan.status = "draft"
  → eventAdapter: 调用 onPlanCreated 回调
  → AgentFactory: activeAbortController.abort()
  → while 循环检查 isAborted() → 停止，不执行任何步骤
  ↓
UI 展示计划草案（Plan tab + 聊天区确认卡片）
  ├── 用户点"确认计划"
  │     → 发送 "确认计划，开始执行"
  │     → 【第二次 run()】，基于确认后的需求重新规划并执行
  │     → 执行过程中如果某步提问 → emit [BLOCKER] → abort → 等待用户输入
  │
  ├── 用户点"拒绝计划"
  │     → plan.status = "rejected"，回到 idle
  │
  └── 用户修改计划后确认
        → 发送修改后的需求描述
        → 【第二次 run()】，重新规划
```

#### 执行中停止 + 补充描述

```
执行中...
  ├── Step 1: ✅ 确认业务范围（离散制造）
  ├── Step 2: ⏳ 查询数据源...
  │
  └── 用户点击"停止"
      → plan.status = "stopped"
      → abort 当前 run
      → UI 显示输入框 + 已完成步骤摘要
      → 用户补充: "需要增加设备管理模块"
      → 【新 run()】，Planner 看到：
          GOAL: 生成一个mes系统
          用户补充: 需要增加设备管理模块
          已完成:
            - step1: 确认业务范围（离散制造） ✓
          → 重新规划剩余步骤，只规划未完成的部分
```

### 状态机

```
idle → planning → draft ──确认──→ confirmed → executing → completed
  ↑                  │                ↑            │
  │               拒绝               │         点击停止
  │                  │                │            │
  └──── idle ←───────┘                │         stopped
                                      │            │
                                      │     用户补充描述
                                      │            │
                                      └── planning ←──┘
```

### 库的 Planner 与 Executor 提示词关系

```
Planner 看到的 system prompt:
  {我们的 systemPrompt}
  ───────────────────
  {PLANNER_PROMPTED}

Executor 看到的 system prompt:
  {我们的 systemPrompt}
  ───────────────────
  {EXECUTOR_PROMPTED}
```

因此修改 `systemPrompt.ts` 可以同时影响 Planner 和 Executor 的行为。

### systemPrompt 修改要点

增加面向 Planner 的规划规则：

```
## 计划生成规则

在生成计划前，先判断用户需求是否明确：
- 如果需求不明确（如缺少关键信息、需要确认具体范围），
  只生成一个"向用户确认需求"的步骤，不要规划后续步骤。
  等用户确认后，系统会重新规划完整计划。
- 如果需求明确，生成 1-6 个独立、可执行的步骤。
```

强化 Executor 的 `[BLOCKER]` 规则：

```
## 阻塞规则

如果你在执行步骤时，需要向用户提问或等待用户确认，
必须将问题写在回复中，并在末尾包含 [BLOCKER]。
包含 [BLOCKER] 的步骤将被标记为阻塞，系统会等待用户回复后再继续。

示例：
  "需要确认：您希望支持哪些用户角色？管理员、普通用户、还是两者？[BLOCKER]"
```
