# 安全架构方案：统一应用访问控制（AppAccess）

## 版本

| 版本 | 日期 | 说明 |
|------|------|------|
| v1.0 | 2026-09-09 | 安全审计后实施的根本性授权重构：统一访问层 + 默认拒绝 + 声明式注解 |
| v1.1 | 2026-09-09 | X-API-Key 语义重定义：从「路径白名单认证」改为「已登录请求内的资源审批凭据」，外部免登录调用一律 401 |
| v1.2 | 2026-09-09 | 审批闭环五项修复：审批端点权限、运行态数据源门禁、平台资源创建权限、Key rotate/吊销级联、Datasource scope 显式化；新增 JUnit 15 项 + 冒烟脚本 |

## 一、背景（审计结论摘要）

2026-09-09 全量审计发现：认证层（JWT/BCrypt/过滤器链）完整，但授权层碎片化——三套机制（平台权限注解、应用角色 ACL、散落的 owner 校验）互不衔接，48 个 controller 仅 14 个有权限注解且集中在概念图谱模块。核心风险：

1. `POST /queries/execute`：任意登录用户对任意数据源执行任意 SQL，DDL 旁路参数 `allowDdl` 由请求自报；
2. `PUT /users/{id}/role` 无权限注解，且直接写 RoleUser——**任意用户可给自己授予 super_admin，完全接管平台**；
3. 流程实例 `force-jump`/`reject-to` 全链路（controller→service→engine）无权限校验；
4. 运行态 `runQuery` 不校验 queryId 归属应用，可跨应用执行查询；
5. `ApplicationOwnershipInterceptor` 只读 query string 的 applicationId，JSON body 与 path variable 全部绕过；
6. API Key 认证按 8 字符前缀查 12 字符前缀列（功能失效），且从不校验 sha256 hash、不检查过期；
7. JWT 密钥与数据源加密密钥默认值硬编码在仓库中；
8. CORS `allowedOriginPatterns=*` + `allowCredentials=true`。

**审计更正**：初版报告中"转办→自批审批绕过链"不成立——`ProcessEngine` 对 APPROVE/REJECT/TRANSFER/ADD_SIGN/DELEGATE 全部有 `checkTaskAssignee`（实为校验完备，初版 grep 截断漏看）。

## 二、方案总览

```
请求 → CachedBodyFilter（缓存 JSON body，供拦截器解析）
     → SecurityFilterChain（JWT / API Key 认证）
     → AppAccessInterceptor（应用级授权：单点强制，默认拒绝）   ← 本方案核心
     → PermissionInterceptor（平台级权限：@RequirePermission 注解）
     → Controller（只写业务，不再散落鉴权代码）
     → AppAccessService（唯一判定实现：owner / super_admin / 应用角色权限矩阵）
          ↑
     AppResourceResolver（资源→应用 解析器，可扩展点）
```

### 2.1 动作分级（AppAction）

| 动作 | 含义 | 满足条件（从上短路） |
|------|------|------|
| `MANAGE` | 成员/角色管理、应用改名/删除、流程强制跳转等危险运维 | super_admin → 应用 owner → 角色持 `app:manage` |
| `DEVELOP` | 开发态写：页面代码、查询定义、流程定义、绑定 | super_admin → owner → `app:manage` 或 `app:develop` |
| `RUN` | 运行态执行：跑查询、调工具、发起流程 | super_admin → owner → 应用任意角色成员（成员即用户） |
| `VIEW` | 查看应用内资源 | 同 RUN |

隐含关系 `MANAGE ⊃ DEVELOP ⊃ RUN ⊃ VIEW`；平台角色（super_admin 除外）不赋予应用访问权；页面级细粒度授权沿用 `app:page:{pageId}`（`assertPageAccess`，开发权直接放行，运行态按页面授权）。

### 2.2 单点强制：AppAccessInterceptor

- **注解声明优先**：`@AppAccess` 三种写法（直接参数 / 资源解析 / 类级兜底），见第三节；
- **默认规则兜底**：无注解但请求可解析出 applicationId（path → query param → JSON body）时，GET 按 `VIEW`、写方法按 `DEVELOP` 强制校验——**新端点忘写注解也有兜底防线**；
- **不可解析则放行**：平台级端点（/users/me 等）不受影响。

### 2.3 判定唯一实现：AppAccessService

所有 owner/角色判定收敛于此。旧的三处散落实现已收编删除：`ApplicationOwnershipInterceptor`（删除）、`QueryController.checkQueryOwnership`、`PageController.checkPageOwnership/checkAppOwnership`、`RuntimeController.checkPageAccess`（内部改调 `assertPageAccess`）、`ApplicationToolController.isAppMember`（成员管理升级为 MANAGE）。

## 三、开发指南（维护性核心）

### 3.1 新增一个应用内端点

```java
// 场景 A：直接持有 applicationId（参数/路径/请求体）
@AppAccess(action = AppAction.DEVELOP, from = AppAccess.Source.BODY, key = "applicationId")

// 场景 B：持有资源 id（如 queryId），经资源解析器定位应用
@AppAccess(action = AppAction.RUN, resource = "query", key = "id")

// 场景 C：controller 下所有端点同一动作 → 类级注解兜底
@AppAccess(action = AppAction.RUN, from = AppAccess.Source.PATH, key = "applicationId")
```

不需要写任何 if 判断；不写注解时默认规则仍然兜底校验。

### 3.2 新增一种可按应用鉴权的资源

在 `StandardAppResolvers` 中加一个静态嵌套 `@Component` 实现 `AppResourceResolver`（两个方法：`resourceType()` + `applicationIdOf(id)`），即可在注解中用 `resource = "<类型>"` 引用。用户级资源（如数据源，按 owner 而非应用归属）覆写 `userScoped() = true`。

### 3.3 平台级权限

与原来一致：`@RequirePermission(Permissions.XXX)`（PermissionInterceptor）。

## 五、部署与运营注意

1. **上线必须设置 `LUBAN_JWT_SECRET`**（≥32 字符随机串），否则每次重启所有用户登录态失效；
2. 数据源加密密钥仍支持 `LUBAN_DATASOURCE_SECRET` 环境变量覆盖，建议同步轮换；
3. 应用角色的 `app:develop` / `app:manage` 权限行需要在角色管理中为存量应用配置（owner 不受影响；未配置前普通成员只有 RUN 权）；
4. API Key 存量数据兼容：新过滤器按 `key_hash` 匹配，存量 Key 的 hash 在生成时已写入，无需迁移；但此前 8/12 前缀不匹配导致所有 Key 本就无法认证，故无兼容损失；
5. 开放注册（`/auth/register`）保持现状（产品决策），但新注册用户因默认拒绝 + 无应用角色，实际可触达面已收敛至其自建资源。

## 六、遗留与建议（未在本轮实施）

1. **前端适配回归**：非 owner 的应用成员此前无法通过开发态端点（被 owner 检查挡住），现在可经 `app:develop` 角色正常使用——建议实测一次"owner 给成员配角色 → 成员进设计器"流程；
2. `validateHtml` 依赖 DOMParser（前端 codeValidate，与本轮无关），Node/CI 环境需 polyfill；
3. `runTool` 的 APPLICATION/PLATFORM 两个分支代码相同（疑似复制粘贴错误），语义需产品确认后修正；
4. 建议补 Spring Security 集成测试（MockMvc 全链路），当前仅覆盖 AppAccessService 判定矩阵；
5. 审计报告原列的"转办→自批"绕过链经验证不成立，风险清单以本文档为准。

## 附录：流程条件分支引擎修复（E2E-2 驱动，2026-09-09）

条件分支 E2E 暴露出流程引擎的**叠加缺陷**（此前任何真实配置的条件分支都不生效）：

1. **`EdgeDef.condition` 只读顶层字段**：前端/Agent 约定把条件写在 `data.condition`，引擎读不到 → 条件恒空。
2. **JDK 15+ 移除 Nashorn**：`ScriptEngineManager.getEngineByName("JavaScript")` 在运行环境（JDK 25）返回 null → `evaluateCondition` 恒 true。运行环境实测确认无任何 JS 引擎。
3. **多满足边并行**：`createTasksForNextNodes` 遍历所有满足的边（end 跳过），条件恒 true 时互斥分支的两条边都被建任务 → 实例会同时走到 ≤3 和 >3 两个分支。

修复（`ProcessEngine` + 新增 `ConditionEvaluator`）：
- `parseEdges` 归一化：顶层 `condition` 优先，否则读 `data.condition`（兼容前端约定）；
- 内置确定性求值器 `ConditionEvaluator`（零依赖、无注入面），支持：数字/字符串比较（< <= > >= == !=）、`&&` / `||` 组合、字段缺失/非法表达式安全处理；顺带消除了"表单数据注入 JS eval"的注入面；
- 新增 `ConditionEvaluatorTest`（5 项）覆盖数值/字符串/逻辑/缺失/非法表达式。

验证：`workflow-e2e-advanced.sh` 用例 A（leaveDays=2 → 直属上级 → COMPLETED）、用例 B（leaveDays=5 → 直属上级 → 部门经理 → COMPLETED）全部通过，条件路由按 ≤3/>3 正确分流。

注意：条件分支设计要求**互斥**（每条满足的边都会建任务）；非互斥设计会并行推进（保留原有语义）。
