# 应用自检测试引擎设计（v3）

> 承接《需求文档-Agent应用自检测试与平台一致性升级-20260917.md》第五节。v2 响应用户新要求：
> ① 平台内**一键按钮**自动跑完"页面按钮 → 表单提交 → 审批"全链路；② 明确角色/账号切换机制（真切换 vs 模拟）；
> ③ 明确测试单据数据的清理机制；④ **用户手工制作的应用（未经 agent）也能测**。
> v3 增补：**通用性论证**（请假仅是样例，方案必须覆盖全部应用形态）+ **安全威胁模型**（以渗透测试标准自查）+ 决策记录。
> 所有集成点已核实到现有代码接口（runPreviewAs / startProcess / completeTask / outbox / bridge）。

## 0. 三个关键问题的结论（先行）

### Q1 角色切换：真切换还是模拟？
**结论：不做登录切换，也不做全局 impersonation；采用"真实账号 + 受限测试身份"**——
- 执行身份是**真实平台用户**（users 表里存在的人），所有业务逻辑（this.auth 过滤、审批人解析、assignee 校验、触发器派发）走正常服务层路径，语义与该用户本人操作完全一致；
- 身份的**传递方式**是服务层参数/逐请求 override（复用并扩展 preview-as 机制），不是登出登入，不是发密码登录：
  - 服务层：`runPreviewAs(queryId, params, actorUserId, operatorId)` 已存在（owner-only）；
  - 流程入口扩展：`startProcess` / `completeTask` 增加可选 `onBehalfOfUserId`（仅应用所有者可用 + 结构化审计），assignee 校验原样生效——"谁能审批"由引擎真实解析结果决定，测试只提供参与者清单；
- **为什么不真登录**：需要知道每个测试账号的密码（不可假设）、无法在后端无人值守执行、HTTP 会话管理复杂；**为什么不全局 impersonation**：X-Impersonate-User-Id 因越权审批风险已删除（commit 31f6215），恢复它等于把任意用户身份暴露给所有 API。受限测试身份把可用面收窄到"owner + 自己应用内的查询/流程/审批"，风险可控且有审计。
- （备选：为每个测试账号真实登录拿 JWT——冒烟脚本的做法。仍保留为可选模式，但不是默认：它要求账号密码入库，违背平台安全原则。）

### Q2 测试单据数据如何删除？
**结论：写入记账（ledger）→ 自动推导 cleanup → 残留审计**，三层保证：
1. **记账**：引擎在执行中记录每一笔写操作——`query_run` 捕获 `insertId`（从查询 SQL 解析 `INSERT INTO <表>` 得到表名）、`workflow_start` 捕获 `instanceId`、页面层 bridge 记账捕获表单提交的 insertId；
2. **自动 cleanup**：按 ledger 生成并执行 `DELETE FROM <表> WHERE id = <insertId>`（TestSpec 显式声明的 cleanup 优先，自动推导兜底）；流程实例**强制终止**（复用 process_ops 的强制终止语义）+ 按 runId 清理平台侧实例/任务/outbox 行（平台自有数据，owner-only purge 接口）；
3. **残留审计**：报告列出"本次创建但未能清理"的记录（表 + 主键），用户可一键手动删；TestSpec 无法推导出任何 cleanup 且未显式声明 → **拒绝执行**（强约束）。
- 触发器回写（状态变更、扣余额）只 UPDATE 已记账记录，不新增行，天然随主键清理；审批通过产生的余额扣减会**真实改数据**——测试数据段（setup 里 capture 初值 + cleanup 恢复余额或删除记录）由引擎自动补齐：对每条被 UPDATE 的行，执行前先 capture 原值，cleanup 按 PK 恢复。

### Q3 手工制作的应用（未经 agent）能测吗？
**结论：能。关键是一键入口不依赖 agent 的分析报告，而是从平台元数据自动提取"应用测试契约"。**
- **契约提取器（纯规则代码）**：扫描应用的页面代码（HTML/JS 解析出 DataQuery 调用、onclick 入口函数、startWorkflow(ID, formData) 调用点）、查询清单（读/写、参数）、流程定义 + 表单绑定（字段、approverType）、平台组织数据 → 产出结构化契约；
- **默认 TestSpec 由规则引擎生成**（无需 LLM）：取已发布流程 → 按表单字段类型填默认值（text→'测试'、number→1、date→今天、select→第一个选项）→ 按参与角色推导 actors（approverType=leader 选一个 leaderId 非空的用户，其 leader 为审批人；=member 直接用配置成员）；
- **agent 可选增强**：同一份契约交给 agent 生成更全的 TestSpec（主分支 + 驳回分支 + 边界）。有无 agent 只影响覆盖度，不影响可用性；
- **附带价值**：手工应用跑一键自检本身就是**链路体检**——提取不到 startWorkflow 注入点、触发器 paramsMapping 引用的字段页面不携带等断链问题，直接以"可测性缺口"出现在报告里。

## 1. 一键交互入口

- **按钮位置**：应用设计器工具栏「⚡ 链路自检」+ 应用列表操作菜单（同一后端端点）；
- **点击后流水线**（全平台自动，无需 agent 在场）：
  ```
  ① 契约提取（规则）→ ② TestSpec 生成（规则默认；agent 在场时可增强）
  → ③ 页面冒烟（每个页面在预览沙箱加载 + 触发关键 handler，收集 JS 错误与 bridge 记账）
  → ④ 业务链路执行（后端：表单写入 → 发起流程 → 审批 → 等 outbox → 断言）
  → ⑤ cleanup（ledger 驱动）→ ⑥ 测试报告（前端抽屉展示，含证据与残留清单）
  ```
- 用户看到的是一份报告，不是过程；失败步骤可展开看证据（SQL、outbox 状态、JS 错误栈）。
- agent 技能 `test:app-selfcheck` 复用同一端点（agent 生成的 TestSpec 直接提交执行）。

## 2. 分层执行架构

| 层 | 执行环境 | 测什么 | 身份机制 |
|---|---|---|---|
| **L2 业务链路**（后端同步执行，60s 上限） | AppSelfTestService | 写查询→发起→审批→触发器→数据断言（身份隔离、幂等、死信） | 服务层 actor 参数（扩展 preview-as） |
| **L2.5 页面冒烟**（预览 iframe 内，平台已有沙箱） | 测试钩子注入 useQueryBridge 桥 | 页面 JS 加载无错、按钮 handler 可执行、表单提交真的发起 DataQuery/startWorkflow 且参数正确 | bridge 每步声明 actor，后端逐请求 owner 校验 + 身份注入 |
| L4 浏览器级（远期） | Playwright headless | 真实渲染点击、断言 DOM/Toast | 测试令牌换取会话 |

**页面冒烟实现（不用 Playwright 的理由：零新增部署，复用 InteliPreview 的 iframe + postMessage 桥）**：
1. 预览容器注入测试模式 → 加载页面代码（与真实渲染同路径）；
2. 用 DOM API 填充页面自己的表单控件（注意 LubanUI.select 必须走 LubanUI.select().setValue——测试钩子直接调用平台组件 API，等价于真实操作）；
3. 程序化调用 onclick 指向的全局函数（`saveData()` 等）；
4. bridge 记账每一次 RUN_QUERY / START_WORKFLOW（查询名、参数、返回的 insertId/instanceId）→ 与契约核对："提交按钮应触发 InsertLeaveRequest + startWorkflow(250, formData 含 id)"；
5. 捕获 console error / 未定义函数 / 未注册 DataQuery 调用。
- 局限（明示）：不验证视觉呈现与像素，不验证跨页面导航的视觉流转——由远期 L4 补足。
- 多角色审批**不在页面层做**（页面只验"发起人视角"的按钮与提交）；审批链路在 L2 层验证。

## 3. TestSpec（v2，增补部分）

在 v1 基础上（actors / steps / setup / cleanup / `${插值}`，见 git 历史或 v1 文档）增加：

```json
{
  "testName": "员工请假-审批通过-扣减余额",
  "source": "rule-extracted | agent-generated | user-authored",
  "runs": {
    "business": { "steps": [ /* v1 的 L2 steps */ ] },
    "pageSmoke": [
      { "pageId": 164, "actions": [
        { "handler": "openAdd", "fill": { "name": "测试员工", "employeeNo": "T001" }, "invoke": "saveData" },
        { "handler": "searchData" } ] }
    ]
  },
  "actors": { "employee": { "platformUserId": 3 }, "leader": { "platformUserId": 2 } },
  "autoCleanup": true
}
```

- `source` 标记来源，报告据此展示"规则默认/agent 增强"；
- `pageSmoke[].actions`：`fill` 走平台组件 API，`invoke` 调 handler；bridge 记账自动核对，无需手写断言；
- `autoCleanup: true`（默认）：ledger 驱动的自动清理 + 被 UPDATE 行的原值恢复。

## 4. 后端设计（PR1 范围）

新增：`AppSelfTestController`（POST /applications/{appId}/self-test/run、POST .../cleanup-residual）、`AppSelfTestService`、`TestContractExtractor`（可在前端做——所有数据源都是现有前端 API；MVP 放前端，后端只收 TestSpec）、dto（TestSpec / TestRunReport / StepResult）。

执行语义（全部复用现有服务）：
| step | 调用链 | 关键校验 |
|---|---|---|
| query_run | QueryService.runPreviewAs | queryId 属于该应用；actor 存在 |
| workflow_start | ProcessEngine.startProcess(+onBehalfOf 参数) | PUBLISHED；审计记录 runId |
| task_complete | findByInstanceIdAndStatus(PENDING) → assigneeId==actor → completeTask(+onBehalfOf) | "没有指派给此用户的待办"明确报错 |
| wait_outbox | WorkflowTriggerOutboxRepository.findByInstanceIdOrderByIdAsc 轮询 | 全部 DISPATCHED/DEAD；DEAD 即 fail |
| assert_sql | QueryService.executeSql（owner） | SELECT-only；期望 vs 实际 vs resolvedSql |
| cleanup | executeSqlBatch + 平台侧 purge 接口 | DELETE/UPDATE 强制带 WHERE |

安全：owner-only（app.createdBy == 当前用户）；单应用并发锁 1；整体超时 60s；结构化审计日志（runId/appId/operator/actors/结果）。

### Q4 通用性论证：请假只是样例，方案如何覆盖全部应用形态？

方案里**没有任何请假专属逻辑**：契约提取器只依赖平台元数据（页面 JS、查询、流程定义、表单绑定、平台组织），TestSpec 是声明式通用格式，断言/清理按元数据推导。按应用形态逐个核对：

| 应用形态 | 契约提取 | 规则生成的默认 TestSpec | 说明 |
|---|---|---|---|
| 纯 CRUD 页面（无流程） | 页面 JS 的读写查询调用 | 只跑页面冒烟 + 查询步骤 | 流程清单为空即自动跳过审批段 |
| 单/多级审批流（本例） | startWorkflow 调用点 + 绑定表单字段 | INSERT → start → 逐节点审批 → outbox → 实例终态断言 | 审批人数按节点 approverType 推导 |
| 会签/或签 | collaborationMode 元数据 | 为每个 assignee 各生成一个 task_complete 步骤 | 或签只需一人，规则取第一个 assignee |
| 条件分支 | condition 边 + 表单字段默认值 | 用默认值让条件真实求值走一条主分支；**未覆盖分支列入报告** | 其余分支由 agent/用户补充用例 |
| 驳回/驳回至节点 | 同上 | 主链路 + 一条 REJECT 分支（agent 增强） | rejectToNode 属进阶动作，agent 生成 |
| 无表单流程（页面弹窗发起） | 页面 startWorkflow 的 formData 字面量 | 直接 start，无业务记录绑定 | 触发器若引用 form.data.* 而页面未注入 → 可测性缺口 |
| approverType=member/role/leader/department_head | 平台组织数据 | 全部可自动推导参与者 | leader→选 leaderId 非空用户；role→角色成员第一个 |
| approverType=form_field/script | — | **无法自动推导 → 标记缺口**，要求 agent/用户在 TestSpec 中显式给 actor | 诚实边界，不做猜测 |
| 编排类应用（orchestration） | 编排定义 | MVP 不自动生成，只跑页面冒烟 + 查询 | 编排试运行已有独立能力（test_run_orchestration） |
| 文件/明细表/人员部门等特殊表单控件 | 字段类型元数据 | file/excel 跳过并标记；member→owner；department→首个部门；detail_table→一行默认子行 | 类型化默认值表，全部可配置 |

**规则生成器的断言边界（诚实声明）**：自动断言 = 链路级事实——实例到达预期终态、outbox 全部 DISPATCHED（无 DEAD）、触发器 params 全部非 NULL（断链检测）、表单提交真的发生了（bridge 记账）。**语义级断言**（"余额必须减 2"、"状态必须变成已通过"）规则无法从元数据推导，由 agent 增强（它有分析报告）或用户手写。这个边界让规则生成器在任何应用上都不说谎。

### Q5 安全：渗透测试视角的威胁模型

| # | 威胁 | 攻击路径 | 缓解（全部为实现约束） |
|---|---|---|---|
| T1 | 越权使用（IDOR） | 非所有者对他人应用发起自检 | 端点 `app.createdBy == 当前用户` 强校验（与 runPreviewAs 同语义）；datasourceId 必须属于该应用 |
| T2 | 伪装任意用户横向越权 | owner 传 actor=其他用户，读其数据 | actor 身份只影响**本应用**查询的 `this.auth` 替换与本应用流程的审批——数据源和业务库都是 owner 自己的，无新数据可读；审批的 assignee 校验原样生效（只有真实被指派人能完成），owner 无法替别人批别的应用的流程 |
| T3 | 用户枚举 oracle | 穷举 actorId 探测平台用户是否存在 | actor 校验失败统一报"参与者不可用"；actors ≤5 + 每小时每用户运行次数限流 |
| T4 | SQL 注入/越权 SQL | TestSpec 的 assert_sql 夹带 DML/DDL/多语句 | assert/capture 仅允许单条 SELECT/WITH 开头语句（无分号分隔）；全部经现有 SqlSecurityValidator；**cleanup 全部引擎生成**（按 ledger 主键 DELETE / 原值恢复 UPDATE），不接受用户声明的任意 DELETE |
| T5 | `WHERE 1=1` 清库 | cleanup 语义绕过 | 因 T4 的"引擎生成 cleanup"，DELETE 一律 `WHERE id = <ledger 记录的字面主键>`，不存在用户可注入的清理 SQL |
| T6 | 资源耗尽 | 巨型 TestSpec / 无限等待 / 并发轰炸 | steps ≤50、actors ≤5、整体 60s 超时、单应用并发锁 1、每小时运行次数限流 |
| T7 | 审计痕迹污染 | 以他人身份审批，workflow history 落了假审批人 | 每次运行的 completeTask/startProcess 由 AppSelfTestService 统一记录审计日志（runId、appId、operator、actors、各步结果）；实例数据连同平台侧行一起物理清除（决策 3），不留假审批历史 |
| T8 | 页面 JS 恶意行为（冒烟层） | 用户手写页面代码在冒烟时乱调接口 | 冒烟环境与现有预览沙箱同权限（本来就执行用户代码，无新增授权）；bridge 记账 + cleanup 兜底 |
| T9 | 报告泄露 | report 含敏感数据被他人读取 | MVP 报告**同步返回不落库**，无 GET 端点，只有发起者拿到 |
| T10 | REST 层基础项 | CSRF/会话固定/越权路径 | 复用平台现有 SecurityConfig（无状态 JWT + ApiKey 过滤器），新端点不加任何豁免 |

### 决策记录（原 1-5 决策点，已拍板）

1. **身份机制 = 受限测试身份**（Q1）；实现上无需给 ProcessEngine 加 onBehalfOf 参数——服务层直接以 actor 作为 operator 调用 completeTask/startProcess（assignee 校验原样生效），审计在自检引擎层统一记录（T7）。
2. **原值恢复 = 做**：ledger 三类条目——ROW_DELETE（INSERT 产生的行）、VALUE_RESTORE（触发器/UPDATE 改过的行，先捕获 pre-image 再恢复）、INSTANCE_PURGE（流程实例及其任务/历史/outbox 行）。
3. **实例清理 = 物理清除**：连平台侧实例/任务/历史/outbox 一起删（演示环境干净、避免假审批记录入历史），运行摘要保留在审计日志。
4. **cleanup = 全引擎生成**：TestSpec 不接受用户声明 cleanup，v2 的"拒绝执行"条款被更强方案取代（T4/T5）。
5. **页面冒烟 = 发起人视角**：加载 + 表单提交 + bridge 记账核对；审批链路只在服务层验证。
