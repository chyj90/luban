## 一、事件复盘：这次为什么必须手动停止

致命链条（17:47–17:49）：

1. 主智能体按平台指南写页面代码，调用 `DataQuery.PlatformDepartments()` 取部门下拉（`get_dataquery_guide` 和身份规则都明确要求这么做）；

**这不是 agent 一时糊涂，而是平台两套事实互相矛盾，而报错文案把 agent 引向了违反平台原则的修复路径。**

| 组件 | 立场 | 位置 |

## 二、问题清单（按严重度）

### P0-1 内置查询被校验器拒绝 → 错误委派 → 违反单一事实源
见上文复盘。修复点：
- `validateDataQueryCallNames`（codeValidate.ts:519）注入内置查询名白名单；
- `codeSkills.ts:476-482` 闸门为「仅内置查询」页面豁免；
- **把内置查询清单提为单一常量模块**，`promptFragments.ts`、`codeValidate.ts`、`useQueryBridge.ts` 三处引用同一来源，防止再次漂移。

### P0-2 intervention 误报暂停，且 agent 学会了 override 安全机制
- `detectManualInterventionRequest`（`frontend/src/agent/registry/skills/delegateSkills.ts:633-649`）用 `/interventionRequired/i` **纯子串匹配**扫 DBA 最终汇报；
- DBA 的汇报纪律（`dbaPrompt.ts:191-194`）要求【风险与残留】「没有也要写无」，于是产出「无 interventionRequired」——否定式照样命中；
- L917-929 拼出 `success:false, _pause:true` 暂停消息（日志中的双句号「。。」即 reason 尾句号 + 模板句号拼接产物）；
- 主智能体自行判定「系统误报」并继续执行。**这次恰好判断对了，但这是危险先例**：agent 会被训练成无视暂停机制；
- 回归测试 `agentEvals.ts` E13b（L777-812）恰好没有否定式用例。

修复方向（二选一，推荐 b）：
- a) 正则排除否定式（先剔除「无/没有/不需 interventionRequired」再匹配）——治标；
- b) **改协议：干预标记走结构化输出**。DBA/流程助手最终汇报末尾输出一行 JSON（如 `{"interventionRequired": false, "reason": "..."}`），检测器只认 JSON 字段，不认散文。判定这种关键决策不应依赖自然语言匹配和被截断的拼接文本（本次 DBA 子会话 61656 字符被 contextWindow 裁剪后才做判定）。

### P1-3 工具 schema 与提示词宣称不一致 + 缺 workflow 只读工具
- `promptFragments.ts:175-183` 宣称 delegate_workflow 支持 8 种 task_type（design_form/design_workflow/query_org/approval_task/process_ops/lint/copy_preview/general），工具 schema（`delegateSkills.ts:982`）只有 2 种，预校验（`argsValidator.ts:69-72` + `kernel/runtime.ts:330-338`）直接拦截；
- 主智能体为「确认流程 250 是否已发布」**起了一整个流程设计子智能体会话**——一次只读状态查询的成本；
- 根因：主智能体有 list_queries/get_query/list_pages，**唯独没有 list_workflows/get_workflow**。

### P1-4 lint 误报 ×2 → 告警疲劳
- (a) `lint_workflow` 断链误报：`LintService.java:281-284,340-344` 要求 paramsMapping 的 `form.data.*` 字段必须存在于绑定表单，但「业务记录 id 由发起页 startWorkflow 运行时注入」是平台级约定，lint 不知道，本次报了 4 个错误，流程助手只能口头解释为「预期内误报」；
- (b) `lint_query` 回写守卫误报：`queryLint.ts:66` 写的是 `/\bSTATUS\b/.test(body)`——正则测的是**原始大小写**的 body，而 `trimmed` 才是已大写版本。三条守卫 SQL 全部用小写 `status`，全部漏判、全部误报；
- 危害：当 agent 习惯性解释掉报错（「预期内误报」），真正的错误也会被解释掉。

### P1-5 发布即克隆新草稿，ID 混淆
`ProcessService.publishDefinition`（backend ProcessService.java:103-152）：草稿原地转 PUBLISHED（250），同时**新建一条 DRAFT 记录作为下一版编辑副本**（新 ID 258，publishedVersionId=250）。设计意图（发布 ID 稳定）没错，但 list_workflows 把两个同名流程并列展示，stale 资源检查也会盯上 258，agent/用户需要额外推理「用 250 不用 258」。

### P2-6 分析阶段引用幽灵页面
list_pages 始终只有 Page1(90)，分析报告却写「员工管理 (id:163) 页面记录已存在但代码缺失」（陈旧会话记忆）。执行时 agent 靠 404 自行恢复改用 create_page_scaffold 新建 164，但计划步骤类型（update）与实际（create）漂移，触发计划漂移提醒噪音。

### P2-7 脚手架主查询选错
`create_page_scaffold` 的 `primaryRead = readQueries[0]`（codeSkills.ts:573），把统计查询 GetEmployeeStats（单行聚合）当主列表查询，生成了「total_employees/monthly_new_hire 两列的员工表」。多读查询页面必须显式声明哪个是列表主查询。

### P2-8 script 审批人上下文无契约
流程助手为「leader 解析 + 空兜底」猜了两次脚本上下文（this.initiator / initiator / this.flow.initiator），预演全部解析为空，烧掉两轮 update_workflow + 预演。平台没有文档说明 script 里可用什么变量；「leader + 兜底」这个高频诉求没有一等公民表达，才逼出 script 方案。另外 `leader` 解析为空时静默 SKIP 节点（APPROVED 触发器永不执行）本身值得商榷。

### 结构性总结
指南（prompt）、运行时（bridge）、校验器（validate）、lint、预演**五套事实各自为政**。人类工程师遇到矛盾会怀疑工具，agent 只能按报错文案走——**平台对 agent 的每一条报错都必须是真话 + 正确的修复指引**。

## 四、Agent 行为升级

1. **冲突升级策略**：当校验器报错与平台指南（get_dataquery_guide / system prompt 规则）矛盾时，禁止直接按报错文案修复；先低成本求证（重读指南、查 `window.__QUERIES__`、或把矛盾上报用户）。可配套一个 `verify_capability` 工具（查询某 DataQuery 名运行时是否真的可用）。
2. **不许悄悄 override _pause**：配合 P0-2 的结构化协议后，若仍需解除暂停，必须走显式 `resolve_pause` 类工具（被记录、被确认的动作），而不是 agent 自行判读后继续。
3. 状态确认用只读工具，不起子智能体（配合平台 P1-5）。
4. 告警处理纪律：把一个报错解释为「预期内误报」必须附证据（预演输出/数据验证），无证据不许忽略——本次流程助手用预演证明的做法是对的，应写进 prompt 固化。

## 五、应用自检测试工具（核心新增能力）

### 5.0 定位
**测试对象是 agent 通过平台搭建出来的应用**（页面 + 绑定查询 + 表单/流程/触发器 + 多用户协作），不是 luban 平台本身。解决两个痛点：
- agent 交付前无法自动验证应用真的能跑通（当前只有静态 rehearse_triggers 预演）；
- 人工验收要反复登出登入切换账号（员工发起 → 领导审批 → 查余额），非常麻烦。

**核心洞察：agent 搭建应用的过程本身就产出了测试规约。** 分析报告第 2/8 章（功能模块、交互与联动）+ submit_analysis 的 pages/workflows/callbacks + 实际产出资源（页面代码、查询 ID、流程 ID、触发器清单、参与角色）拼起来就是现成的验收标准。

### 5.1 现有积木（可直接复用，约 60% 底座已在）
| 积木 | 位置 | 现状 |
|---|---|---|
| 多账号真实登录 JWT | AuthController + 冒烟脚本已在用 | 可用 |
| 预览身份切换 previewAsUserId | InteliPreview → QueryService.runPreviewAs（QueryService.java:434-447，仅应用所有者） | **只覆盖查询执行**，不覆盖 startWorkflow/审批 |
| 事务回滚式 SQL 试跑 | ExecuteSqlRequest.rollback + QueryService.executeSqlBatch | 可用（本次 DBA 已用它验证守卫语义） |
| 触发器派发观测 | WorkflowTriggerOutbox（at-least-once、状态、重试、DEAD） | 完美断言点 |
| 页面运行沙箱 | iframe + useQueryBridge postMessage 桥 | 可挂测试钩子 |
| agent 确定性回归 | frontend/src/agent/registry/test/agentEvals.ts | 模式可复制 |
| ~~全局模拟登录~~ | X-Impersonate-User-Id + impersonationStore（commit 31f6215 已删） | 因越权审批风险移除，**不恢复**；新方案走显式测试会话 |

### 5.2 整体设计：应用验收测试（App Acceptance Test, AAT）

```
L1 静态链路检查（已有：lint + rehearse_triggers，修掉误报即可）
L2 场景执行引擎（核心新增：TestSpec 驱动，API 级多用户场景 + 数据断言）
L3 页面级冒烟（可选：桥接冒烟 / headless 浏览器两档）
智能层：agent 生成 TestSpec → 执行 → 自修复 → 证据汇报
```

### 5.3 TestSpec 格式（从分析报告自动派生，agent 可补充）

```yaml
testId: leave-approve-happy-path
scenario: 员工请假-领导审批通过-扣减余额
actors:                       # 全部用真实平台用户（复用 search_platform_users 的绑定）
  employee: { platformUserId: 3 }   # 张三
  leader:   { platformUserId: 2 }   # 周九（由流程引擎解析，也可显式指定）
setup:                        # find-or-create，按 tag 幂等
  - ensure: employees 绑定 user_id=3 且 leave_balance>=2（记录初始值）
steps:
  - actor: employee
    action: query.run { queryId: 154, params: { leaveType: '年假', days: 2, ... } }
    capture: leaveId = insertId
  - actor: employee
    action: workflow.start { processId: 250, formData: { id: '${leaveId}', leave_type: 'annual', ... } }
  - actor: leader
    action: task.approve                    # 也可 task.reject 走驳回分支
assertions:
  - wait: triggerOutbox(instance).allTerminal(timeout=30s)   # 4 条触发器全部 SUCCESS/跳过
  - expect: query.run { sql: "SELECT status FROM leave_requests WHERE id=${leaveId}" } == '已通过'
  - expect: employees.leave_balance(user_id=3) == 初始值 - 2
  - replay: trigger(155) once               # 可选：重放一条触发器验证幂等（守卫命中 0 行，余额不变）
cleanup:
  - delete leave_requests WHERE id=${leaveId}   # finally 语义，失败也执行
```

### 5.4 L2 执行引擎要点

**身份（多用户切换的安全方案）**：不恢复全局 impersonation 头。走「测试会话」：
- 应用所有者显式发起一次 AAT 运行 → 后端创建 test session（审计记录：谁、何时、测哪个应用）；
- 为每个 actor 签发真实 JWT（或带 test-session 标记的受限令牌）；
- 把 `previewAsUserId` 的语义从「仅查询」扩展为「test-session 作用域内覆盖 startWorkflow / 审批任务处理」，复用 QueryService.runPreviewAs 的所有者校验模式；
- 会话结束令牌即失效，全程留痕。

**流程驱动**：startWorkflow（以发起人身份）→ 引擎解析审批人 → 以审批人身份 approve/reject → 轮询 WorkflowTriggerOutbox 到终态（现成的 at-least-once 观测点，含 group_order 顺序与重试语义，TriggerDispatcher）。

**数据断言**：以任意 actor（或所有者）跑 SELECT 对比期望值；支持前后快照对比（余额 = 初始值 - 天数）与**触发器重放**（验证守卫幂等——把本次 DBA 手工做的 rollback 验证自动化）。

**数据隔离**（按成本递进）：
1. TestSpec 自带 setup（find-or-create by tag，幂等）+ cleanup（finally 删除本次创建的记录）——最低要求，杜绝再出现 9 个「冒烟测试部门」（smoke-test-workflow.sh 固定名创建、`set -euo pipefail` 中途失败即跳过清理的教训）；
2. 受影响表行级快照/恢复；
3. （远期）每应用可选「测试数据源」：同一 schema 克隆，绑定到测试模式，测完整体丢弃。

### 5.5 L3 页面级冒烟（两档）

- **桥接冒烟（便宜档，推荐先做）**：复用 InteliPreview 的 iframe + useQueryBridge，注入测试钩子——加载页面 JS，收集 console error、未注册的 DataQuery 调用、onclick 引用的函数是否定义（静态可达性）；bridge 记账断言关键 DataQuery 调用真的发生、startWorkflow 被以正确参数调用。能抓住 L2 测不到的「页面 JS 运行时报错」。
- **headless 浏览器（完整档，发布门禁用）**：Playwright 真实渲染 + 点击（打开弹窗 → 填表 → 提交 → 断言 toast/表格刷新）。

### 5.6 智能自测闭环（agent 技能）

新增技能 `test:app_selfcheck`（或把计划模板里的「链路验证」步骤从 rehearse_triggers 升级为 run_app_test）：
1. agent 用自己的分析报告 + 实际产出资源 ID 生成 TestSpec（主分支 + 驳回分支各一份，样例数据贴近真实——本次 rehearse 的样例准备过程直接平移）；
2. 调 L2 引擎执行，拿结构化报告（每步 pass/fail + SQL 证据 + outbox 证据）；
3. 失败 → 自修复（改页面代码/触发器/查询）→ 重跑，循环上限 N 次；
4. 向用户汇报证据。「禁止无证据标完成」从预演证据升级为**运行时证据**。

### 5.7 交互式多用户预览（解决人工验收切账号的痛点）

把设计器已有的「身份预览」下拉（目前只影响查询）升级为**测试模式全链路身份切换**：选张三 → 查询、发起流程都按张三执行；切周九 → 看到待办并能审批。边界：应用所有者 + 显式开启测试模式 + 审计日志。人工验收从此不用登出登入。

### 5.8 落地顺序

1. P0 修复（半天级：白名单两处 + 正则一处 + 结构化干预标记）；
2. TestSpec + L2 引擎（后端 AppTestController：test session 签发、步骤执行、outbox 等待、断言、cleanup；复用现有 query/workflow API）；
3. agent 自测技能接入计划模板（替代 rehearse_triggers 作为完成证据）；
4. L3 桥接冒烟；
5. 交互式身份切换（扩展 previewAsUserId 作用域）；
6. headless 浏览器档、测试数据源克隆（远期）。
