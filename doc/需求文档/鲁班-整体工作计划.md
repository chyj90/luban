# 一、顶层架构

## 1.1 一句话定位

> **鲁班 = 企业 Agent 的操作系统**，让企业 Agent 能 **连接** 业务系统、**问数** 做决策、**开发** 自动化流程。

## 1.3 数据流方向

| 方向 | 谁调谁 | 协议 | 优先级 | 干什么 |
|------|--------|------|:--:|------|
| 北向 ↓ | 企业 Agent → 鲁班 | **A2A** | ⭐ 远期 | 委派任务给鲁班 Agent，Agent 自主完成（Sprint 4） |
| 北向 ↓ | 企业 Agent → 鲁班 | **MCP** | ⭐⭐ 重要 | 调用鲁班包装好的企业工具 |
| 南向 ↓ | 鲁班 → 业务系统 | HTTP / SQL / MCP Consumer | ⭐⭐⭐ 核心 | 查询数据、执行操作 |
| 南向 ↑ | 业务系统 → 鲁班 | ❌ 不存在 | — | 业务系统不调鲁班 |

## 1.4 鲁班的核心价值：连接企业系统 + 转化为 MCP

鲁班的首要价值不是「被企业 Agent 通过 MCP 调用」，而是：

```
1. 连接企业系统
   鲁班 → HTTP 调用企业 API（MES/ERP/SCADA）
   鲁班 → SQL 查询企业数据库
   鲁班 → MCP Consumer 调用已有 MCP 服务

2. 将传统 API 转化为 MCP 工具
   企业传统 HTTP API → 鲁班工具注册表 → 暴露为 MCP Server
   → 企业 Agent 可以像调用函数一样调用传统业务系统

3. 接受企业 Agent 的 A2A 委派
   企业 Agent 说"帮我处理设备故障"
   → 鲁班 Agent 自主编排工具链（查状态→建工单→通知）
   → 返回结果给企业 Agent
```

| 角色 | 协议 | 优先级 | 说明 |
|------|------|:--:|------|
| 鲁班 → 企业系统 | HTTP / SQL / MCP Consumer | ⭐⭐⭐ 核心 | 鲁班连接企业系统的能力 |
| 企业 API → MCP 工具 | MCP Server（北向） | ⭐⭐ 重要 | 将传统 API 包装为 MCP，供企业 Agent 调用 |
| 企业 Agent → 鲁班 | A2A | ⭐ 远期（Sprint 4） | 委派任务，鲁班 Agent 自主完成 |
| 企业 Agent → 鲁班 | MCP（直接调工具） | ⭐ 次要 | 企业 Agent 直接调用某个包装好的工具 |

## 1.5 两层 Agent 的关系

| | 企业自建 Agent | 鲁班 Agent |
|------|------|------|
| 归属 | 企业自己的 | 鲁班内置的 |
| 入口 | Claude Desktop / 飞书 / 自研 | Web 对话界面 |
| 调用方式 | MCP 调工具（当前）/ A2A 委派（Sprint 4） | 直接调度连接/问数/开发 |
| 典型场景 | 复杂任务委派、多步流程 | 用户直接对话、单工具调用 |
| 例子 | "CNC-07 报警了，帮我处理" | "查 CNC-07 状态" |

## 2.3 MCP 网关层设计

**选型：自研轻量实现，不引入 Spring AI。**

理由：
- MCP 协议本身很简单：JSON-RPC 2.0 + SSE transport
- 自研可以精确控制行为，与现有 Spring Security + JWT 认证体系无缝集成
- 避免 Spring AI 的依赖冲突和版本兼容问题

**代码结构（规划）：**

```
backend/src/main/java/com/luban/mcp/
├── McpServerConfig.java          # MCP Server 配置
├── transport/
│   ├── McpSseController.java     # SSE 端点 + 消息端点
│   └── McpSessionManager.java    # 会话管理（sessionId → API Key）
├── protocol/
│   ├── JsonRpcMessage.java       # JSON-RPC 消息模型
│   ├── JsonRpcRequest.java
│   ├── JsonRpcResponse.java
│   └── McpMethods.java           # initialize/tools.list/tools.call
├── handler/
│   ├── InitializeHandler.java    # 握手处理
│   ├── ToolsListHandler.java     # 工具发现
│   └── ToolsCallHandler.java     # 工具调用
├── auth/
│   └── McpApiKeyFilter.java      # API Key 认证过滤器
└── model/
    ├── ToolDefinition.java       # MCP 工具定义
    └── ToolCallResult.java       # MCP 调用结果
```

**关键设计决策：**

| 决策 | 方案 | 理由 |
|------|------|------|
| 传输方式 | SSE | MCP 标准推荐，Spring Boot 原生支持 `SseEmitter` |
| 会话管理 | `ConcurrentHashMap<sessionId, McpSession>` | 单机部署，内存会话足够 |
| 认证 | 独立 Filter，只拦截 `/mcp/**` | 与现有 JWT Filter 链共存，互不干扰 |
| 超时 | 30 秒，可配置 | 工具调用可能较慢，需要在 SSE 超时前返回 |

**MCP 协议交互流程：**

```
企业 Agent                          鲁班 MCP 网关
    │                                   │
    │── GET /mcp/sse ──────────────────→│  建立 SSE 长连接
    │←── SSE: endpoint event ──────────│  返回消息端点 URL
    │                                   │
    │── POST /mcp/messages/{sessionId} →│  发送 JSON-RPC 请求
    │   { "jsonrpc": "2.0",             │
    │     "method": "initialize" }      │
    │←── SSE: data ────────────────────│  通过 SSE 推送响应
    │                                   │
    │── POST /mcp/messages/{sessionId} →│
    │   { "method": "tools/list" }      │
    │←── SSE: 工具列表 ────────────────│
    │                                   │
    │── POST /mcp/messages/{sessionId} →│
    │   { "method": "tools/call",       │
    │     "params": {                   │
    │       "name": "query_device",     │
    │       "arguments": {              │
    │         "device_id": "CNC-07" }}} │
    │                                   │── 工具注册表查询
    │                                   │── HTTP Executor 调用
    │←── SSE: 调用结果 ────────────────│
```

## 2.4 工具注册表设计

**核心思路：用一张表统一管理所有类型的工具，现有 Query 也需要注册进去。**

```
ToolDefinition 实体：
├── id: Long
├── name: String              # 工具名称（唯一），Agent 通过这个调用
├── description: String       # 工具描述，Agent 语义理解用
├── type: ToolType            # HTTP / SQL / MCP_PASSTHROUGH
├── status: ToolStatus        # ENABLED / DISABLED
├── inputSchema: JSON         # JSON Schema 定义输入参数
├── outputSchema: JSON        # 输出结构描述
├── config: JSON              # 类型特定的配置（见下方）
├── groupId: Long             # 所属分组
├── createdAt: Instant
└── updatedAt: Instant

config 字段（根据 type 不同）：

type=HTTP:
{
  "method": "GET",
  "url": "https://mes.example.com/api/device/{device_id}",
  "headers": {"Authorization": "Bearer {{api_key}}"},
  "contentType": "application/json",
  "authType": "BEARER",
  "authConfig": {"headerName": "Authorization", "prefix": "Bearer"},
  "timeout": 30000
}

type=SQL:
{
  "queryId": 42                # 关联现有 Query 实体
}

type=MCP_PASSTHROUGH:
{
  "mcpServerUrl": "https://mes.example.com/mcp/sse",
  "remoteToolName": "query_device_status",
  "authConfig": {"type": "API_KEY", "key": "mcp_xxx"}
}
```

**与现有 Query 的关系：**

```
ToolDefinition ──config.queryId──→ Query ──datasourceId──→ Datasource
     │                                                       │
     │  统一工具注册表              现有查询系统              │
     └───────────────────────────────────────────────────────┘
                       完整工具链路
```

**权限模型：**

```
ToolDefinition ←──many-to-many──→ Role ←──many-to-many──→ User
                                              │
                                    ┌─────────┴─────────┐
                                    │                    │
                               API Key              SSO 用户
                            (Agent 连接用)        (控制台登录用)
```

# 四、需求文档问题分析

## 4.1 🔴 问题 1：技术栈与现有代码完全不一致

| | 需求文档 | 现有代码 |
|------|---------|---------|
| 后端语言 | Python 3.11 + FastAPI | **Java 21 + Spring Boot 3.3** |
| MCP SDK | `mcp` Python 库 | **不存在** |
| 数据库 | SQLite | **MySQL 8.0** |
| 前端框架 | React 18 + Ant Design 5 | **React 19 + 无 UI 库（自研）** |

**影响：** Sprint 1 的 MCP 网关需要 Python MCP SDK，但现有后端是 Java 生态。需求文档没考虑现有代码。

## 4.2 ✅ 问题 2：产品定位与现有代码的关系（已澄清，非问题）

> **关键认识：现有平台 = 三大核心能力中的「开发」，不是全部产品。**

| | 需求文档 | 现有代码 |
|------|---------|---------|
| 覆盖范围 | 连接 + 问数 + 开发（完整产品） | 开发（三大能力之一，已实现） |
| 关系 | 需求文档是蓝图 | 现有代码是「开发」模块的落地 |
| 定位 | 企业 Agent 的操作系统 | 低代码应用构建平台（开发子模块） |

需求文档中「开发」部分描述的工具开发、可视化看板、流程编排——现有代码已实现或部分实现。这不是冲突，而是**需求文档的「开发」模块已经有了现成实现**。需求文档未提及的低代码能力（Monaco 编辑器、iframe 预览、页面生成）正是「开发」模块的具体实现方式。

**结论：不存在定位冲突。需求文档描述完整产品，现有代码覆盖了其中「开发」这一块。**

## 4.3 🟡 问题 3：「流程编排」一词指代了两个完全不同的东西

需求文档 Sprint 3 说的「流程编排」本质是 **API 编排**：
> 把多个 HTTP/SQL API 串起来自动执行，机器自己跑完，不需要人参与每一步。

现有代码的「流程编排」本质是 **审批流程**：
> 请假审批：发起人 → 领导审批 → 人事确认，每一步都要等人点按钮。

| | API 编排（需求文档想做的） | 审批流程（现有代码已做的） |
|------|-----------|-----------|
| 谁执行 | 机器自动 | 人等机器提示，人操作 |
| 典型场景 | 查设备→建工单→发通知 | 请假→领导批→归档 |
| 执行时长 | 秒级 | 小时/天级 |

需求文档用同一个词「流程编排」描述这两个东西，但它们的引擎、数据模型、执行方式完全不同。

## 4.4 🟡 问题 4：Sprint 2 的「数据库直连工具」与现有 Query 体系冲突

需求文档 S2 描述：
> "管理员录入 SQL 模板，参数占位符 `{{device_id}}`，系统自动解析为 MCP 工具"

现有代码已有完整的 Query + Datasource 体系，支持参数化查询。问题是：
- 现有 Query 是为「低代码页面」服务的，绑定到 CodePage 的 iframe 中
- 需求文档的 SQL 工具是为「MCP Agent」服务的，暴露给外部 Agent 调用

**两者可以统一，但需求文档没有考虑现有 Query 体系的重用。**

## 4.5 🟡 问题 5：「连接」和「开发」中的工具开发有重叠

需求文档中：
- **连接**：把 HTTP API 注册为 MCP 工具（手工录入 / OpenAPI 导入）
- **开发**：工具开发（手工录入 / 批量导入 / SQL 查数）

这两者在功能上高度重叠——都是「把什么东西注册为工具」。正确理解应该是：
- **连接**是「管接入」：认证、授权、安全、协议转换
- **开发**是「管创建」：用什么方式创建工具（手工、OpenAPI、SQL）
- 两者是正交维度，不是并列关系

## 4.6 🟡 问题 6：Sprint 1 不做「数据库直连」，但现有代码核心就是数据库直连

需求文档 Sprint 1 明确不做：
> "数据库直连（SQL→工具）Sprint 2 再做"

但现有代码的 Datasource + Query 就是数据库直连，且是现有产品的核心链路。Sprint 1 的规划完全无视了现有资产。

## 4.7 🟡 问题 7：Sprint 依赖关系不成立

需求文档假设线性依赖 `S1 → S2 → S3 → S4`，但实际情况是：
- **鲁班 Agent**（S3 的 Web 对话界面）已经存在
- **可视化看板**（S3）和**流程编排**（S3）已经存在
- **MCP 网关**（S1）不存在
- **连接**（S1+S2）不存在

**真实依赖应该是：MCP 网关（S1）→ 连接（S2）→ 把现有 Agent/看板/流程接入 MCP → 新增问数能力**

## 4.8 🟡 问题 8：缺少「统一工具注册表」的设计

需求文档中，工具注册分散在多个地方：
- 手工录入（S1.1.2）
- OpenAPI 导入（S2.1）
- SQL 查询（S2.2）
- 算法插件（S4）

但没有一个统一的「工具注册表」概念。现有代码已经有 Query、Datasource、JsFunction 等实体，需要一个统一的 Tool Registry 来管理所有类型的工具。

### 模块1.1：MCP网关核心（P0）

**目标**：实现一个兼容MCP协议的服务端，能够接收Agent的连接请求并响应工具调用。

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|----------|
| G-01 | 实现MCP协议标准的`initialize`握手流程 | Agent（如Claude Desktop）能成功建立连接，返回正确的协议版本和服务器信息 |
| G-02 | 实现`tools/list`方法，返回所有已注册工具的列表 | 返回符合MCP规范的Tool列表，包含name、description、inputSchema |
| G-03 | 实现`tools/call`方法，根据工具名和参数执行对应的业务逻辑 | 正确解析Agent发来的工具调用请求，触发对应的HTTP调用并返回结果 |
| G-04 | 支持**HTTP API → MCP工具**的映射配置 | 管理员配置一个HTTP接口后，Agent能通过`tools/list`看到该工具，且调用时鲁班能正确转换为HTTP请求 |
| G-05 | 支持工具调用结果的**结构化返回** | 返回给Agent的响应是标准MCP格式，包含正确的content和结构化数据 |
| G-06 | 支持**同步超时控制** | 单个工具调用超时默认30秒，超过后向Agent返回明确的超时错误信息 |
| G-07 | 服务**启动和健康检查** | 提供`/health`端点，返回服务状态和版本号，可被监控系统集成 |
| G-08 | 结构化**调用日志** | 每次工具调用记录：timestamp, tool_name, user_id, input_params, output_summary, status_code, duration_ms |

> **约束**：
> - MCP协议版本锁定2025年11月稳定版（MCP官方OAuth授权规范定稿版本）
> - 仅支持SSE（Server-Sent Events）传输方式，HTTP Streaming作为备选
> - 单实例内存占用不超过512MB

### 模块1.2：手工录入工具配置（P0）

**目标**：管理员可以通过Web界面手工录入一个HTTP接口的信息，将其配置为MCP工具。

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|----------|
| T-01 | 工具创建表单：**基本信息** | 必填字段：工具名称（唯一）、工具描述（Agent语义理解用）；选填：分类标签、图标 |
| T-02 | 工具创建表单：**接口信息** | 必填字段：请求方法（GET/POST/PUT/DELETE）、请求URL；支持Path参数（如`/device/{id}`）和Query参数 |
| T-03 | 工具创建表单：**请求体定义** | 支持配置Content-Type（JSON/Form/Text），提供JSON Schema编辑器定义请求体结构 |

```
┌─────────────────────────────────────────────────────────────────┐
│                    两套流程引擎，各司其职                          │
│                                                                 │
│  AI 工具编排引擎（Sprint 3 新建）     人审批流程引擎（现有）       │
│  ┌────────────────────────────┐  ┌────────────────────────────┐  │
│  │ 节点类型：MCP 工具调用      │  │ 节点类型：审批/条件/抄送    │  │
│  │ 执行方式：自动执行          │  │ 执行方式：等待人操作        │  │
│  │ 编排方式：AI 生成 / 手动    │  │ 编排方式：拖拽设计器        │  │
│  │ 数据流：变量自动映射        │  │ 数据流：表单字段传递        │  │
│  │ 典型场景：查状态→建工单→通知│  │ 典型场景：请假→领导批→归档  │  │
│  │ 引擎：轻量 DAG，内存执行    │  │ 引擎：ProcessEngine（JPA） │  │
│  └────────────────────────────┘  └────────────────────────────┘  │
│                                                                 │
│  两者关系：互不依赖，独立演进                                     │
│  未来可能：DAG 引擎中的「人工确认节点」可以触发审批流程            │
└─────────────────────────────────────────────────────────────────┘
```

**技术决策：新建轻量 DAG 引擎，不改造现有 ProcessEngine**

理由：
1. 现有 ProcessEngine 是为「人参与决策」设计的，核心是状态机（待审批→已通过→已驳回）
2. AI 工具编排需要的是「自动执行的有向无环图」，核心是拓扑排序 + 并行执行
3. 强行改造会让两个引擎都变得复杂，且互相拖累
4. 两者未来可以通过「人工确认节点」桥接，但那是 V2 的事情

**DAG 引擎核心设计：**

```
com/luban/dag/
├── DagEngine.java              # DAG 执行引擎
├── DagDefinition.java          # DAG 定义（JSON 存储节点和边）
├── DagNode.java                # 节点定义
│   ├── nodeId: String
│   ├── toolName: String        # 关联的 ToolDefinition.name
│   ├── inputMapping: JSON      # 输入参数映射（从上下文变量取）
│   ├── outputMapping: JSON     # 输出结果映射（写入上下文变量）
│   └── condition: String       # 条件表达式（可选）
├── DagEdge.java                # 边定义
│   ├── sourceNodeId: String
│   ├── targetNodeId: String
│   └── condition: String       # 条件边（if/else）
├── DagContext.java             # 执行上下文（变量池）
└── DagExecutor.java            # 拓扑排序 + 并行执行 + 结果收集
```

**DAG 执行流程：**

```
1. 加载 DAG 定义（JSON）
2. 拓扑排序，确定执行顺序
3. 按层级并行执行（同层节点可并行）
4. 每个节点：
   a. 从 DagContext 读取输入变量
   b. 调用 ToolDefinition 对应的执行器
   c. 将输出写入 DagContext
5. 条件边：根据节点输出决定下一跳
6. 全部完成 → 返回 DagContext 中的所有变量
```

# 七、关键设计决策

## 7.1 连接 vs 开发 职责边界

### 问题

原始需求文档中，「连接」和「开发」都有「工具创建」的功能，边界模糊。

### 正确划分

```
连接（CONNECT）— 管「接入」
  ├── 这个系统能不能接入鲁班？（认证）
  ├── 接入后能做什么？（授权）
  ├── 接入后数据安全吗？（安全防护）
  ├── 怎么快速接入 100 个系统？（批量接入）
  └── 谁在什么时候调了什么？（审计日志）

开发（DEVELOP）— 管「创建」
  ├── 创建一个 HTTP 工具（手工录入 / OpenAPI 导入）
  ├── 创建一个 SQL 工具（基于现有 Query）
  ├── 创建一个 MCP 透传工具（对接已有 MCP 系统）
  ├── 创建一个可视化看板（已实现 ✅）
  ├── 编排一个工具流程（DAG 引擎）
  └── 注册一个算法插件
```

**两者的关系：**

```
            开发（创建工具）
                │
                │ 工具创建后，需要配置谁能用
                ▼
            连接（管控接入）
                │
                │ 认证通过后，Agent 才能调用工具
                ▼
            Agent 调用工具
```

**举例说明：**

> 管理员在「开发」中创建了一个「查询设备状态」的 HTTP 工具。
> 然后在「连接」中配置：只有「设备工程师」角色可以调用这个工具。
> 设备工程师的 Agent 通过 API Key 连接鲁班 → 认证通过 → 只能看到被授权的工具 → 调用成功。

### 对 Sprint 的影响

| Sprint | 连接 | 开发 |
|--------|------|------|
| S1 | API Key 认证 | HTTP 工具创建、SQL 工具创建、工具注册表 |
| S2 | RBAC、HMAC、SSO、数据级权限 | OpenAPI 批量导入、分组模板 |

## 7.4 AI 工具编排 vs 人审批流程

### 7.4.1 技术方案决策

**决策：新建轻量 DAG 引擎，不改造现有 ProcessEngine。**

| 对比维度 | 人审批流程引擎（现有） | AI 工具编排引擎（新建） |
|---------|---------------------|---------------------|
| 核心引擎 | `ProcessEngine.java` | `DagEngine.java` |
| 数据模型 | `WorkflowDefinition` + `ProcessInstance` + `Task` | `DagDefinition`（JSON） |
| 节点类型 | 审批节点、条件节点、抄送节点 | MCP 工具调用节点、条件节点、并行节点 |
| 执行方式 | 等待人操作（状态机驱动） | 自动执行（拓扑排序 + 并行） |
| 数据流 | 表单字段（FormDefinition） | 上下文变量池（DagContext） |
| 存储 | JPA 实体（可持久化、可恢复） | JSON 定义（轻量，可导出） |
| 典型场景 | 请假审批、报销审批 | 查设备→建工单→发通知 |

### 7.4.2 DAG 定义 JSON Schema

```json
{
  "id": "dag_001",
  "name": "设备故障闭环",
  "description": "报警触发 → 查状态 → 查历史 → 建工单 → 通知",
  "nodes": [
    {
      "id": "node_1",
      "toolName": "query_device_status",
      "inputMapping": {
        "device_id": "$trigger.device_id"
      },
      "outputMapping": {
        "device_status": "$result.status",
        "device_location": "$result.location"
      }
    },
    {
      "id": "node_2",
      "toolName": "query_maintenance_log",
      "inputMapping": {
        "device_id": "$trigger.device_id",
        "limit": 5
      },
      "outputMapping": {
        "recent_issues": "$result.records"
      }
    },
    {
      "id": "node_3",
      "toolName": "create_work_order",
      "inputMapping": {
        "title": "设备故障: $trigger.device_id",
        "description": "状态: $node_1.device_status, 位置: $node_1.device_location",
        "priority": "$trigger.severity"
      },
      "outputMapping": {
        "work_order_id": "$result.id"
      }
    }
  ],
  "edges": [
    { "source": "node_1", "target": "node_2" },
    { "source": "node_2", "target": "node_3" }
  ],
  "trigger": {
    "type": "manual",
    "inputSchema": {
      "device_id": { "type": "string", "description": "设备ID" },
      "severity": { "type": "string", "enum": ["high", "medium", "low"] }
    }
  }
}
```

### 7.4.3 两套引擎的未来桥接

```
未来场景（V2）：
  AI 工具编排中需要「人工确认」步骤

方案：
  DAG 引擎增加「人工确认节点」类型
  → 执行到该节点时，DAG 引擎暂停
  → 调用现有 ProcessEngine 创建一个审批任务
  → 审批通过后，ProcessEngine 回调 DAG 引擎继续执行
  → 审批驳回后，DAG 引擎执行失败分支

  这是桥接，不是合并。两个引擎保持独立，只在特定节点处交互。
```

# 八、需求文档补充不合理之处

> 以下是在详细设计过程中发现的额外问题，补充到第四节的问题清单中。

## 8.1 🔴 问题 9：Sprint 1 不做 SQL 工具导致演示价值低

原始 Sprint 1 只做 HTTP 工具（Mock MES），不做 SQL 工具。但现有代码的核心资产就是 Datasource + Query 体系。不做 SQL 工具意味着：
- Agent 无法查询真实数据库，只能调 Mock HTTP API
- 演示时只能展示「玩具级」能力，而非「生产级」能力
- 现有 Query 资产完全闲置，无法被 Agent 利用

**修正：Sprint 1 必须包含 SQL 工具，且优先级高于 HTTP 工具。**

## 8.2 🔴 问题 10：Sprint 3 才做 Web 对话界面，但已有现成的

原始需求文档 Sprint 3 模块 3.3「智能助手交互界面」要求新建 Web 对话界面，但现有代码已经有完整的 AgentPanel + Agent Loop + 多轮对话。这会导致：
- 要么重复造轮子（新建一个对话界面）
- 要么浪费现有资产（不用已有的 Agent）

**修正：Sprint 1 就让现有 Agent 接入 MCP 工具链，Sprint 3 只增强对话能力（归因分析、建议 Prompt）。**

## 8.3 🟡 问题 11：原始文档的「场景模板」定义过于模糊

原始文档把「场景模板」定义为预置内容包，但没说明：
- 场景模板和工具模板有什么区别？
- 场景模板是配置还是代码？
- 场景模板如何导入/导出？

**修正：**
- **工具模板**（Sprint 1）：单个工具的预置配置，一键导入即可用
- **场景包**（Sprint 3）：DAG 流程 + 工具链绑定 + NL2SQL 查询配置 + 看板模板，是一个完整的演示方案
- 场景包 = DAG 定义 JSON + 工具配置 JSON + 看板代码，可通过「导入场景包」功能一键部署

## 8.4 ✅ 问题 12：原始文档缺少「问数」模块的详细设计（已解决）

原始文档对「问数」的描述只有一句话：「5 大类 30+ 典型问法，覆盖制造业 80% 日常查询」。

**已确认方案：**

```
问数 = 两个独立功能：

1. 自然语言查询（NL2SQL）
   用户自然语言提问
      │
      ▼
   鲁班 Agent 意图识别 → 判断为「数据查询」
      │
      ▼
   LLM 根据表结构（Datasource Schema）生成 SELECT SQL
      │
      ▼
   SQL 执行器（复用现有 Query 体系）→ 返回结果
      │
      ▼
   LLM 将结果转为自然语言回复

   不需要预置问答模板，大模型直接生成 SQL。
   优点是灵活，用户问什么都能查，不局限于预设问题。

2. 归因分析
   用户问"为什么 X 下降了"
      │
      ▼
   LLM 拆解分析维度（时间、产线、班组、物料、设备...）
      │
      ▼
   企业知识图谱提供维度关系（产线→设备→班组→物料→供应商）
      │
      ▼
   LLM 推理链：逐维度查询 → 对比 → 排除 → 定位根因
      │
      ▼
   生成归因报告（结论 + 证据链 + 建议）
```
