## 一、背景

平台对"平台数据源、系统工具(API)"的授权历史上有两条并行链路，语义互相纠缠：

| 链路 | 授权对象 | 存储 | 审批流 | 原本服务的场景 |
|------|---------|------|--------|--------------|
| A. KEY 授权 | API Key → 数据源/工具 | `api_key_datasource` / `api_key_tool` | 工具权限审批 / 数据源权限审批 | 外部系统经 X-API-Key 调平台 |
| B. 系统权限 | 用户 → 系统（ToolGroup） | `system_permission` | 系统权限审批 | 用户申请系统访问 |

矛盾在"应用使用平台资源"这个场景上爆发：

1. **应用数据源面板**曾把「KEY 授权数据源」当展示项，造成"应用的数据源授权 = 给 KEY 申请"的认知；
2. **工具执行**（PAGE 入口）的真实门禁是"应用绑定 ACTIVE KEY + KEY 有该工具 APPROVED 授权"（`ToolTargetExecutor.assertPageAccess`、`ApplicationToolController.run`）——把机器身份的授权当成了人的授权用；
3. **执行层死路**：`QueryService.executeSql/executeSqlBatch` 把数据源 `ownerId` 当应用 id 校验归属，平台数据源（ownerId=系统 id）在这条路上必然失败；
4. 与《需求文档-统一调用架构与流程触发器》的入口分域原则冲突：**Key 授权只应出现在 PUBLIC_API 入口**，PAGE 入口的授权是"页面级授权 + 应用归属"。

## 二、目标模型：主体分域，资产收敛

### 2.1 主体只有两类，应用不是授权主体

```
                 ┌─────────────── 人（USER）───────────────┐
                 │  角色权限体系，永远不经过 API Key          │
                 │                                        │
   系统维度       │  system_permission(APPROVED)            │  ← 建模中心「申请平台数据源」
   （系统资产）    │  → 该系统下数据源可见/可执行、工具可调用    │     走「系统权限审批」工作流
                 │                                        │
   应用维度       │  应用角色三态（RUN/DEVELOP/MANAGE）        │  ← 页面运行、应用管理
   （应用资产）    │  + 页面级授权 app:page:{pageId}           │
                 └────────────────────────────────────────┘

                 ┌─────────────── 机器（API_KEY）──────────┐
                 │  只在 X-API-Key 外部入口生效              │
   外部调用       │  api_key_datasource / api_key_tool       │  ← KEY 权限页申请
                 │  APPROVED 绑定 + 限流配额                 │     走工具/数据源权限审批工作流
                 └────────────────────────────────────────┘
```

**应用（Application）是资产的容器（页面/查询/流程/应用工具），不是授权主体。** 旧模型"应用绑定 KEY → 借 KEY 的授权用平台资源"废除。

### 2.2 主体 × 资产矩阵（判定唯一事实源）

| 资产 | 人（开发态） | 人（页面运行时） | 机器（X-API-Key） |
|------|------------|---------------|------------------|
| 平台数据源 | `canUseSystemAsset`（SQL 控制台/测试；可见性同一谓词） | 页面权限（查询本身不重复判数据源） | `api_key_datasource` APPROVED |
| 应用数据源 | 应用归属（owner） | 页面权限 | `api_key_datasource` APPROVED |
| 平台工具(API) | `canUseSystemAsset` + 开发态应用角色 | **应用成员 + `canUseSystemAsset`** | `api_key_tool` APPROVED |
| 应用工具 | 应用归属（groupId=appId） | 页面权限 | `api_key_tool` APPROVED |
| 编排/流程 | 应用角色三态 | 页面权限 + 应用归属 | 后续按统一调用架构开放 |

`canUseSystemAsset(userId, systemGroupId)` 定义在 `AppAccessService`：超管 ∨ 平台管理员(connect:systems) ∨ 持有该系统 APPROVED 系统权限。**可见性（数据源面板清单）与可执行（SQL/工具调用）共用这一谓词。**

### 2.3 与统一调用架构四类入口的映射

| 入口 | 认证 | 授权 | 本需求的修正 |
|------|------|------|------------|
| 开发态 | JWT | 应用角色三态 + 系统资产走 canUseSystemAsset | executeSql 归属校验按 scope 分流（原平台数据源必失败） |
| 运行时页面 | JWT | 页面级授权 + 应用归属 + **系统资产加 canUseSystemAsset** | 摘除"应用→KEY→工具授权"门禁（原实现违背本原则） |
| 外部 API Key | X-API-Key | api_key_tool / api_key_datasource APPROVED + 限流 | **不变**——这是 Key 唯一的生效位置 |
| 内部触发 | manifest | 发布固化清单 | 不变 |

## 四、KEY 的最终定位

- **Key 是机器身份**：签发后授予数据源/工具（各自审批流），只在 X-API-Key 入口（PublicInvocation / MCP Gateway）生效 + 限流配额 + 统一审计。
- **Key 不再与应用绑定**：绑定端点已 @Deprecated，后续版本删除；KEY 权限页（/modeling/keys/:keyId/permissions）保留"申请工具/数据源权限"能力——那是给外部调用配权，不是给应用配权。
- **应用需要外部能力时的路径**：外部系统通过 Key 调平台公开 API；应用页面如需调用外部 HTTP 服务，用平台工具（系统工具走系统权限、应用工具走归属）。

## 五、迁移与兼容

1. 存量 KEY↔应用绑定已直接删除：`application_api_key` 表 DROP，绑定端点、服务方法、实体与仓库移除（平台未上线，不保留兼容层）。
2. 「数据源权限审批」「工具权限审批」两条工作流保留，继续服务 Key（机器主体）的授权申请；节点已由种子升级 `resolutionPolicy=fail`（申请前需确认审批人可解析）。
3. 超管申请系统权限直接生效（无需审批）。
4. `api_key_datasource`/`api_key_tool` 校验只在 `api_key_id` 请求属性存在时触发，普通用户会话不受影响——历史行为保持。
