## 一、背景

平台四类可调用对象——**Query（查询）、API/Tool（工具）、编排（Orchestration）、流程（Workflow）**——当前调用逻辑分散：入口按对象各建 Controller，鉴权散落在各入口且规则不一致；跨对象调用（编排调 Query、编排调流程）是点对点直连；流程引擎没有任何节点级扩展点，未来要在审批节点上加"触发器"（触发 Query/API/编排）将无处可挂。

### 1.1 现状问题清单

| 风险等级 | 问题 | 现状证据 | 影响 |
|:--:|------|------|------|
| 🔴 高 | Tool 执行逻辑散落多处，各自内联 HttpClient，鉴权/超时/重试不一致 | `RuntimeController.java:75`、`ApplicationToolController.java:53`、`DefaultNodeInvokers.java:43`、`AgentService.java:85`、`ToolDefinitionController.java:139`、`McpMethodRouter.java:90`（未实现） | 无法统一加固，新增一个入口就要复制一份执行+鉴权代码 |
| 🔴 高 | 流程引擎无任何节点级钩子，`event/listener/scheduler` 目录为空 | `workflow/event`、`workflow/listener`、`workflow/scheduler` 均为 0 文件（target 中残留 PostActionListener 编译产物，说明曾动工又废弃） | 审批节点触发器无处挂载 |
| 🟠 中 | 编排嵌套是隐式半残机制：无子编排节点，只能"发布成 ORCHESTRATION 型 ToolDefinition 再被 Agent/页面触发"；http 节点引用此类工具时 `config.url` 为空、静默不递归 | `OrchestrationService.java:251-273`、`DefaultNodeInvokers.java:61-67` | 嵌套行为不可预期，无审计 |
| 🟠 中 | 嵌套防护只有全局深度 64 兜底：无环检测、无超时预算传递（子编排重新拿 60s）、无跨对象调用图 | `OrchestrationEngine.java:29-30` | 深层嵌套/环可能耗尽线程与连接 |
| 🟠 中 | 鉴权三层并存但语义不齐：`@AppAccess`（应用角色三态）、页面级 `app:page:{pageId}`、API Key 工具级授权，分别写在不同入口 | `AppAccessInterceptor.java:54-77`、`RuntimeController.java:260-264`、`PublicOrchestrationController.java:26-47` | 同一对象从不同入口进，权限判定规则不同，审计困难 |
| 🟠 中 | 审批人脚本（`approverType=script`）用 Groovy 执行，无沙箱、无鉴权，注入了 userRepository/roleRepository | `ProcessEngine.java:1147-1207` | 流程定义者可借脚本查全库用户数据 |
| 🟡 低 | Query 模板参数值是"转义后字符串拼接"进 SQL，非 PreparedStatement 绑定 | `QueryService.java:894-898` | `{{params}}` 展开后的二次注入防御脆弱 |
| 🟡 低 | 领域服务横向直调：编排 query 节点直调 `QueryService.run`、编排 workflow 节点直调 `ProcessService` | `DefaultNodeInvokers.java:52,120-163` | 调用图是网状，深度/环/审计无处统一实现 |

### 1.2 未来诉求

在流程每个审批节点上增加**触发器**：节点进入/审批通过/驳回等事件发生时，自动调用编排、Query 或 API（工具）。触发器使"流程 → 编排 → 流程节点 → 再触发流程"成为可能，若用同步直调，环与事务耦合问题会立刻爆发（编排 `execute` 已有教训：不加 `@Transactional` 防 workflow 节点 rollback-only 吞结果，`OrchestrationService.java:171-177`）。

## 二、目标架构：星型拓扑 + 唯一漏斗

### 2.1 设计原则（三条）

1. **Controller 按调用方身份分，不按对象分**。调用方身份只有 4 类：开发态、运行时页面、外部 API Key、内部触发。对象差异（Query/Tool/编排/流程）全部下沉到 Service 层。
2. **跨对象调用一律走 `InvocationService` 唯一漏斗**。四个领域服务之间禁止横向互调（同域内部调用除外）；嵌套深度、环检测、超时预算、审计只在漏斗一个类里实现一次。
3. **内部触发不走 HTTP 自调用，权限用"发布时固化清单"**。编排/流程发布时静态校验其引用的目标并固化为 manifest，运行时内部触发只验清单，不再动态判页面权限——解决"流程触发器运行时该用谁的身份判权"的问题。

## 三、详细设计

### 3.1 核心模型

#### 3.1.1 ExecutionContext（执行上下文，强制透传）

所有进入漏斗的调用必须携带，所有跨对象调用由漏斗负责构造子上下文并传递：

```java
public class ExecutionContext {
    private Origin origin;            // DEV / PAGE / PUBLIC_API / ORCHESTRATION_NODE / FLOW_TRIGGER / AGENT / SCHEDULER
    private Principal principal;      // 用户身份 / ApiKey 身份 / 内部触发=流程发起人(on-behalf-of)
    private Long appId;               // 归属应用
    private String traceId;           // 本次调用链根 id
    private String parentTraceId;     // 父调用的 trace 记录 id，串全链路
    private int depth;                // 跨对象嵌套深度，根=0
    private Duration timeoutBudget;   // 剩余超时预算（子调用取剩余，不重置）
    private Set<String> ancestorPath; // 已过节点集，如 {"ORCH:8","FLOW:3"}，用于环检测
    private String idempotencyKey;    // 异步触发场景必填（outbox id）
}
```

#### 3.1.2 InvocationService（唯一漏斗）

```java
public interface InvocationService {
    InvocationResult invoke(InvocationRequest request);
}

public class InvocationRequest {
    private TargetType targetType;    // QUERY / TOOL / ORCHESTRATION / FLOW
    private String targetRef;         // queryId / toolId / 编排 definitionId / 流程 definitionId
    private String versionRef;        // 可选：锁定编排版本 / 流程定义版本
    private Map<String, Object> params;
    private ExecutionContext ctx;
}
```

漏斗内部按职责分四步（责任链）：

1. **鉴权**：按 `(origin, principal)` 查授权策略。内部触发（ORCHESTRATION_NODE / FLOW_TRIGGER）校验目标 ∈ 发起方版本的 manifest 清单；外部触发额外校验 Key 的 `api_key_tool` 授权（清单 ∩ Key 授权取交集）。
2. **护栏**：`depth > 8` 拒绝；`(targetType,targetRef) ∈ ancestorPath` 判环拒绝；子调用 `timeoutBudget = 父剩余 − 已耗`，耗尽拒绝；按 origin 查限流配额。
3. **分发**：按 targetType 路由到 `TargetExecutor`（策略模式，4 个实现），各 Executor 适配现有领域服务（QueryService.run / ToolExecutionService / OrchestrationEngine / ProcessService），**领域服务本身不改动**。
4. **审计**：写统一执行记录（含 parentTraceId），沿用现有 `PipelineTrace`。

```java
public interface TargetExecutor {
    TargetType support();
    InvocationResult execute(InvocationRequest request, ExecutionContext ctx);
}
```

#### 3.1.3 发布固化清单（capability manifest）

- 编排发布（`OrchestrationService.publish`）与流程发布时，解析 DSL/节点配置中引用的所有目标（queryId/toolId/编排/流程），**静态校验存在性 + 有权性**，写入版本记录的 `targets` JSON 字段（与现有 sha256 checksum 同级存储）。
- 运行时内部触发只验 `target ∈ 发起方版本 manifest`，不再动态判用户页面权限。principal 仍传递发起人，供目标服务内部的数据级过滤使用（如 Query 的数据源权限）。
- manifest 校验失败的调用记入执行记录并告警，返回统一错误码 `TARGET_NOT_IN_MANIFEST`。

### 3.2 Phase 1：ToolExecutionService 收敛（独立可交付）

新建 `service/ToolExecutionService`，作为 TOOL 类型的唯一执行实现，复用现有 `HttpExecutor`/`McpExecutor`：

| 改造点 | 现状 | 改造 |
|------|------|------|
| RuntimeController 工具执行 | 内联 HttpClient（`RuntimeController.java:75`） | 委托 ToolExecutionService |
| ApplicationToolController 调试 | 内联 HttpClient（`ApplicationToolController.java:53`） | 委托 |
| 编排 http 节点 | 自带重试 HttpClient（`DefaultNodeInvokers.java:43`） | 委托（保留 IpGuard 前置校验） |
| AgentService 工具调用 | 内联 HttpClient（`AgentService.java:85`） | 委托 |
| ToolDefinitionController `/tools/{id}/test` | 分发 httpExecutor/mcpExecutor | 委托 |
| McpMethodRouter tools/call | 未实现（`McpMethodRouter.java:96`） | 直接接 ToolExecutionService |

**不动**：SwaggerImportController（导入期抓取，非运行时执行）、AgentController 的对话转发。

### 3.3 Phase 2：InvocationService 骨架接入存量入口

1. 实现 InvocationService + 4 个 TargetExecutor + ExecutionContext。
2. 三个存量入口改为经漏斗，行为保持等价：RuntimeController（origin=PAGE）、PublicOrchestrationController（origin=PUBLIC_API）、AgentService（origin=AGENT）。
3. 编排节点改走漏斗：`DefaultNodeInvokers` 的 query/tool/workflow 节点改为构造 ExecutionContext（origin=ORCHESTRATION_NODE，principal=编排触发时的原始 principal）后调 InvocationService；删除对 QueryService/ProcessService 的直接 import。
4. 新增 `subflow` 显式子编排节点：DSL 加节点类型（`OrchestrationDsl.java:36` + `OrchestrationLinter.java:26` 白名单），执行时 origin=ORCHESTRATION_NODE、depth+1，替代"发布成 ToolDefinition 被 Agent 隐式再触发"。
5. 发布时生成 manifest（见 3.1.3）。
6. trace 打通：漏斗执行记录带 parentTraceId，PipelineTrace 可展示完整调用树。

### 3.4 Phase 3：流程触发器（本需求核心）

#### 3.4.1 触发器配置模型（存于流程定义节点 JSON）

```json
{
  "nodeType": "approval",
  "name": "部门审批",
  "triggers": [
    {
      "triggerId": "tg_001",
      "on": "APPROVED",
      "target": { "type": "ORCHESTRATION", "ref": "12" },
      "paramsMapping": [
        { "to": "instanceId",   "from": "instance.id" },
        { "to": "formData",     "from": "form.data" },
        { "to": "approverComment", "from": "task.comment" }
      ],
      "mode": "ASYNC",
      "retry": { "maxAttempts": 3, "backoffSeconds": [30, 120, 600] }
    }
  ]
}
```

- `on` 事件枚举：`NODE_ENTERED` / `APPROVED` / `REJECTED` / `INSTANCE_COMPLETED` / `INSTANCE_REJECTED`。
- `type` 支持：`ORCHESTRATION` / `QUERY` / `TOOL`。
- `mode` 固定 `ASYNC`（见 3.4.3）；`paramsMapping` 来源路径解析失败按空值处理并记录告警，不阻断主流程。
- 发布校验：LintService 增加 triggers 校验——targetRef 存在、类型合法、写入 manifest。

#### 3.4.2 事件产生：ProcessEngine 埋点 + 事务性 Outbox

- `workflow/event`、`workflow/listener` 目录落位：定义 `WorkflowNodeTriggerEvent`，在 ProcessEngine 的节点进入、审批通过、驳回、实例完结/驳回处（`checkAndCompleteInstance` 及任务状态流转点，`ProcessEngine.java:673-992`）发布。
- 监听器**只做一件事**：把触发器记录写入 outbox 表（与业务同事务），**不同步执行目标**。重试/派发与流程事务彻底解耦，避免上次 PostAction 雏形废弃的事务/重试问题。

```sql
CREATE TABLE workflow_trigger_outbox (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  instance_id     BIGINT NOT NULL,
  task_id         BIGINT,
  node_id         VARCHAR(64) NOT NULL,
  trigger_id      VARCHAR(64) NOT NULL,
  target_type     VARCHAR(32) NOT NULL,          -- ORCHESTRATION / QUERY / TOOL
  target_ref      VARCHAR(64) NOT NULL,
  payload         JSON NOT NULL,                  -- paramsMapping 解析结果 + 发起人/appId/traceId
  idempotency_key VARCHAR(64) NOT NULL UNIQUE,    -- outbox 天然唯一，作漏斗幂等键
  status          VARCHAR(16) NOT NULL DEFAULT 'PENDING',  -- PENDING/DISPATCHED/FAILED/DEAD
  attempts        INT NOT NULL DEFAULT 0,
  next_retry_at   DATETIME,
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  dispatched_at   DATETIME,
  KEY idx_status_retry (status, next_retry_at)
);
```

#### 3.4.3 派发：TriggerDispatcher（新建，`workflow/scheduler/`）

- 独立定时扫 `status=PENDING AND next_retry_at<=now`，逐条调 `InvocationService.invoke(origin=FLOW_TRIGGER, principal=流程发起人, idempotencyKey=outbox.id)`。
- **at-least-once + 幂等**：派发成功置 DISPATCHED；失败按 retry 退避重试，超过 maxAttempts 置 DEAD 并告警。漏斗以 idempotencyKey 去重。
- **环防护是结构性的**：触发器一律异步派发，"流程→编排→workflow 节点→触发新流程"链条被异步边界打断，不存在同请求递归；漏斗侧 ancestorPath + depth≤8 作为最后防线。同实例内触发器**禁止**配置同步回调本实例的动作。

#### 3.4.4 事务与超时边界（延续既有教训）

- ProcessEngine 埋点不等待触发器结果，审批接口响应时间不受触发器影响。
- 编排 `execute` 保持不加 `@Transactional` 的现状（`OrchestrationService.java:171-177`）；触发器执行记录由 `OrchestrationExecutionRecorder`（REQUIRES_NEW）继续兜底落库。

### 3.5 Phase 3 附带安全修复：审批人脚本沙箱

`approverType=script` 的 Groovy 执行（`ProcessEngine.java:1147-1207`）收敛为与 Query 模板同款的受限白名单沙箱（参照 `QueryService.java:75-117` OGNL RESTRICTED 做法）：移除 userRepository/roleRepository 直接注入，改为注入受控查询接口（按 id/roleCode 查询），加执行超时。

### 3.6 Phase 4（后续，不在本期）：外部统一端点与 Query 加固

- PublicInvocationController 合并为单端点 `POST /api/v1/public/invocations`（body 带 type/ref），现有 `/public/orchestrations/{toolName}/invoke` 保留为别名，逐步开放 TOOL/QUERY 外调（Key 授权粒度沿用 `api_key_tool` + 数据源授权）。
- QueryService 参数值改 PreparedStatement 绑定（`QueryService.java:894-898`）。

## 四、影响分析

### 4.1 前端影响

| 阶段 | 影响 |
|------|------|
| Phase 1-2 | 无。对外 HTTP 契约不变，页面/外部调用行为等价 |
| Phase 3 | 流程设计器需增加"节点触发器"配置 UI（事件、目标、参数映射、重试策略）；运维侧建议增加 outbox 死信查看页 |
| Phase 4 | 外部接入方无感（别名保留） |

### 4.2 历史数据兼容

- 存量流程定义无 `triggers` 字段 = 无触发器，行为完全不变。
- 存量编排版本的 query/tool 节点改走漏斗后行为等价；首次发布新版本时补生成 manifest，旧版本执行按"无 manifest = 按原直调目标校验存在性"降级兼容一个周期。
- 编排"发布为 ToolDefinition"机制保留（Agent/页面继续可用），仅嵌套推荐改用 subflow 节点。

### 4.3 数据库变更

| 变更 | 阶段 |
|------|------|
| 新表 `workflow_trigger_outbox` | Phase 3 |
| 编排版本表 / 流程定义表增加 `targets`（manifest JSON）字段 | Phase 2 |

### 4.4 性能

漏斗引入一次策略查表 + 上下文构造 + 一次审计落库（异步写），单次调用增加毫秒级开销；触发器为异步派发，审批接口耗时不受影响。深度限制从 64 收紧到 8，嵌套资源消耗显著下降。

## 五、验证方案

### A 组：漏斗行为等价（Phase 1-2 回归）

1. 页面运行时调用 Query / Tool / 编排：结果、错误码、耗时与改造前一致。
2. 外部 API Key 调用编排：Key 未授权工具仍 403；限流/日配额仍生效。
3. 编排试运行（开发态）+ 发布 + 运行全流程回归；nodeTrace 完整。
4. PipelineTrace 能看到"页面→编排→Query"三层 parentTraceId 链。

### B 组：嵌套与护栏

1. subflow 编排 A→B→C 正常执行；A→B→A 被环检测拦截，错误码明确。
2. 深度超过 8 被拒；子编排超时取剩余预算（父已耗 30s 时子最多 30s）。
3. http 节点引用 ORCHESTRATION 型工具：lint 报错（提示改用 subflow），不再静默不递归。

### C 组：流程触发器（Phase 3）

1. 审批节点配置 `on=APPROVED` 触发编排：审批接口立即返回，编排异步执行成功，payload 参数映射正确。
2. 触发器调编排 → 编排 workflow 节点 start 新流程 → 新流程触发器再调编排：链条异步推进，depth 到 8 后拒绝，无死循环。
3. 目标不可用（编排停用）：按退避重试 3 次后置 DEAD，告警产生，流程实例状态不受影响。
4. 幂等：Dispatcher 重启后重扫同一条 outbox，目标编排不重复执行（幂等键生效）。
5. 无触发器的存量流程实例回归：行为与埋点前一致。

### 通用检查清单

- [ ] 四个领域服务之间无新增横向 import（CI 可加 ArchUnit 规则固化）
- [ ] 所有跨对象执行记录可在 PipelineTrace 按调用树展示
- [ ] outbox 死信有告警通道
- [ ] Groovy 沙箱：注入仓库的旧脚本定义发布时报错并给出迁移提示
