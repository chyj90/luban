## 一、背景

### 1.1 现状

当前鲁班平台已完成「一、自动洞察（查数 → 懂数）」的核心能力建设：

- **NL2SQL**：用户自然语言 → FAISS 向量检索 → 概念匹配 → 本体展开 → LLM 推理 → SQL 生成/执行
- **CODE_MODE**：LLM 可生成 Python 代码（pandas/numpy），通过 `/v1/execute-code` 端点执行，支持传入 `input_data`（SQL 查询结果），实现复杂数据分析
- **下钻引擎**：DRILLS_INTO 关系定义维度下钻路径，LLM 自动多轮下钻分析
- **关联维度**：CORRELATED 关系交叉验证，排除干扰因素
- **异常阈值**：概念级别的 anomalyThresholdExpr，自动触发异常检测

### 1.2 问题

CODE_MODE 虽然支持 LLM 生成 Python 代码做数据分析，但存在以下局限：

| 问题 | 影响 | 严重度 |
|:--:|------|:--:|
| LLM 生成的代码不可靠 | 复杂算法可能出错，需人工验证 | 🟠 高 |
| 无法复用企业已有算法 | 已投入的算法资产无法接入 | 🔴 严重 |
| 无算法版本管理 | 算法更新后旧链路不可追溯 | 🟡 中 |
| 算法发现靠文本匹配 | 用户不知道有哪些算法，LLM 依赖描述匹配 | 🟠 高 |

### 1.3 目标

将「三、算法热加载（LLM + 企业算法编排）」与「一、自动洞察」结合，通过本体驱动算法发现与编排，实现企业决策场景落地。

**核心思路**：算法作为"本体感知的工具"注册到概念知识图谱中，复用 CODE_MODE 的 Python 执行通道，LLM 通过概念关系（INVOKES/INPUT_OF/OUTPUT_OF）自动发现并调用算法，输出可解释的决策建议。

### 1.4 企业实际使用场景分析

#### 两类用户角色

| 角色 | 能力 | 典型行为 | 平台诉求 |
|------|------|------|------|
| 算法工程师 | 能写 Python 脚本 | 上传排产算法、注册到平台 | 算法注册、版本管理、复用 |
| 业务人员 | 不会写代码 | 对话："三号线接5000件，产能利用率尽量高" | 平台自己搞定，无需预注册算法 |

#### 核心矛盾

当前 Phase 1 设计假设"企业有算法工程师预先写好脚本"（算法注册 → LLM 发现 → 调用）。但实际业务场景中，**最终用户是业务人员**，他们不会写代码，只会在对话中表达意图和优化目标。

平台必须覆盖以下三种算法来源（**Phase 1 实现 ①+③，Phase 2 加入 ②**）：

```
用户："三号线接5000件A产品，产能利用率尽量高"
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 算法来源路由（按优先级）                                         │
│                                                                  │
│ ① 已注册企业算法（ALGORITHM）                         【Phase 1】 │
│    企业算法工程师上传的排产脚本 → 精确、可审计、可复用            │
│                                                                  │
│ ② 预置算法模板（ALGORITHM_TEMPLATE）                   【Phase 2】 │
│    平台预置的通用排产/预测/检测模板 → LLM 按意图填充参数          │
│    → CODE_MODE 生成代码执行                                      │
│                                                                  │
│ ③ LLM 自由生成（CODE_MODE）                            【Phase 1】 │
│    无匹配算法时，LLM 根据约束和目标自主生成代码                   │
│    → 灵活但结果不可靠，需人工复核                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Phase 1 降级策略**：当企业算法不存在或执行失败时，LLM 使用 CODE_MODE 自行生成代码作为降级方案。Phase 2 加入模板后，降级链路变为：企业算法 → 模板 → CODE_MODE。

#### 设计原则

| 原则 | 说明 |
|------|------|
| 算法是增强，不是前提 | 没有预注册算法，平台也能通过 CODE_MODE 工作；有算法则更精确 |
| 意图驱动，自然语言交互 | 业务人员只需描述"做什么 + 优化什么"，无需关注技术细节 |
| 优化目标可声明 | "成本最低""产能利用率最高""交期最早" → LLM 转化为优化代码 |
| 渐进式精度提升 | ③ LLM 自由生成 → ② 模板化 → ① 企业算法 → 精度逐步提升 |
| 结果可解释 | 无论是哪种算法来源，最终输出都需 LLM 解读为业务语言 |

### 1.5 算法模板（Phase 2）

**模板的本质**：模板不是预写的算法，而是**结构化的 Prompt 元数据**。它告诉 LLM"这是什么场景、用什么优化框架、输入输出长什么样"，LLM 自己生成代码。模板是 CODE_MODE 的增强版——把"好的 prompt"固化下来，提高代码生成质量。

#### 模板从哪来

模板有三个来源，按重要性排序：

| 来源 | 说明 | 覆盖率 | 维护者 |
|------|------|:--:|------|
| **① LLM 自生成** | 用户描述意图后，LLM 自动推断场景、约束、优化目标，生成临时模板结构 → 生成代码执行。这是最核心的来源，覆盖无限场景 | 100% | LLM |
| **② 用户保存** | CODE_MODE 成功执行后，用户一键"保存为模板"。模板从成功案例中沉淀，随使用自然增长，覆盖企业专属场景 | 长尾 | 业务人员 |
| **③ 平台预置** | 5-6 个最高频场景的通用模板，覆盖 80% 常见需求，作为开箱即用的起点 | 80% | 平台 |

**核心逻辑**：模板不是"人写的"，是"跑出来的"。平台预置只是种子，真正的模板库在企业使用过程中自然生长。

```
用户："三号线接5000件，成本尽量低"
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ ① LLM 自生成临时模板（无需预置）                                  │
│    IntentParser 解析意图 → 场景=排产, 约束={line:3, qty:5000},   │
│    优化目标=成本最低 → 生成临时模板:                              │
│    { framework: "线性规划", input: [...], output: [...] }        │
│    → LLM 按模板生成代码 → 执行 → 结果                             │
│                                                                  │
│ ② 用户觉得好用 → 点"保存为模板" → 下次同场景直接用，精度更高     │
│                                                                  │
│ ③ 如果平台预置了排产模板 → 跳过自生成，直接使用预置模板           │
└─────────────────────────────────────────────────────────────────┘
```

#### 模板结构

模板是一个轻量级的元数据对象，不包含算法代码：

```json
{
  "name": "【模板】排产可行性评估",
  "category": "SCHEDULING",
  "input_schema": {
    "line_id": "string",
    "daily_capacity": "number",
    "order_quantity": "number",
    "deadline": "string"
  },
  "output_schema": {
    "feasible": "boolean",
    "utilization": "number",
    "suggested_start": "string"
  },
  "framework_hint": "scipy.optimize.linprog",
  "prompt_hint": "你是一个排产优化专家..."
}
```

#### 平台预置模板（种子库，20 个模板覆盖 4 个领域）

| 领域 | 模板数 | 典型场景 |
|------|:--:|------|
| 生产制造 | 5 | 排产、库存、OEE、异常检测、根因分析 |
| 金融 | 5 | 信用评分、还款评估、反欺诈、投资组合、流失预警 |
| 运营商 | 5 | 流失预测、话务量、负载均衡、用户分群、投诉分析 |
| 政法公安 | 5 | 案件趋势、风险评估、警情热点、相似度匹配、舆情分析 |

> 完整模板定义见附录 A，每个模板包含 `prompt_hint`、`framework_hint`、`input_schema`、`output_schema`。

#### 模板与算法的关系

| 维度 | 用户保存的模板 | 平台预置模板 | LLM 临时模板 | 企业算法 |
|------|:--:|:--:|:--:|:--:|
| 来源 | CODE_MODE 成功案例 | 平台团队 | LLM 实时生成 | 算法工程师 |
| 代码 | 无（存的是 prompt 元数据） | 无 | 无 | 有（Python 脚本） |
| 精度 | 中 | 中 | 低-中 | 高 |
| 适用场景 | 企业专属 | 通用 | 任意 | 企业专属 |
| 维护成本 | 零（自动沉淀） | 低 | 零 | 中 |

## 二、需求范围

### 2.1 本次需求（Phase 1：算法注册 + 本体绑定 + Agent 编排）

**目标**：支持算法注册、本体绑定、LLM 自动编排调用，覆盖 5 个验证场景。

**功能清单**：

| 编号 | 功能 | 说明 |
|:--:|------|------|
| F1 | 算法注册 | 算法作为 ToolDefinition（type='ALGORITHM'）注册，支持上传 Python 脚本 |
| F2 | 本体绑定 | 算法通过 ToolConcept（relation=INVOKES/INPUT_OF/OUTPUT_OF）绑定到业务概念 |
| F3 | Agent 路由 | AgentService 新增 `algorithm` action type，与 tool_call/nl2sql/code_mode 并列 |
| F4 | 算法执行 | 复用 CodeExecutorService 的 Python 执行通道，传入 SQL 查询结果作为 input_data |
| F5 | 结果解读 | LLM 对算法输出结果进行自然语言解读，生成决策建议 |
| F6 | 前端管理 | 算法复用现有工具管理页面（ToolListPage），新增 ALGORITHM 类型切换。ToolType 枚举统一管理所有工具类型，前端通过 `/api/v1/tools/types` 动态获取类型列表，无需新建独立页面 |

### 2.2 后续需求（Phase 2/3，不在本次范围）

- 算法链式调用（多算法级联编排）
- 算法版本管理与回滚
- 算法执行结果缓存
- 算法性能监控与告警
- MCP 协议接入（支持外部算法服务）

## 三、数据模型设计

### 3.1 复用现有表结构

算法热加载最大程度复用现有数据模型，减少新增表。

#### ToolType 枚举（新增，`com.luban.constant.ToolType`）

后端统一管理所有工具类型，避免硬编码字符串。每个枚举值包含 `value`（存储值）、`label`（展示名）、`description`（描述）：

| 枚举值 | label | description | 说明 |
|------|------|------|------|
| `HTTP` | HTTP 接口 | 调用外部 REST API | 现有 |
| `MCP_PASSTHROUGH` | MCP 透传 | 透传 MCP Server 工具 | 现有 |
| `ALGORITHM` | 算法脚本 | 企业算法 Python 脚本 | **新增** |

**设计原则**：
- 后端 `ToolType` 枚举是唯一真相源，新增类型只需加枚举值
- 前端通过 `GET /api/v1/tools/types` 动态获取类型列表，无需前后端分别维护
- `ToolDefinitionController.executeTool()` 和 `AgentService.executeTool()` 使用枚举 switch 替代字符串 switch

#### ToolDefinition 表（复用）

现有 `tool_definition` 表，新增 `tool_type='ALGORITHM'` 类型，config 字段存储算法脚本路径：

| 字段 | 类型 | 说明 | 算法类型的值 |
|------|------|------|-------------|
| tool_type | VARCHAR(20) | 工具类型 | `ALGORITHM`（新增枚举值） |
| config | JSON | 配置 | `{"scriptPath": "/path/to/algorithm.py", "timeout": 30, "pythonVersion": "3.11"}` |
| input_schema | JSON | 输入参数 | `{"type": "object", "properties": {"line_id": {"type": "string"}, "quantity": {"type": "number"}}}` |
| output_schema | JSON | 输出参数 | `{"type": "object", "properties": {"feasible": {"type": "boolean"}, "utilization": {"type": "number"}}}` |

#### ToolConcept 表（复用，扩展 relation 枚举）

现有 `tool_concept` 表，relation 字段新增算法专用关系类型：

| 字段 | 类型 | 说明 | 新增值 |
|------|------|------|--------|
| relation | VARCHAR(16) | 关系类型 | `INVOKES`、`INPUT_OF`、`OUTPUT_OF`（新增） |

关系类型说明：

| 关系类型 | 方向 | 语义 | 示例 |
|---------|------|------|------|
| INVOKES | 概念 → 算法 | 此概念的业务问题可调用此算法 | 订单量 → INVOKES → 排产算法 |
| INPUT_OF | 概念 → 算法 | 此概念的数据是算法的输入参数 | 产能 → INPUT_OF → 排产算法 |
| OUTPUT_OF | 算法 → 概念 | 算法的输出对应此概念 | 排产算法 → OUTPUT_OF → 产能利用率 |

### 3.2 新增表：algorithm_execution_log

记录算法执行历史，用于监控和审计：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT | 是 | 主键 |
| algorithm_id | BIGINT | 是 | 算法 tool_definition.id |
| session_id | VARCHAR(64) | 是 | 会话 ID |
| user_query | TEXT | 否 | 触发调用的用户问题 |
| input_data | JSON | 是 | 输入的 SQL 查询结果 |
| output_data | JSON | 否 | 算法输出结果 |
| execution_time_ms | INT | 否 | 执行耗时（毫秒） |
| success | BOOLEAN | 是 | 是否执行成功 |
| error_message | TEXT | 否 | 错误信息 |
| created_at | DATETIME | 是 | 创建时间 |
| tool_call_id | VARCHAR(64) | 否 | 关联的 Agent tool call ID，用于精确关联到对话中的某次算法调用 |

### 3.3 新增表：algorithm_template（Phase 2）

存储平台预置和用户保存的算法模板（只存 prompt 元数据，不包含代码）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|

| input_schema | JSON | 是 | 输入参数定义 |
| output_schema | JSON | 是 | 输出参数定义 |
| framework_hint | VARCHAR(128) | 否 | 推荐使用的 Python 库 |
| prompt_hint | TEXT | 是 | 引导 LLM 生成代码的 prompt |
| prompt_version | VARCHAR(16) | 否 | prompt 版本号，用于迭代优化 |
| is_system | BOOLEAN | 是 | 是否平台预置（true=预置，不可删除；false=用户保存） |
| usage_count | INT | 是 | 使用次数 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 否 | 更新时间 |

## 四、实现方案

### 4.1 架构总览

```
用户自然语言
    │
    ▼
┌─────────────────────────────────────────────────────────────────────┐
│ IntentParser: 意图解析（Phase 2）                                    │
│   1. 识别业务场景（排产/预测/检测/优化）                              │
│   2. 提取约束条件（交期、产能、成本）                                 │
│   3. 提取优化目标（产能利用率最高、成本最低、交期最早）               │
│   4. 匹配概念知识图谱                                                │
└─────────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────────┐
│ AlgorithmRouter: 算法路由（按优先级）                                │
│   ① 已注册企业算法？→ ALGORITHM action（精确，可审计）               │
│   ② 匹配预置模板？  → 填充参数 → CODE_MODE 生成代码（通用，中等精度）│
│   ③ 无匹配          → LLM 自由生成 CODE_MODE（灵活，需复核）         │
└─────────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ContextBuilder: 构建上下文 Prompt                                    │
│   1. FAISS 向量检索 → 匹配概念                                       │
│   2. toolConceptRepository.findByConceptIdIn() → 发现关联算法        │
│   3. 注入算法列表到 prompt（名称、描述、输入/输出 schema）            │
│   4. 注入概念-算法关系（INVOKES/INPUT_OF/OUTPUT_OF）                 │
│   5. 注入预置模板列表（Phase 2）                                     │
└─────────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────────┐
│ AgentService: ReAct Agent Loop                                       │
│   routeByType():                                                     │
│     ├─ nl2sql      → buildNl2sqlExecutorNode()  (查数据)             │
│     ├─ algorithm   → buildAlgorithmExecutorNode() (调算法)  ★新增    │
│     ├─ code_mode   → buildCodeExecutorNode()     (LLM 写代码)        │
│     ├─ tool_call   → buildToolExecutorNode()     (API 工具)          │
│     └─ final_answer → buildFinalAnswerNode()     (输出结果)          │
└─────────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────────┐
│ CodeExecutorService: Python 执行通道（复用）                          │
│   - 企业算法：脚本路径从 ToolDefinition.config.scriptPath 获取        │
│   - 算法模板：LLM 生成代码 + 标准库（scipy/numpy）                    │
│   - CODE_MODE：LLM 自由生成代码                                      │
│   - SQL 查询结果作为 input_data 传入                                  │
│   - 返回 stdout/stderr + 结构化输出                                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 核心改动点

```java
        List<Map<String, Object>> messages, Map<String, Object> parsed) {

    @SuppressWarnings("unchecked")
```

**改动点 C**：新增 `buildAlgorithmExecutorNode()` 方法：

```java
private AsyncNodeAction<AgentState> buildAlgorithmExecutorNode() {
    return (state) -> {
        Map<String, Object> data = new LinkedHashMap<>(state.data());
        @SuppressWarnings("unchecked")
        Map<String, Object> algoCall = (Map<String, Object>) data.get("pending_algorithm");
        String algorithmName = (String) algoCall.get("algorithm_name");
        @SuppressWarnings("unchecked")
        Map<String, Object> inputData = (Map<String, Object>) algoCall.getOrDefault("input_data", Map.of());
        String toolCallId = (String) algoCall.get("tool_call_id");
        String sessionId = (String) data.get("session_id");
        String userQuery = (String) data.get("user_query");
        @SuppressWarnings("unchecked")
        List<Map<String, Object>> messages = (List<Map<String, Object>>) data.get("messages");

        // 1. 根据算法名称查找 ToolDefinition
        ToolDefinition algo = toolDefinitionRepository.findByName(algorithmName);
        if (algo == null || !"ALGORITHM".equals(algo.getToolType())) {
            messages.add(Map.of("role", "tool", "tool_call_id", toolCallId,
                "content", "算法 " + algorithmName + " 未找到或已禁用"));
            data.put("next_action", "continue");
            data.remove("pending_algorithm");
            return CompletableFuture.completedFuture(data);
        }

        // 2. 从 config JSON 中解析脚本路径和超时
        Config config = parseConfig(algo.getConfig()); // JSON → {"scriptPath":"...","timeout":30}
        String scriptPath = config.getScriptPath();
        int timeout = config.getTimeout();

        long startTime = System.currentTimeMillis();
        Map<String, Object> result = codeExecutorService.executeScript(scriptPath, inputData, timeout);
        long elapsed = System.currentTimeMillis() - startTime;

        Boolean success = (Boolean) result.getOrDefault("success", false);
        String stdout = (String) result.getOrDefault("stdout", "");
        String stderr = (String) result.getOrDefault("stderr", "");

        // 3. 记录执行日志
        saveExecutionLog(algorithmExecutionLogRepository, algo.getId(), sessionId,
            toolCallId, userQuery, inputData, success ? stdout : null, elapsed,
            success, success ? null : stderr);

        // 4. 校验算法输出必须是 JSON 格式
        if (success) {
            try {
                objectMapper.readTree(stdout); // 验证 stdout 是合法 JSON
            } catch (Exception e) {
                messages.add(Map.of("role", "tool", "tool_call_id", toolCallId,
                    "content", "算法 " + algorithmName + " 输出格式错误：期望 JSON，实际输出非 JSON 格式"));
                data.put("next_action", "continue");
                data.remove("pending_algorithm");
                return CompletableFuture.completedFuture(data);
            }
            messages.add(Map.of("role", "tool", "tool_call_id", toolCallId,
                "content", "算法 " + algorithmName + " 执行成功，耗时 " + elapsed + "ms:\n" + stdout));
        } else {
            messages.add(Map.of("role", "tool", "tool_call_id", toolCallId,
                "content", "算法 " + algorithmName + " 执行失败（耗时 " + elapsed + "ms）: " + stderr));
        }

        data.put("next_action", "continue");
        data.remove("pending_algorithm");
        return CompletableFuture.completedFuture(data);
    };
}
```

**注意**：
- `algorithm_name` 匹配 `ToolDefinition.name` 字段，非 `toolType`
- config JSON 格式为 `{"scriptPath": "/data/algorithms/scheduling.py", "timeout": 30}`
- 算法脚本入口必须为 `def main(input_data):`，返回 `dict`（JSON 序列化后输出到 stdout）
- **算法必须输出 JSON 到 stdout**，否则 LLM 无法可靠解析结果
- `stderr` 直接透传给 LLM 作为错误信息（含 traceback），LLM 可据此决定重试或降级
- `toolCallId` 使用完整 UUID（32 位 hex），确保无碰撞

| 编号 | 场景 | 预期行为 | 前置条件 | 模拟方法 |

**E-04 数据不足的契约约定**：算法脚本必须通过返回特定格式的 JSON 来告知 Agent 数据不足：
```json

```
LLM 收到此错误后，应自动调用 nl2sql 补查缺失字段的数据，然后重新调用算法。

**E-05 多算法选择逻辑**：当 ContextBuilder 注入多个算法时，LLM 根据以下优先级选择：
1. 算法名与用户意图关键词匹配度最高
2. 算法的 input_schema 与已查询到的数据字段匹配度最高
3. 若无法确定，LLM 逐一调用（最多 3 个），取首个成功结果

#### A.1.4 【模板】质量异常检测

| 属性 | 值 |
|------|-----|
| 类别 | QUALITY |
| 框架 | IQR 法 + 3-sigma |
| 输入 | `metrics`(list[float], 指标时序数据), `timestamps`(list[str]) |
| 输出 | `anomalies`(list[{index, value, timestamp, method, severity}]), `stats`({mean, std, q1, q3, iqr}) |
| 优化目标 | 识别异常点，区分偶发异常和趋势异常 |

**prompt_hint**：

```
你是一个质量管理专家。请编写 Python 代码检测指标异常：
- 使用 IQR 法：异常值 < Q1-1.5×IQR 或 > Q3+1.5×IQR
- 使用 3-sigma 法：异常值偏离均值超过 3 个标准差
```

### A.5 模板使用说明

#### 模板存储结构

模板存储在 `algorithm_template` 表中，不在 `tool_definition` 中：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| name | VARCHAR(64) | 模板名称 |
| category | VARCHAR(32) | 类别（SCHEDULING/INVENTORY/QUALITY/RISK/FRAUD/CRM/NETWORK/MARKETING/SERVICE/ANALYSIS/PATROL/INVESTIGATION/MONITORING） |
| domain | VARCHAR(32) | 领域（MANUFACTURING/FINANCE/TELECOM/PUBLIC_SECURITY） |
| input_schema | JSON | 输入参数定义 |
| output_schema | JSON | 输出参数定义 |
| framework_hint | VARCHAR(128) | 推荐使用的 Python 库 |
| prompt_hint | TEXT | 引导 LLM 生成代码的 prompt |
| is_system | BOOLEAN | 是否平台预置（true=预置，false=用户保存） |
| usage_count | INT | 使用次数 |
| created_at | DATETIME | 创建时间 |

#### 模板使用流程

```
1. 用户提问 → IntentParser 提取场景和约束
2. AlgorithmRouter 查找匹配模板（按 category + 关键词匹配）
3. 命中模板 → 将 prompt_hint + input_schema 注入 LLM 上下文
4. LLM 按模板生成代码 → CodeExecutorService 执行
5. 执行成功 → 用户可选"保存为模板"（usage_count+1, 存入用户模板库）
```

#### 模板与 CODE_MODE 的区别

| 维度 | CODE_MODE | 算法模板 |
|------|------|------|
| Prompt 来源 | 通用 system prompt | 场景专属 prompt_hint |
| 代码质量 | 不稳定，取决于 LLM | 更稳定，有框架引导 |
| 可复用性 | 每次重新生成 | 模板可复用，积累优化 |
| 适用场景 | 任意 | 模板覆盖的场景 |
