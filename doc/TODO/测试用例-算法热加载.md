## 一、场景概述：离散制造业智能排产

### 1.1 业务背景

离散制造业（如电子装配、机械加工、汽车零部件）的排产决策远比流程制造业复杂。流程制造业（化工/钢铁）是连续流，排产主要看产能余量；离散制造业是多品种小批量、多工序多工作中心、有 BOM 展开和物料齐套约束，排产本质是一个 **约束满足 + 优化** 问题。

### 1.2 排产前置检验清单

在调用排产算法之前，必须完成以下前置检验。任何一项不通过，算法不应执行，而应返回具体原因供 LLM 解读给用户：

| 编号 | 检验项 | 检验内容 | 失败影响 | 对应本体概念 |
|:--:|------|------|------|------|
| P1 | **工作中心存在性** | 指定产线/工作中心在系统中是否存在 | 排产无执行主体 | 工作中心 |
| P2 | **工作中心可用性** | 产线当前是否在运行（非停机/维修/封存状态） | 无法排产 | 工作中心 → 设备可用率 |
| P3 | **额定产能 > 0** | 工作中心的日额定产能是否为正数 | 算法除零或无意义 | 工作中心 → 产能利用率 |
| P4 | **BOM 存在性** | 产品是否有 BOM 定义 | 不知道用什么料、走什么工序 | BOM |
| P5 | **工艺路线存在性** | 产品是否有工艺路线（至少 1 道工序） | 不知道在哪加工 | 工艺路线 |
| P6 | **物料齐套率** | BOM 展开后所有子项的可用库存是否满足生产数量 | 缺料无法开工 | BOM → 可用库存 |
| P7 | **已排产负荷** | 工作中心已排产数量 + 新订单数量 ≤ 日产能 × 排产天数 | 产能不足 | 产能利用率 → 工作中心 |
| P8 | **交期可达性** | 最早开工日 + 生产周期 ≤ 客户交期 | 无法按时交付 | 工艺路线 → 工作中心 |
| P9 | **设备可用率** | 关键工作中心的主设备可用率 ≥ 阈值（如 80%） | 设备故障风险高 | 设备可用率 → 设备 |
| P10 | **在制订单冲突** | 同一工作中心是否有未完工的在制订单与新订单工序冲突 | 工序干涉 | 生产订单 → 工作中心 |

### 1.3 本体概念覆盖分析

将前置检验映射到本体 SQL 中的概念：

| 前置检验 | 需要的概念 | 本体中是否存在 | 缺失说明 |
|---------|-----------|:--:|---------|
| P1 工作中心存在性 | 工作中心 | ✅ | 生产域 |
| P2 工作中心可用性 | 工作中心、设备可用率 | ✅ | 生产域 + 设备域 |
| P3 额定产能 > 0 | 工作中心、产能利用率 | ✅ | 生产域 |
| P4 BOM 存在性 | BOM | ✅ | 生产域 |
| P5 工艺路线存在性 | 工艺路线 | ✅ | 生产域 |
| P6 物料齐套率 | BOM、可用库存 | ✅ | 生产域 + 采购域 |
| P7 已排产负荷 | 产能利用率、工作中心 | ✅ | 生产域 |
| P8 交期可达性 | 工艺路线、工作中心 | ✅ | 生产域 |
| P9 设备可用率 | 设备可用率、设备 | ✅ | 设备域 |
| P10 在制订单冲突 | 生产订单、工作中心 | ✅ | 生产域 |

**结论**：现有本体概念**完全覆盖**排产前置检验所需的全部概念。无需新增概念。

**前置检验推导关系**（`concept_relation`，`relation_type` 为 `DERIVED_FROM`）：

P1~P10 的检验规则存储在 `init-scheduling-ontology.sql` 中，每条 `DERIVED_FROM` 关系的 `expression` 字段编码检验指令（SQL 查询模板 + 判定规则 + 失败影响）。ContextBuilder 沿 `INPUT_OF → Concept → DERIVED_FROM` 链路展开，将 `PRE_CHECK[Pn]` 指令注入 Agent prompt。

**算法绑定关系**（`ConceptToolBinding`，`binding_type` 为 `INVOKES`/`INPUT_OF`/`OUTPUT_OF`）：

| 算法 | 概念 | binding_type | 说明 |
|------|------|:--:|------|
| 排产可行性评估 | 工作中心 | INVOKES | 此概念的业务问题可调用排产算法 |
| 排产可行性评估 | 生产订单 | INVOKES | 此概念的业务问题可调用排产算法 |
| 排产可行性评估 | 工作中心 | INPUT_OF | 工作中心数据是排产算法的输入 |
| 排产可行性评估 | BOM | INPUT_OF | BOM 数据是排产算法的输入 |
| 排产可行性评估 | 工艺路线 | INPUT_OF | 工艺路线数据是排产算法的输入 |
| 排产可行性评估 | 可用库存 | INPUT_OF | 可用库存数据是排产算法的输入（齐套率计算） |
| 排产可行性评估 | 产能利用率 | INPUT_OF | 产能利用率数据是排产算法的输入 |
| 排产可行性评估 | 设备可用率 | INPUT_OF | 设备可用率数据是排产算法的输入 |
| 排产可行性评估 | 生产订单 | INPUT_OF | 在制生产订单是排产算法的输入（负荷计算） |
| 排产可行性评估 | 产能利用率 | OUTPUT_OF | 排产算法输出产能利用率预测 |

### 1.4 需求文档开发后能否实现

| 能力 | 需求文档是否覆盖 | 说明 |
|------|:--:|------|
| 算法注册（F1） | ✅ | ToolDefinition type=ALGORITHM |
| 本体绑定（F2） | ✅ | ConceptToolBinding binding_type=INVOKES/INPUT_OF/OUTPUT_OF |
| Agent 路由（F3） | ✅ | routeByType 新增 algorithm 分支 |
| 算法执行（F4） | ✅ | CodeExecutorService.executeScript() |
| 结果解读（F5） | ✅ | LLM 对算法输出自然语言解读 |
| 前端管理（F6） | ✅ | 复用 ToolListPage |
| 前置检验 | ✅ | **本体推导架构**：ContextBuilder 沿 INPUT_OF → DERIVED_FROM 展开，将 PRE_CHECK[Pn] 注入 prompt，LLM 执行 nl2sql 查询并判断 |
| 检验失败降级 | ✅ | LLM 解读前置检验失败原因 → 给出业务建议（不调用算法） |

**前置检验的实现策略**（本体推导 + LLM 执行）：

前置检验规则不由 LLM 每次凭经验生成，也不在算法脚本中硬编码，而是由本体概念关系推导：

```
ContextBuilder 注入算法时：
  1. 沿 ConceptToolBinding (INPUT_OF) 找到算法输入概念集合
  2. 对每个输入概念，沿 ConceptRelation (DERIVED_FROM) 展开推导关系
  3. 筛选 expression LIKE 'PRE_CHECK[P%]' 的推导关系
  4. 将匹配到的 PRE_CHECK 指令注入 Agent prompt

LLM 执行前置检验：
  1. 收到注入的 PRE_CHECK 指令
  2. 将模板占位符替换为对话上下文中的实际值
  3. 生成 nl2sql 查询并执行
  4. 根据判定规则判断通过/失败
  5. 全部通过 → 调用算法；任一失败 → 不调用算法，返回失败原因
```

## 三、测试数据准备

### 3.1 算法脚本

排产算法脚本 `scheduling.py`，放置在 `algorithms/` 目录下（由 `luban.algorithms.storage-path` 配置，默认 `algorithms`）。

**注意**：前置检验由本体推导 + LLM nl2sql 执行（见 1.4 节），算法脚本**只做约束优化求解**，不包含前置检验逻辑：

```python
import json
import sys


def schedule(data):
    """排产计算（简化版：单工作中心产能平衡）"""
    wc = data["work_center"]
    capacity = data["daily_capacity"]
    scheduled = data.get("already_scheduled", 0)
    qty = data["order_quantity"]
    available_days = data.get("available_days", 1)

    remaining = capacity - scheduled
    feasible = qty <= remaining
    utilization = (scheduled + qty) / capacity if capacity > 0 else 0
    required_days = qty / capacity if capacity > 0 else float("inf")

    result = {
        "feasible": feasible,
        "required_days": round(required_days, 2),
        "utilization": round(utilization, 4),
    }

    if feasible:
        result["suggested_start"] = "today"
        result["bottleneck"] = ""
    else:
        result["suggested_start"] = None
        result["bottleneck"] = f"产能不足，需 {qty} 件但剩余产能仅 {remaining} 件"

    return result


def main(input_data):
    data = json.loads(input_data) if isinstance(input_data, str) else input_data
    result = schedule(data)
    return json.dumps(result, ensure_ascii=False)


if __name__ == "__main__":
    input_data = sys.stdin.read()
    print(main(input_data))
```
