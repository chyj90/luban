## 一、背景

### 1.1 现状

当前问数流程是一条 6 级管道：

```
用户问题 → ① 问题理解 → ② 概念匹配 → ③ 思维链 → ④ SQL 生成 → ⑤ 查询执行 → ⑥ 最终回答
```

现有反馈系统（`concept_feedback` 表）混杂了点赞和点踩，但点赞从未被真正利用——管理员不需要知道"用户满意"，只需要知道"哪里出了问题"。管理员拿到的反馈是"用户说结果不对"，但不知道是管道中哪个环节出了问题。

### 1.2 问题

| 问题 | 影响 | 严重度 |
|------|------|:--:|
| 反馈粒度是整条回复 | 管理员无法定位具体出错环节，只能靠 LLM 猜 | 🔴 严重 |
| 上下文采集不完整 | 缺少 SQL、查询结果、思维链，LLM 分析质量差 | 🔴 严重 |
| 点踩 `userQuestion` 传错 | 前端点踩时传了 AI 回复而非用户问题 | 🟠 高 |
| 反馈无管道定位 | 用户无法指出"概念匹配错了"还是"SQL 写错了" | 🟠 高 |
| 逐条独立处理 | 多条反馈无法聚合分析，看不到模式 | 🟡 中 |
| 点赞功能冗余 | 点赞从未被分析利用，数据库混存赞/踩数据，徒增复杂度 | 🟡 中 |

### 1.3 目标

**只保留问题反馈**，去除点赞。将反馈从"结果级"升级为"管道级"，实现：

1. **用户可精确定位**：在问数管道的哪个环节出了问题
2. **上下文完整采集**：该环节及前置环节的完整上下文自动带入
3. **管理员可高效处理**：反馈自带管道定位 + 完整上下文，LLM 分析更精准
4. **支持聚合分析**：多条反馈可批量分析，发现模式

## 二、问题反馈架构

### 2.1 问数管道定义

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 阶段  │ 名称       │ 输入                │ 输出                        │
├───────┼────────────┼─────────────────────┼─────────────────────────────┤
│ ①     │ 问题理解   │ 用户原始问题          │ NLU 解析结果                 │
│ ②     │ 概念匹配   │ NLU 解析结果          │ FAISS 匹配 + 本体展开         │
│ ③     │ 思维链     │ 匹配的概念 + 表结构    │ LLM 推理步骤                 │
│ ④     │ SQL 生成   │ 思维链 + 表结构       │ SQL 语句                     │
│ ⑤     │ 查询执行   │ SQL 语句             │ 查询结果 + 执行状态           │
│ ⑥     │ 最终回答   │ 查询结果 + 思维链     │ 自然语言回答                  │
└───────┴────────────┴─────────────────────┴─────────────────────────────┘
```

### 2.2 问题反馈流程

**核心原则**：用户不需要理解管道阶段，只需要用自然语言描述遇到的问题。LLM 自动将问题定位到具体阶段。

```
**为什么不让用户选择阶段？**

- 用户可能同时遇到多个阶段的问题（如上面的例子：② 和 ⑤ 都有问题）
- 用户不一定能准确判断问题出在哪个阶段（"概念好像错了"用户可能去点 ③ 思维链）
- 用户只需要描述现象，LLM 对照管道各阶段的输入输出，能更准确地定位
- 减少用户操作步骤，降低反馈门槛
```

### 2.3 交互规则

| 操作 | 行为 |
|------|------|
| 点击 [问题反馈] 按钮 | 打开问题反馈表单，弹出一个文本输入框 |

| 非问数消息（如问候） | 不显示管道面板，不显示反馈入口 |
| 管道不完整（中断未续写） | 不显示 [问题反馈] 按钮 |
| 已提交过反馈的管道 | [问题反馈] 按钮置灰，不可重复提交 |

### 2.4 中断续写边界情况

#### 2.4.1 问题场景

AI 回答可能因 token 上限、超时、流中断等原因被截断，用户会要求续写。用户续写时可能说"继续"、"接着来"、"你还没说完"、"go on"等任意表述，**不能靠关键词匹配判断是否是续写**。

```
场景示例：

用户: 华东区上周销量多少？        ← 问题 A（有完整管道）
AI:   华东区上周销量为... [中断]   
用户: 继续                        ← 续写指令（无独立管道）
AI:   ...12,340 件。              ← 继续输出

用户点击 [反馈] → 反馈模块应拿到问题 A，而非"继续"
```

#### 2.4.2 核心原则

**管道归属原始问题，反馈始终指向原始问题 A。**

- "继续"是续写指令，不是新问题，没有独立的管道
- 管道的所有阶段（问题理解、概念匹配、思维链、SQL……）都基于原始问题 A 构建
- 反馈提交时，`userQuestion` 字段必须填原始问题 A，而非续写指令

#### 2.4.3 解决方案：后端状态驱动 + LLM 意图分类

不靠前端匹配关键词，而是后端维护中断状态，结合 LLM 做轻量意图分类。

**整体流程**：

```
1. AI 回复中断 → 后端设置 session.pendingContinuation = true
2. 用户发送下一条消息
   ├── pendingContinuation = true
   │    ├── LLM 意图分类：续写 or 新问题？
   │    │
   │    ├── 续写 → 合并管道，userQuestion 保持原始问题 A
   │    │
   │    └── 新问题 → 清空中断标记，新建管道，userQuestion = 当前消息
   │
   └── pendingContinuation = false
        └── 正常流程，新建管道
```

#### 2.4.4 意图分类

判断用户输入是"续写"还是"新问题"。**规则优先 + LLM 兜底**，避免每次都调 LLM（节省 200-500ms 延迟和 token 消耗）：

```
1. 如果 session_continuation.pending_continuation = true：
   a. 规则匹配续写：消息长度 < 20 且匹配 /^(继续|接着|go on|continue|还有吗|没说完|说完|你还没说完|接着输出)/i → 续写
   b. 规则匹配新问题：消息包含疑问词（多少|什么|怎么|为什么|查询|分析|呢|吗|不对|纠正）→ 新问题
   c. 规则无法判断 → 调 LLM 零样本分类（兜底，实际触发率 < 5%）
2. 默认新问题
```

**LLM 兜底 Prompt**（仅规则无法判断时调用）：

```
你是对话意图分类器。上一个 AI 回答被中断了。判断用户当前的输入是"续写"还是"新问题"。

上一个问题: {lastUserQuestion}
被中断的回答: {lastAssistantResponse 截取末尾 500 字}

用户当前输入: "{userMessage}"

规则:
- 续写: 用户想让 AI 继续完成上一个回答，没有提出新问题
- 新问题: 用户提出了新问题，或纠正/修改了上一个问题

只回复 "续写" 或 "新问题"。
```

**分类示例**：

| 用户输入 | 分类结果 | 管道行为 |
|---------|---------|---------|
| "继续" | 续写 | 合并管道，原始问题不变 |
| "接着输出" | 续写 | 合并管道，原始问题不变 |
| "你还没说完" | 续写 | 合并管道，原始问题不变 |
| "go on" | 续写 | 合并管道，原始问题不变 |
| "华南区呢" | 新问题 | 新建管道，问题="华南区销量" |
| "不对，我要的是订单数" | 新问题 | 新建管道，问题=纠正后的问题 |
| "再查一下上个月的" | 新问题 | 新建管道，问题=新问题 |

**兜底策略**：分类不确定时，默认为"新问题"（宁可新建管道，也不错乱合并）。

#### 2.4.5 管道合并

当意图分类为"续写"时，后端从中断点继续执行剩余阶段，合并到原管道：

```
原始管道（中断时）:
  ① 问题理解 ✅ → ② 概念匹配 ✅ → ③ 思维链 ⏳（中断）

续写后继续执行:
  ③ 思维链 ✅ → ④ SQL 生成 ✅ → ⑤ 查询执行 ✅ → ⑥ 最终回答 ✅

合并后完整管道:
  ① 问题理解 ✅ → ② 概念匹配 ✅ → ③ 思维链 ✅ → ④ SQL ✅ → ⑤ 查询 ✅ → ⑥ 回答 ✅
  userQuestion: "华东区上周销量多少？"（不变）
```

**合并规则**：
- 从 `lastCompletedStage + 1` 开始继续执行，不重复执行已完成阶段
- 合并后的管道归属原始问题消息，续写指令消息不绑定管道
- 管道标记 `isContinued: true`，记录 `continuationMessageId`

```

│                                                                     │

提交的反馈:
```

- 如果管道不完整（AI 中断后用户还没续写），不显示反馈按钮

#### 2.4.7 数据结构扩展

```typescript
interface PipelineTrace {
  // ... 已有字段 ...

  /** 是否为续写合并的管道 */
  isContinued?: boolean;
  /** 续写指令消息 ID */
  continuationMessageId?: string;
  /** 中断原因 */
  interruptReason?: 'token_limit' | 'timeout' | 'stream_error' | 'user_cancelled';
}
```

**会话中断状态必须落库**（不能只存内存），原因：

- 服务重启 → 内存状态丢失 → 用户说"继续"被当成新问题
- 多实例部署 → 请求打到不同实例 → 状态不一致
- 长时间中断（用户 10 分钟后回来）→ 内存状态可能被 GC

```sql
CREATE TABLE session_continuation (
  session_id VARCHAR(64) PRIMARY KEY,
  pending_continuation BOOLEAN NOT NULL DEFAULT FALSE,
  last_interrupted_message_id VARCHAR(64),
  last_user_question TEXT,
  last_partial_response TEXT COMMENT '中断前的部分输出，用于续写拼接',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

> **读写时机**：AI 回复中断时写入/更新，意图分类后清除。TTL 策略：`updated_at` 超过 30 分钟的记录可由定时任务清理。

## 三、管道数据结构

### 3.1 管道 Trace 定义

```typescript
interface PipelineTrace {
  /** 管道唯一标识 */
  pipelineId: string;
  /** 所属会话 */
  sessionId: string;
  /** 所属消息（原始问题消息 ID） */
  messageId: string;
  /** 用户原始问题 */
  userQuestion: string;
  /** 各阶段追踪 */
  stages: PipelineStage[];
  /** 对话历史通过 sessionId 实时获取，不在此冗余存储 */
  /** 是否为续写合并的管道 */
  isContinued?: boolean;
  /** 续写指令消息 ID */
  continuationMessageId?: string;
  /** 中断原因 */
  interruptReason?: 'token_limit' | 'timeout' | 'stream_error' | 'user_cancelled';
}

interface ChatTurn {
  role: 'user' | 'assistant';
  content: string;
  timestamp: string;
}

interface PipelineStage {
  /** 阶段序号: 1-6 */
  stage: number;
  /** 阶段名称 */
  name: string;
  /** 阶段状态 */
  status: 'success' | 'warning' | 'error' | 'skipped';
  /** 阶段输入 */
  input: string;
  /** 阶段输出 */
  output: string;
  /** 阶段详情（结构化数据） */
  detail: Record<string, unknown>;
  /** 阶段耗时 */
  durationMs?: number;
}
```

### 3.2 各阶段 detail 内容

| 阶段 | detail 字段 | 说明 |
|------|------------|------|
| ① 问题理解 | `{ entities: [{ type, value, confidence }], intent: string }` | NLU 实体识别和意图分类 |
| ② 概念匹配 | `{ faiss: { concepts, confidence }, ontology: { concepts, depth }, submitted: { concepts, tableCount, joinCount } }` | FAISS 结果 + 本体展开 + 提交给 LLM 的概念 |
| ③ 思维链 | `{ steps: [{ description, dependencies }] }` | LLM 推理步骤 |
| ④ SQL 生成 | `{ sql: string, tables: string[], joins: JoinDef[] }` | 生成的 SQL 和涉及的表/JOIN |
| ⑤ 查询执行 | `{ success: boolean, rowCount: number, data: object[], error?: string, durationMs: number }` | 执行结果 |
| ⑥ 最终回答 | `{ answer: string, usedConcepts: { conceptId, conceptName }[] }` | 最终回答和使用的概念 |

### 4.3 LLM 阶段自动定位

**触发时机**：管理员在反馈工作台点击某条反馈的「详情」时，后端调用 LLM 分析用户描述，对照管道各阶段内容，自动判定问题出在哪些阶段。定位结果缓存到 `llm_analysis` 字段，后续查看无需重复调用。

> **为什么不在提交时定位**：用户提交的反馈不一定每条都被管理员处理，提交时触发 LLM 浪费成本。定位是给管理员看的，在管理员需要时再算。

**定位 Prompt**：

```
你是问题定位助手。用户对一次问数结果提出了反馈。请分析用户描述，对照管道各阶段的输入输出，判断问题出在哪些阶段。

## 管道各阶段
① 问题理解: {NLU 解析结果}
② 概念匹配: {FAISS + 本体展开}
③ 思维链: {推理步骤}
④ SQL 生成: {SQL 语句}
⑤ 查询执行: {查询结果}
⑥ 最终回答: {自然语言回答}

## 用户描述
{用户反馈文本}

## 输出格式
以 JSON 输出，只列出有问题的阶段（无问题的省略，减小 JSON 体积，且扩展性好——未来新增阶段无需改结构）：

```

## 五、数据模型

### 5.1 管道数据独立存储（不嵌套在反馈表中）

> **设计原则**：管道数据与反馈数据生命周期不同。一条管道可能被多次反馈引用，不应在每条反馈中存一份副本。对话历史同理，已存在于消息表中，无需冗余存储。

```sql
-- 管道追踪主表：一次问数一条记录
CREATE TABLE pipeline_trace (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  pipeline_id VARCHAR(64) NOT NULL,
  session_id VARCHAR(64) NOT NULL,
  message_id VARCHAR(64) NOT NULL,
  user_question TEXT NOT NULL,
  is_continued BOOLEAN DEFAULT FALSE,
  continuation_message_id VARCHAR(64),
  interrupt_reason VARCHAR(32),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_session (session_id),
  INDEX idx_message (message_id),
  UNIQUE INDEX uk_pipeline (pipeline_id)
);

-- 管道阶段明细表：每个阶段一行，避免单行 JSON 过大
CREATE TABLE pipeline_stage (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  pipeline_id VARCHAR(64) NOT NULL,
  stage TINYINT NOT NULL,
  name VARCHAR(32) NOT NULL,
  status VARCHAR(16) NOT NULL,
  input_json JSON,
  output_json JSON,
  detail_json JSON,
  duration_ms INT,
  INDEX idx_pipeline_stage (pipeline_id, stage),
  FOREIGN KEY (pipeline_id) REFERENCES pipeline_trace(pipeline_id)
);
```

### 5.2 扩展反馈表

```sql
ALTER TABLE concept_feedback
  ADD COLUMN pipeline_id VARCHAR(64) COMMENT '关联管道ID（引用 pipeline_trace）',
  ADD COLUMN user_description TEXT COMMENT '用户自然语言描述的问题',
  ADD COLUMN llm_analysis JSON COMMENT 'LLM 阶段定位结果 JSON',
  MODIFY COLUMN feedback_type VARCHAR(16) COMMENT 'dislike|problem_feedback';
```

> **注意**：`feedback_type` 不再有 `like`。所有反馈都是问题反馈，类型为 `problem_feedback`。
>
> **LLM 自动定位**：`user_description` 是用户唯一需要填写的字段。`llm_analysis` 由后端 LLM 在管理员查看详情时自动生成，包含问题阶段定位结果。不再需要用户手动选择 `feedback_stage`、`issue_type` 等字段。
>
> **管道数据引用**：反馈表通过 `pipeline_id` 关联 `pipeline_trace` 表，需要管道上下文时 JOIN 查询，不存副本。对话历史同理——通过 `session_id` + `message_id` 从消息表实时查前 N 轮，不冗余存储。

**反馈状态枚举**：

```java
public enum FeedbackStatus {
    PENDING,      // 待处理（用户刚提交）
    CONFIRMED,    // 管理员确认问题存在
    ANALYZING,    // LLM 分析中
    APPLIED,      // 已应用修复
    IGNORED       // 已忽略/误报
}
```

**反馈状态流转**：

```
pending（待处理）→ 管理员查看详情（LLM 定位）
  ├── 确认问题存在 → confirmed（已确认）
  │     ├── LLM 分析 → analyzing（分析中）
  │     │     └── 应用修复建议 → applied（已应用，本体热重载）
  │     └── 忽略 → ignored（已忽略）
  └── 确认问题不存在 → ignored（已忽略/误报）
```

### 5.3 删除冗余字段

```sql
-- 点赞相关字段不再需要，但保留 feedback_type 列兼容旧数据
-- 旧 like 数据保留或迁移到归档表，不参与问题反馈流程
```

### 5.4 新增索引

```sql
ALTER TABLE concept_feedback
  ADD INDEX idx_feedback_type (feedback_type),
  ADD INDEX idx_session_id (session_id),
  ADD INDEX idx_pipeline (pipeline_id);
```

## 八、LLM 分析增强

### 8.1 阶段一：自动定位（管理员查看反馈时触发）

管理员点击某条反馈的「详情」时，后端调用 LLM 分析用户描述，对照管道各阶段内容，自动判定问题出在哪些阶段。定位结果缓存到 `llm_analysis`，后续查看无需重复调用。

**定位 Prompt**（详见 4.3 节）

**输出存储**：定位结果存入 `llm_analysis` 字段，管理员在反馈详情中可直接查看。

### 8.2 阶段二：优化建议（管理员手动触发）

管理员在反馈详情页点击「LLM 分析」按钮后，LLM 结合阶段定位结果 + 管道上下文 + 概念详情，给出本体优化建议。

## 十一、风险与约束

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 管道数据不全（部分阶段无数据） | LLM 定位准确度下降 | 没有数据的阶段在 prompt 中标注"无数据"，LLM 仍可基于其他阶段分析 |
| 用户不理解管道概念 | 反馈率低 | 管道面板默认折叠，用户只需写自然语言描述，无需理解管道 |
| 管道数据量大 | 存储压力 | `pipeline_trace` 按需生成，不是每次问数都存 |
| LLM 阶段定位不准确 | 管理员看到错误定位 | 定位结果仅供参考，管理员可手动修正；反馈详情展示完整管道供人工判断 |
| LLM 批量分析质量 | 分析结果不可靠 | 保留人工审核环节，分析结果仅供参考 |
| 旧 `like` 数据清理 | 历史数据丢失 | 保留旧数据在表中，不删除，仅不再写入新 `like` |
