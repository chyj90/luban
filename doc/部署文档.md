# 鲁班平台部署执行手册

> **用法**：拿起来按 1、2、3… 顺序执行，不要跳步。每个阶段末尾有 ✓ 检查点，检查点不通过先解决再往下走；文末《部署完成验收清单》全部勾选 = 部署完成。
> 架构说明、密钥细节、换省/换行业等参考内容在附录，主流程不需要阅读附录。

## 开始前：准备清单

**0.1 环境要求**

- [ ] 服务器：JDK 17+、Maven 3.8+、Node.js 18+、Python 3.10+（启用代码沙箱需 Docker）
- [ ] MySQL 8.x 已就绪（可远程；部署账号对该实例有建库权限）
- [ ] 网络互通：服务器 ↔ MySQL、服务器 ↔ 大模型 API、用户浏览器 ↔ 服务器

**0.2 向客户收集的信息（缺一项，对应步骤会被卡住）**

- [ ] 平台元数据库连接信息（host/端口/账号密码）
- [ ] 业务库清单及**只读账号**（运营商：BOSS/经分/客服库；写明每库的业务含义）
- [ ] 客户行业（决定阶段二走哪条分支）
- [ ] 组织架构（部门树，用于权限边界，如地市/区县）
- [ ] 业务人员常用口语说法样本（几十条即可，用于方言词典，如"携转""拉新"）

## 阶段一：安装平台（约 30 分钟，全行业通用）

1. **配置平台元数据库**：编辑 `backend/src/main/resources/application.yml` 的 `spring.datasource`（url/username/password）。库可不存在，连接串已带 `createDatabaseIfNotExist=true`。
2. **启动语义服务**（提供概念向量检索与代码沙箱）：
   ```bash
   cd embedding-service && pip install -r requirements.txt && ./start.sh -d
   ```
3. **启动后端**（自动生成并持久化密钥，见附录 B）：
   ```bash
   cd backend && ./start.sh -d
   ```
4. **启动前端**：开发验证用 `cd frontend && npm install && npm run dev`（5173）；正式交付用 `npm run build` 后发布 `dist/` 并反代 API 到 8080。
5. **登录验证**：浏览器打开平台地址，用超管账号登录（首次启动种子账号 **root / 123456**，登录后立即改密）。

✓ **检查点 1**
- [ ] 启动日志出现 `Started LubanApplication`
- [ ] 启动日志出现 `平台语义包就绪`（组织/人员/部门，全行业必有）
- [ ] 浏览器能登录进平台首页

## 阶段二：就位行业语义包（分叉点）

**判断：客户是什么行业？**

### 分支 A：客户是运营商（内置包，开箱即用）

1. 确认阶段一启动日志出现 `运营商语义包就绪：数据源「运营商演示库」→ 独立演示库 luban_demo_operator，概念 8 个`。
2. **保持 `luban.operator-package.enabled=true` 不要关**（生产也建议保留）：标准层概念与演示库一起就位，演示库不影响真实数据源，可作培训环境和回归基线。只有非运营商行业才关闭它。
3. 确认回归题集就位：建模中心 → 语义包回归 → 列表应出现「运营商语义包（8 用例）」。

→ 直接进入阶段三。

### 分支 B：客户是其他行业（平台当前**没有**内置该行业包）

**先弄包，再继续部署。** 按下列优先级三选一：

1. **向平台厂商索取行业语义包**（首选）：语义包交付物是"五件套"——行业 Seeder（概念+关系+映射骨架）、方言词典、回归题集 JSON、演示库结构、演示数据。厂商随平台版本内置交付，拿到含该行业包的平台版本后，按该版本说明启用（通常为 `luban.<行业>-package.enabled=true`）并重启。**弄完再进入阶段三。**
2. **自制语义包**（厂商未覆盖且交付周期不可接受时）：参照 `backend/src/main/java/com/luban/config/OperatorOntologySeeder.java` 实现行业五件套（概念描述**不得写死表名**，映射留给阶段三自动绑定；参照 `backend/src/main/resources/ontology-questionsets/operator-semantics.json` 编写回归题集）。开发-自测完成后随版本发布，再进入阶段三。
3. **降级路径：先部署后补包**（客户着急上线时）：不启用行业包，进入阶段三前先用 ConceptImportService（建模中心 → 概念导入）从客户的行业口径手册/文档导入概念，阶段三手工补映射。**注意**：此路径缺关系/词典/题集，问数命中率有限，属过渡方案，语义包到位后替换。

✓ **检查点 2**
- [ ] 分支 A：`运营商语义包就绪` 日志出现，回归列表有运营商题集
- [ ] 分支 B：所选路径的语义包已就位（启动日志/回归列表可见）；选降级路径的，已记录"补包计划"并告知客户

## 阶段三：接入客户数据源并与语义层对齐（核心，0.5–2 天）

> 本阶段目标：业务库的表列与语义层（概念→映射）对上，且用回归证明对上了。

1. **新建系统**：建模中心 → 系统管理 → 「新建系统」（填系统名/编码，如"BOSS核心"/"经分"）。一个源系统一条记录。
2. **新建数据源并测通**：选中该系统 → 「新建数据源」（类型选 MySQL 等，填 host/端口/库名/**只读账号**）→ 列表中点「测试连接」→ 状态变为**已连接**。逐库重复。
3. **自动绑定（映射生成）**：建模中心 → 绑定管理 → 对每个数据源执行**自动绑定**（规则优先 + LLM 兜底，后台任务自动轮询完成）。完成后查看绑定明细。
4. **人工复核关键映射**（自动绑定不等于正确，以下五类必须人工过目）：
   - 金额/数量类：单位、是否含税、正负号
   - 状态/类型枚举：在网/离网、已缴/未缴等枚举值与库中实际值一致
   - 时间锚列：指标用哪个时间字段归属账期/日（错一个，所有趋势都错）
   - JOIN 路径：概念间关联字段是否唯一、是否漏桥表
   - 组织字段：地市/区县/部门与平台组织架构对齐（权限依赖它）
5. **方言词典本地化**：绑定管理 → 该数据源绑定集 → 术语词典，把 0.2 收集的口语说法逐条配上概念（term/synonyms/conceptName）。
6. **概念域授权**：平台管理 → 角色管理 → 概念域授权，按"谁能看哪些业务数据"配好角色边界（如地市账号只授本地市域）。
7. **本地化回归题集**：复制 `backend/src/main/resources/ontology-questionsets/operator-semantics.json` 为 `operator-province-<省>.json`，把 `sqlContains` 断言改为客户真实表名（拿不准的可只保留 `mustHitConcepts`）。
8. **跑回归**：建模中心 → 语义包回归 → 运行本地化题集 → 查看报告。

✓ **检查点 3**
- [ ] 每个业务库状态"已连接"
- [ ] 自动绑定完成且第 4 步五类映射复核通过
- [ ] 回归报告 **100% 通过**；有失败 → 回到第 4/5 步修映射或词典，重跑直到全过

## 阶段四：开通用户并交付（约 0.5 天）

1. **建账号与角色**：平台管理 → 用户/组织（导入部门树）→ 角色分配（基线见附录 E）。

| 组件 | 技术 | 默认端口 | 说明 |

数据边界：平台库只存平台元数据。业务数据（含演示数据）一律在外部库——运营商演示表在独立库 `luban_demo_operator`，与平台库物理解耦。

## 附录 B：密钥管理

`backend/start.sh` 首次运行自动生成并持久化到 `backend/.env`（已 gitignore，勿提交）：

| 环境变量 | 用途 |
|---|---|
| `LUBAN_JWT_SECRET` | 登录态签名；未注入时用随机临时密钥，重启后登录态全部失效 |
| `LUBAN_DATASOURCE_SECRET` | 数据源密码加密；**换密钥后外部数据源需重新保存密码**，内置演示数据源启动自愈 |
| `LUBAN_AGENT_AES_KEY` | 大模型 API Key 加密 |
| `LUBAN_RSA_PRIVATE_KEY` | 传输层信封加密私钥 |

生产要求：一律环境变量外部注入（或审核 start.sh 生成的 .env）；大模型 Key 用 `LUBAN_LLM_API_KEY / LUBAN_LLM_ENDPOINT / LUBAN_LLM_MODEL` 初始化，或在「建模中心 → 大模型配置」填写。

**多副本（K8s 多 Pod）硬性要求**：这 4 个密钥必须**所有 backend Pod 完全一致**——不一致时 A Pod 签发的登录态在 B Pod 上验签失败，表现为间歇性 401、登录失败、数据源密码解不开。两种做法：

1. **K8s Secret 注入环境变量（推荐）**：entrypoint 检测到环境变量已配置时直接复用、不再生成；
2. **共享卷**：同一 RWX 卷挂到所有 backend Pod 的 `/app/secrets`。注意首启竞态——多个 Pod 同时冷启动会各自生成密钥并互相覆盖 `luban.env`，必须先用 Job/Hook 预生成好 `luban.env` 再拉起 Pod；拿不准就用方式 1。

## 附录 D：已部署之后——换省 / 换行业 / 换库

> 核心原则：**标准层随软件走，本地层不带走。**

**换省公司（同行业新客户）**：
- 自动获得：标准层骨架（种子）、平台语义包、演示语义。带不走也不该带走：表列映射、方言本地化、组织权限、问数历史。
- 全新环境（推荐）：重走本手册阶段一→四（映射与词典按新省现场生成）。
- 原环境重置：备份并清空平台库、删除旧省业务库与演示库 → 重启种子自重建 → 从阶段二第 2 步继续。
- 旧省下线：导出审计数据（变更台账、回归报告）后连库回收。

**换行业**：在换省步骤之上增加——
1. 关闭旧行业包（`luban.operator-package.enabled=false`）
2. 清理语义残留：删除旧行业演示数据源、概念域、演示库、题集 JSON
3. 归档 `agent_query_log` 旧概念引用（否则健康度统计失真）
4. 已固化查询不受影响（SQL 文本不依赖概念运行时）
5. 按阶段二分支 B 部署新行业包 → 重走阶段三、四
6. 平台语义（组织/人员/部门）任何行业都保留

**省内换库/表结构变更**：接新库 → 绑定管理重新自动绑定并复核 → 更新本地化题集表名断言 → 回归通过交付。业务用户口径不变、无感。

## 附录 F：常见问题排查

| 现象 | 原因与处理 |
|---|---|
| 日志「运营商语义包初始化失败」 | 数据库账号无建库权限：授权，或 `luban.operator-package.enabled=false` 跳过 |
| 问数报「Embedding 服务不可用」降级 | 语义服务 8765 未启动或沙箱镜像构建失败，看 `embedding-service/logs/server.log` |
| 换 DATASOURCE_SECRET 后外部数据源连不上 | 重新保存该数据源密码即可；内置演示数据源自愈 |
| 自动绑定结果大量为空 | 概念与客户表差异过大：先人工补核心概念的映射，再跑绑定收敛 |
| 回归用例失败 | 看报告里失败的断言类型：概念未命中→补词典；SQL 落表错→修映射；回答不可用→查数据与权限 |
| 问数 300 秒超时 | 大模型端点可用性/网络连通性排查 |
| 登录态全部失效 | JWT 密钥变化（未用 start.sh 手工启动），统一用 start.sh |
| 多 Pod 场景间歇性 401 / 登录失败 | 各 Pod 密钥不一致：按附录 B 多副本要求统一注入，见附录 B、G |

## 附录 G：Kubernetes 部署要点

> 适用：用 K8s 承载平台容器（镜像与 compose 相同）。本附录只列 K8s 特有的边界与必备配置，不替代主流程。
> 多副本（backend / 语义服务均可 >1）已在本版本支持，前提是 G.2 的配置到位。

### G.1 副本数与扩容

| 组件 | 副本 | 说明 |
|---|---|---|
| backend | 1..N | 触发器派发已带认领（条件 UPDATE，防重复执行）；本体图 30s 指纹对账自动同步 |
| 语义服务 embedding | 1..N | 索引构建广播到全部实例 + 检索失败自愈 + 60s 对账；要求 G.2 的端点配置 |
| mysql | 1 | 平台元数据库，建议使用客户环境的外部 RDS |

限流与并发闸门按 Pod 生效：API Key 限流（`LUBAN_APIKEY_RATE_LIMIT_MAX` / `LUBAN_APIKEY_RATE_LIMIT_DAILY_QUOTA`）与问数并发（`LUBAN_AGENT_CONCURRENT_LIMIT`，默认 5）的全局值 = 配置值 × Pod 数，多副本时按此校准。

### G.2 必备配置

**密钥**：4 个密钥全 Pod 一致，K8s Secret 注入 env（推荐）或共享卷，见附录 B。

**语义服务端点（多副本语义服务必配）**：`LUBAN_EMBEDDING_BASE_URL` 指向语义服务的 **headless Service**（如 `http://embedding-headless:8765`）——后端按 DNS A 记录自动发现全部 Pod，把索引构建广播到每一个实例。指向普通 Service 时只有检索负载均衡、构建无法广播，多副本索引会漂移。实例地址也可用 `EMBEDDING_SERVICE_ENDPOINTS` 显式列出（逗号分隔）。

**附件文件卷（跨节点必配 RWX）**：backend 与语义服务共享 `/app/files`（附件、Excel 解析路径都走它）。backend 与语义服务 Pod 可能调度到不同节点，跨节点时必须是 RWX 存储类（NFS/CephFS），RWO 卷会有一方挂载失败或路径不通：

```yaml
# backend 与 embedding 两个 Deployment 都挂同一 PVC
volumes:
  - name: files
    persistentVolumeClaim:
      claimName: luban-files   # RWX storageClass
# backend 容器挂载 /app/files；
# embedding 容器挂载 /app/files 并设置环境变量 LUBAN_FILES_ROOT=/app/files（代码执行路径边界校验依赖它）
```

**启动顺序（推荐）**：backend 启动时会做一次 EB 健康检查并重建语义索引，此时语义服务还在加载模型会让向量检索降级几分钟（此后自愈/对账会补齐）。用 initContainer 等语义服务就绪再启动 backend，首日起体验更稳：

```yaml
initContainers:
  - name: wait-embedding
    image: curlimages/curl:8.10.1
    command: ["sh", "-c",
      "until curl -sf http://embedding-headless:8765/health | grep -q '\"loaded\":true'; do sleep 3; done"]
```

**探针**：

```yaml
# embedding：模型加载完成才监听端口，用 startupProbe 覆盖加载期
startupProbe:   { httpGet: { path: /health, port: 8765 }, periodSeconds: 5, failureThreshold: 60 }
readinessProbe: { httpGet: { path: /health, port: 8765 } }
# backend：无免认证健康端点，用 TCP 探针
readinessProbe: { tcpSocket: { port: 8080 } }
livenessProbe:  { tcpSocket: { port: 8080 } }
```

**MCP 网关（使用 MCP 功能时才需要）**：MCP 的 SSE 会话绑定在接收连接的那个 backend Pod 上，须配 `sessionAffinity: ClientIP`（Service）或 ingress cookie 亲和（`nginx.ingress.kubernetes.io/affinity: "cookie"`）。

### G.3 语义服务更新 / 重启

1. 更新策略用 `Recreate`：`RollingUpdate` 会新旧 Pod 并存，新 Pod 索引未就绪会分到检索流量（自愈会补建，但更新窗口内有抖动）；
2. **无需人工重建索引**：Pod 重启丢失的索引由两层机制自动恢复——检索失败即时自愈 + 60s 逐实例对账（重启后 ≤90s 内补齐）。

### G.4 代码沙箱（生产必须开启）

生产环境 LLM 生成的代码必须在沙箱内执行。语义服务支持三种沙箱 runtime，按集群权限选择：

| `SANDBOX_RUNTIME` | 适用环境 | 沙箱形态 | 语义服务需要的权限 |
|---|---|---|---|
| `external` | **受限 K8s（无 K8s API 权限，本产品交付的默认场景）** | 运维人工部署的沙箱 Deployment，镜像内置 HTTP Agent（:9000） | 无任何 K8s API 权限，仅 HTTP 访问沙箱 Service |
| `k8s` | 允许 K8s API 的集群 | 语义服务经 K8s API 动态管理 Pod 池 | SA 需 `pods create/get/list/delete` + `pods/exec create` |
| `docker` | compose / 裸机 dev | docker 容器池（挂 docker.sock） | 容器内可访问 docker daemon |

三种模式池化协议一致（探活/熔断/巡检/超时），`GET <语义服务>/v1/sandbox/health` 可观测（返回 `runtime` 与逐槽状态）。

#### G.4.1 external：受限集群的外部托管沙箱池（无 API 权限）

K8s 集群不授予 API 权限时，**沙箱 Pod 由运维人工部署**（Deployment 固定副本），镜像内运行
`sandbox_agent.py` HTTP 服务；语义服务只能做两件事——探活（`GET /health`）与执行脚本
（`POST /execute`），**不能也无需控制 Pod 启停**：扩缩由运维改副本数，个别 Pod 损坏时
语义服务按槽位退避重探、恢复后自动重新纳管。

**第一步：人工部署沙箱 Deployment**（用 `embedding-service/Dockerfile.sandbox` 构建 `luban-sandbox` 镜像）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: luban-sandbox }
spec:
  replicas: 3                      # 建议 >= SANDBOX_POOL_SIZE
  selector: { matchLabels: { app: luban-sandbox } }
  template:
    metadata:
      labels: { app: luban-sandbox, luban.io/role: sandbox }
    spec:
      containers:
        - name: sandbox
          image: <registry>/luban-sandbox:latest
          ports: [ { containerPort: 9000 } ]
          env:
            - name: SANDBOX_AGENT_TOKEN       # 生产必须设置（执行任意代码的接口要鉴权）
              value: "<与语义服务一致的共享令牌>"
          securityContext:
            readOnlyRootFilesystem: true
            runAsNonRoot: true
          volumeMounts:
            - { name: tmp, mountPath: /tmp }  # Agent 工作目录（每次执行独立子目录）
          resources:
            limits:   { memory: 512Mi, cpu: "1" }
            requests: { memory: 512Mi, cpu: "1" }
      volumes:
        - name: tmp
          emptyDir: {}
---
apiVersion: v1
kind: Service
metadata: { name: luban-sandbox }
spec:
  selector: { app: luban-sandbox }
  ports: [ { port: 9000, targetPort: 9000 } ]
---
# 沙箱必须断网（等价 docker --network=none）：沙箱内代码不应能出网/进内网。
# 若集群 CNI 不支持 NetworkPolicy，须用其他手段兜底并向客户安全团队书面确认。
kind: NetworkPolicy
spec:
  podSelector: { matchLabels: { luban.io/role: sandbox } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: luban-embedding } }   # 仅语义服务可达
  # 无 egress 规则 = 出口全拒
```

**第二步：语义服务配置**（Deployment env）：

```yaml
env:
  - name: SANDBOX_ENABLED
    value: "true"
  - name: SANDBOX_RUNTIME
    value: "external"          # 受限集群必须显式指定（auto 会探测为 k8s 而失败）
  - name: SANDBOX_ENDPOINTS    # 普通 Service 地址即可；也可逐 Pod 地址列表
    value: "http://luban-sandbox:9000"
  - name: SANDBOX_AGENT_TOKEN  # 与沙箱 Deployment 一致
    value: "<共享令牌>"
  - name: SANDBOX_POOL_SIZE    # 全局并发上限；建议 <= 沙箱副本数（Pod 内并发受 512Mi 限制）
    value: "3"
```

**第三步：验收**

- `GET <语义服务>/v1/sandbox/health` 返回 `enabled: true, runtime: external, healthy: 3`（满池）；
- 平台上执行一次带代码分析的问数，确认结果正常；
- 沙箱网络隔离验证：沙箱 Pod 内 `curl` 外网地址不通（NetworkPolicy egress 全拒生效）；
- 扩缩演练：把 Deployment 副本改为 0，语义服务侧 `/v1/sandbox/health` 转 degraded
  （execute-code 类请求 503，普通问数不受影响）；恢复副本后满池自动纳管。

**附件解析（execute-code file_paths）**：给沙箱 Deployment 挂与语义服务**同一个只读文件 PVC**
（挂 `/mnt/files`，与 `LUBAN_FILES_ROOT` 指向同一数据卷）——沙箱代码经 `ctx['_files']` 拿到的
路径即从该卷读取，无需经 HTTP 传文件。

#### G.4.2 k8s：允许 API 权限集群的原生 Pod 池（保留能力）

集群授予 API 权限时可选本模式：语义服务经 ServiceAccount 动态管理 Pod 池（创建/探活/exec/删除），
槽位名自带实例后缀、ownerReference 级联回收（语义服务 Deployment 注入 `POD_NAME`/`POD_UID`
downward API）。沙箱 Pod 断网同 G.4.1 的 NetworkPolicy；语义服务 SA 需要：

```yaml
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["create", "get", "list", "delete"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
```

#### G.4.3 禁止事项

- **不要挂 docker.sock**（无论哪种部署形态）：等同交出节点 root，containerd 集群也没有 docker.sock；
- `SANDBOX_ENABLED=true` 但 runtime 未就绪时语义服务会**自动降级 subprocess 直跑**（仅日志 WARNING），
  隔离形同虚设——上线验收必须确认 `/v1/sandbox/health` 满池，不允许带降级运行。

### G.5 副本能力速查（本版本已落地）

| 能力 | 机制 |
|---|---|
| 语义索引多副本一致 | 构建广播（headless 发现全部实例）+ 检索失败自愈 + 60s 逐实例对账 |
| 列索引多数据源/多副本 | EB 按数据源分槽（v2 单槽互相覆盖）+ 结构指纹变更自动重建 + 缺失自愈 |
| 触发器不重复执行 | 条件 UPDATE 认领（PENDING→DISPATCHING）+ 5min 崩溃残留重认领 + 幂等键兜底 |
| 本体图跨实例同步 | 30s 指纹对账自动 reload（概念/关系/关系类型/变更台账） |
| EB 客户端自恢复 | 不可用状态 15s 节流重查，不再"启动判死永不恢复" |
| 沙箱生产开启 | 三 runtime（external 外部托管池 / k8s Pod 池 / docker），详见 G.4；受限集群用 external，语义服务零 API 权限 |
